This is where the map becomes real. You picked a high-value, high-feasibility task last lesson;
now you **automate it end to end** for one department. The skills are the same ones from the
workflows pillar. Here you point them at a single business process and ship it.

## Document the process first

The most common mistake is building the automation before you understand the manual process.
Draw the current workflow as a flowchart: **what triggers it, what steps happen, what decisions
get made, and what comes out the other end.** Talk to the person who does it today; they know the
edge cases that aren't written down. A clear flowchart is your spec. Without it, you're automating
confusion.

## Separate the plumbing from the judgment

Every business process is a mix of two things:

- **Deterministic plumbing**: move this data from email to spreadsheet, when X happens do Y, send
  this to that system. This is classic automation, and **n8n, Make or Zapier** handle it
  predictably. (If you code, a small script or serverless function does the same job.)
- **Judgment**: read this and decide, draft a reply, pull the right fields out of a messy
  document, route this ticket to the right team. This is where an **LLM step** goes.

Build the plumbing first with no AI, prove the data flows, *then* drop AI into the judgment nodes.
This separation keeps the system debuggable: when something breaks you know whether it's a wiring
problem or a prompt problem.

Make the AI node return **structured output**, a fixed JSON shape, rather than free text, and
validate it before anything downstream uses it (→ structured-outputs-tools). A rule like "total
must be a number, date must parse" catches most bad extractions before they reach a spreadsheet.

## Department patterns

- **Operations**: onboarding checklists, data entry between tools, status reports, scheduling.
- **Finance**: invoice and receipt extraction (accounts payable), reconciliation, expense
  categorization, payment-reminder drafts. Always human-approved before money moves
  (→ governance-security).
- **Support**: ticket tagging and routing, draft-first replies from your knowledge base,
  escalation triage, summarizing long threads for the next agent.

## Worked example: a receipts inbox

A small accounting firm receives client receipts by email, and someone types each one into a
spreadsheet. Here's the build:

1. **Trigger (plumbing).** A new email with an attachment arrives in the shared receipts inbox.
2. **Normalize (plumbing).** Save the attachment; convert it to text or an image the model can
   read; record the sender and the client it belongs to.
3. **Extract (AI judgment).** One LLM step returns JSON: vendor, date, total, tax, currency,
   category and a confidence level. Its prompt lists the allowed categories and says to mark
   anything unclear as low confidence rather than guess.
4. **Validate (plumbing).** Check the total is a number, the date parses, and the currency is
   expected. Failures and low-confidence items go to a "needs review" tab.
5. **Approve (human).** A staff member checks the pending rows and approves them into the
   ledger sheet. Unusual items are flagged to a partner, as before.
6. **Measure.** Before launch, time 20 receipts done by hand. After launch, time the review of
   20. That pair of numbers is your result.

Receipts contain personal and financial data, so use tools your firm has approved for it.

> 💡 **Try it:** Paste three real-looking (or invented) receipt emails into ChatGPT, Claude or
> Gemini with: "Extract vendor, date, total and currency as JSON. If a field is unclear, set it
> to null." Check each field by eye. Five minutes shows you where the judgment node will
> struggle.

## Human-in-the-loop, then promote

Start with **AI proposes, human approves.** This is non-negotiable for anything customer-facing or
money-touching. Run it on real volume, watch the error rate, and tune the prompt, kept versioned
like code (→ prompt-as-code). Only once a step is reliably accurate *and* low-risk do you promote
it to fully automatic. The goal isn't to remove humans; it's to remove the *boring* part and let
humans spend their judgment where it counts.

## Common failure modes

- **Garbage rows in the sheet** → the AI's output went straight downstream → require JSON and
  add a validation step that routes failures to review.
- **It fails quietly for days** → no error handling → add an error branch that alerts a named
  person when any step fails.
- **Odd inputs break it** → you tested only clean examples → build a test set of messy real
  cases (multi-page, foreign currency, photos) and re-run it after every prompt change.
- **Nobody knows which prompt is live** → edits made directly in the tool → keep the prompt in a
  versioned file and note every change.

## Instrument it

Capture the **before** (hours a week, cost, error rate) and the **after.** You'll need those
numbers twice: to know the automation actually worked, and for the ROI lesson that closes this
track.
