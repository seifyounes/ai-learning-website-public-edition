Here's the exciting part: in the AI coding era, a tight MVP genuinely fits in a
**weekend.** Everything from the *Shipping apps* pillar now runs at speed. But speed without
discipline just gets you to the wrong place faster, so this lesson is as much about what you
refuse to do as about what you build.

## Two routes, one discipline

You can get to a working MVP whether or not you code. The routes differ; the rules don't.

- **No-code route.** An AI app builder such as Lovable, Bolt, v0 or Replit's agent takes your
  spec as a prompt, builds the app in the browser and hosts it with a publish button. Many
  include a database and login, or connect to one. Best when you don't code or the product is
  simple.
- **Code route.** A builder (or a starter template) throws a skeleton, and you move into a
  coding agent (Claude Code, Cursor, Codex, GitHub Copilot) to build the core feature properly
  in a real repo. Best when the product is core to a business and will grow.

Either way, the spec from the last lesson is your input, and the cut list is the law.

## The fast path

1. **Spec**: your half-page MVP spec.
2. **Scaffold**: a builder or template turns it into a running skeleton in minutes.
3. **Engineer the core**: build the one feature properly and test it on real inputs.
4. **Backend, only if needed**: if the feature needs saved data or accounts, use a managed
   service (Supabase, Firebase, or the builder's own database) instead of writing your own.
5. **Deploy**: a public link via Vercel, Netlify or the builder's hosting. Mobile can be a
   test build instead (→ deploying-and-shipping).

Most of an MVP is glue and boilerplate, exactly what AI generates well. Your job is the
judgment: scope, quality on the core, and shipping.

## Worked example: a weekly football sign-up

The spec: players tap "I'm in" for this week's five-a-side game; the 11th person goes on a
waitlist; the organizer sees the list. Not yet: payments, chat, stats, reminders.

- **Friday evening (2 hours).** Paste the spec into a builder. Because the list must persist,
  ask for a simple database table: game date, player name, timestamp. Get a page that shows
  the list and an "I'm in" button.
- **Saturday (half a day).** Make the core feature *correct*: the waitlist kicks in at exactly
  ten, a player can drop out and the first waitlisted person moves up. Test it with fake names,
  including the edge cases: two people joining at once, someone joining twice.
- **Saturday evening.** Check the glue. Who can read the data? Who can delete a name? Lock it
  down so only the organizer can remove players.
- **Sunday.** Publish. Send the link to the real group chat for next week's game and watch
  what happens. Write down where people got confused.

That's a learning-ready MVP. It's not pretty, and it doesn't need to be.

## Check the glue before strangers use it

AI-generated apps work quickly but can ship unsafe defaults. Before you share a link: make
sure secret API keys are not in front-end code, that database access rules are switched on so
users only see what they should, and that a form can't be spammed into an expensive bill. Ask
your builder or coding agent directly: "Who can read and write each table? Are any secrets
exposed to the browser?"

> 💡 **Try it:** open any app you've built (or a builder's template), and ask its AI chat:
> "List every place user data is stored and who can read it." If the answer surprises you, fix
> that before you share the link.

## Common failure modes

- **The weekend ends with half of five features** → scope crept back in → reopen the cut list
  and finish the one core feature first.
- **The builder gets stuck in a fix-one-break-another loop** → too many changes per prompt on a
  growing app → revert to the last working version and ask for one small change at a time.
- **It works on your laptop but not at the link** → missing environment variables or a local-only
  setting → deploy early on Friday, not on Sunday night.
- **Users' data is visible to everyone** → default-open database rules → turn on access rules
  and re-test logged out.
- **No one tries it** → you never sent the link → pick the 3–5 people before you start.

## Speed is a weapon. Aim it.

The trap of fast building is using it to *avoid* validation: "it's quick, let's just build
it." Resist. Keep the discipline from the last two lessons (validated idea, tiny scope) and
let speed serve **learning**, not ego. A live v1 in front of real people on Monday teaches you
more than a "perfect" prototype you keep polishing. Once it's live, the natural next move for
many products is to make it smarter: adding AI features.
