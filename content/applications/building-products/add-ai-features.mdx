  Spec one small AI feature, prototype it and test it against a basic eval, in about 45
  minutes. Use the feature you kept in Apply it, or a neutral one such as "turn a messy customer
  email into a structured support ticket".

  ```prompt
  I'm building one AI feature for [product]: [one sentence: input → output]. Don't write app
  code yet. Give me: the system prompt; a strict JSON output schema; a guardrail my code can
  check (what every output must contain or avoid, plus length bounds); 5 test inputs (two easy,
  two messy, one that should be refused or flagged) with the expected output for each and a
  one-line pass/fail rule; and a cost ceiling (per-call token estimate, what to cache, and when
  to skip the model call entirely).
  ```

  Playground or the Anthropic Console), turn on JSON or structured output, and run all 5 inputs.

You have a product (or an MVP). Now you can make it genuinely smarter. The *Applied AI
engineering* pillar taught the building blocks; this lesson is about choosing the right
feature and shipping it like a product, not a demo.

## Start from the job, not the model

Write down the one job users come to your product for. Then ask where in that job they spend
effort an AI could remove. That's your feature. Common, proven shapes:

- **Smart search**: find things by meaning over the user's own content (retrieval, or RAG).
- **Summarize**: long threads, documents or meetings into something short and actionable.
- **Auto-tag or categorize**: sort incoming items into fixed buckets.
- **Draft**: a first version the user edits, such as a reply or a description.
- **An in-product assistant** that can use your data and actions. The most powerful shape and
  the hardest to make reliable, so rarely the right first feature.

## The anatomy of a production AI feature

A demo is a prompt and an API call. A feature that survives real users has more parts:

1. **Trigger**: when the model runs (a button, a new item arriving).
2. **Input**: exactly what context it gets, and nothing private it doesn't need.
3. **Structured output**: a fixed schema so the result plugs into your UI (→ structured-outputs-tools).
4. **Guardrail**: a check your code runs on the output (length bounds, required fields, facts
   that must match the input).
5. **Fallback**: what the user sees when the model fails, refuses or times out.
6. **Cost controls**: caching, a cheaper model where quality allows, a per-user cap.
7. **Eval**: a handful of saved test cases you re-run whenever anything changes.

If the feature reads text users supply (emails, documents, web pages), treat that text as
untrusted: it can contain instructions aimed at your model (→ llm-security-prompt-injection).

## Worked example: action items from a note

A notes app adds "turn this note into action items".

1. **Job:** people write meeting notes but forget the follow-ups.
2. **Schema:** a list of items, each with a task, an optional owner, and a short quote from
   the note that supports it.

```json
{ "items": [ { "task": "Send revised quote", "owner": "Sam", "quote": "Sam to resend the quote" } ] }
```

3. **Guardrail:** reject any item whose quote doesn't appear in the note. That one rule
   catches most invented tasks.
4. **Skip the model** when the note is under about 30 words; show "Nothing to extract".
5. **Cache** the result against a hash of the note's text, so reopening an unchanged note
   costs nothing.
6. **Cap** calls per user per day at a number your pricing can carry.
7. **Eval:** five saved notes (clear, messy, no actions, a long one, one in another language)
   with the output you expect. Run them before shipping and after every prompt or model change.

## If you don't code

The design above is the same without code; only the wiring changes. Many app builders now
offer a built-in AI action or an API connector you can point at a model provider. Automation
tools (Zapier, Make, n8n) have AI steps that can run on a new record and write structured
fields back (→ ai-in-automations). Prototype the prompt and schema in a free playground first,
then hand the one-page spec to the builder or a developer.

> 💡 **Try it:** in any chat assistant, paste a real meeting note and ask for action items as
> JSON with a `quote` field for each. Then check every quote against the note. Any that
> don't match are exactly what your guardrail would catch.

## Common failure modes

- **The UI breaks on odd outputs** → free-text responses → enforce a schema and add a
  fallback state.
- **Confident, invented results** → nothing checks output against input → require quotes or
  IDs from the source and validate them in code.
- **A surprise bill** → no cache, no cap, an expensive model on every call → cache, cap per
  user, and test whether a smaller model passes your eval.
- **Quality quietly drops after an update** → no eval to re-run → keep the cases as files and
  re-run on every change (→ evals-and-testing).
- **Nobody uses it** → it doesn't serve the core job → measure usage for a few weeks and be
  willing to remove it.

## Avoid the gimmick trap

An AI feature that doesn't help the core job just adds cost, latency and a new way to be
wrong. Ask: *does this make the main thing users came for noticeably better?* If not, don't
ship it. Done well, one sharp feature can be the reason people choose your product. Next: how
the build route itself is a choice, with no-code AI builders.
