Obsidian is great out of the box, and **plugins** make it yours. The trap is installing fifty
and breaking everything. So start with the **core plugins** (already built in) and add a
small, deliberate set of community plugins. The single most useful "plugin" in this lesson is
now one you don't install.

## Turn on the core plugins first

You've met most of them: **Daily notes**, **Backlinks**, **Graph view**, **Templates**,
**Quick switcher**, **Outline** — and **Bases**, Obsidian's built-in database views, which
shipped to core in **Obsidian 1.9 (2025)**. Enable them in settings before reaching for
anything external.

## Bases — the one that changed the answer

A **base** turns your notes into a table. Rows are files, columns are their **properties**
(lesson 6 is where you started writing those). It stores nothing new: the data stays in the
YAML front matter of your markdown, and the `.base` file just describes filters, columns and
views. Delete the base and you lose a view, never a note.

- **You build it by clicking.** Pick a property to add a column, pick a condition to filter. A
  base with no filters shows your whole vault; you narrow from there.
- **Views are cheap.** One base can hold several views — a "reading list" and a "recently
  finished" over the same notes — and a filter can apply to one view or all of them.
- **It embeds.** Drop `![[Books.base]]` into any note, or write a `base` code block inline. The
  embedded table updates itself as your notes change.

Here's a whole base as a code block — paste it into a note inside a fenced block tagged
`base`:

```
filters:
  and:
    - 'type == "concept"'
views:
  - type: table
    name: Concepts
    order:
      - file.name
      - topic
      - source
```

That's the syntax the buttons write for you. You'll rarely type it by hand.

> 💡 **Try it:** turn on Bases, run *Bases: Create new base* from the command palette, and
> add one property as a column. With no filter it lists every note in your vault, which is
> usually the moment you see how few of your notes have properties yet.

## Templater — still worth installing

**Templater** is supercharged templates. A hotkey inserts a note that's pre-filled and
dynamic: today's date, prompts, inserted values, light logic. Put this at the top of a template
note and every note created from it stamps itself:

```markdown
# Decision — <% tp.date.now("YYYY-MM-DD") %>
```

The real move is having your template write **properties**, not just headings. A template
that stamps `type: decision` on every entry is what makes a base over your decision log
possible three weeks later. Templates feed views.

## Dataview — the second tool now, and why

**Dataview** queries your vault with a real query language: four query types (`LIST`,
`TABLE`, `TASK`, `CALENDAR`) and components you compose — `FROM`, `WHERE`, `GROUP BY`,
`FLATTEN`, `SORT`, `LIMIT`. Paste this into a ` ```dataview ` fenced block:

```
TASK
FROM #side-project
WHERE !completed
GROUP BY file.link
```

That is more expressive than a base, but two things have changed. **Bases covers the common
case natively**, with no syntax to guess and no plugin to keep alive. And **Dataview's own risk
has materialised**: its last release was **0.5.70 in April 2025**, and its declared successor,
**Datacore**, is still a self-described work-in-progress on **0.1.x**, with different syntax.

So: **Bases first. Dataview when Bases can't express it** — task rollups from inside note
bodies, `FLATTEN` over nested lists, anything that wants JavaScript. Learning some Dataview is
worth an evening. Building your system on it is not.

## What Bases can't do at all — and what an AI does instead

A base is a **live filter over structure**. It is superb at questions whose answer is a
*subset of your notes*, expressible as a condition on a property:

- *"Every note where `type` is decision and `area` is billing, newest first."*
- *"Concept pages with no `source`."*

It is powerless at questions whose answer is a *new sentence*:

- *"Which of my side project's architecture decisions do my later meeting notes now
  contradict?"*
- *"Summarise everything in `wiki/` that touches offline-first sync, and tell me what I never
  resolved."*

The answer doesn't exist in the vault yet; it has to be *made* by reading prose across many
notes. That's an AI: a coding agent with the vault as its working folder, a chat assistant
with the notes uploaded, or an AI plugin inside Obsidian (next lesson).

The cheapest test: **could you express it as a filter?** If yes, build the view; it's live
and free forever. If no, ask an AI. The base is the dashboard you glance at daily; the AI is
the colleague you ask a hard question once.

## Errata — this video was recorded in the 1.9 beta

It's from 2025-06-06, when Bases was in early access. Three things have moved:

- **[00:00–03:49] "early access", Catalyst, how to enable it** — obsolete. Bases is a public

- **[23:28] "right now bases are table, that's it"** — no longer true, and it's his main

  install from the directory, so don't hunt Settings for it.
- **[10:49] the filter that won't apply to all views** — a beta bug. The Filter menu now has
  explicit "all views" and "this view" sections, and they work. Treat **[25:22] the roadmap
  chapter** as history: most of it has shipped.

Everything else holds, including the build-by-clicking contrast at [07:39].

## The rule that keeps your vault healthy

**One at a time.** Install a plugin, live with it for a week, then consider the next. Worth
trying when you feel the need: **Calendar** (jump between daily notes), **QuickAdd** (fast
capture + macros), **Excalidraw** (sketches), **Style Settings** (theme tweaks). Plugin sprawl
is how vaults break and how people quit Obsidian — and tonight's most useful addition required
installing nothing at all.

With Bases reading your properties and Templater writing them, the mechanical layer is done.
Next: the layer that reads what your properties can't capture — **AI inside Obsidian.**
