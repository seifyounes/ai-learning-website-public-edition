Setup takes ten minutes. The **layout** you pick in those ten minutes is the lesson —
because this vault has two readers.

You read it in Obsidian: that's where you browse, link, and notice what's wrong. **An AI
reads it too**: a coding agent (Codex, Claude Code, Gemini CLI and the like) straight from
the folder, or a chat assistant from the notes you upload to it. From lesson 4 onward that AI drafts the filing,
the summarising and the cross-referencing. A vault is a folder of markdown files on your
disk, and that's exactly what makes the second reader possible — an agent can open a
folder and any chat app can take a `.md` upload; neither can open a proprietary notes API.

So we don't "let structure emerge" at the top level. We decide it now, once, and write the
decision down where the agent will read it.

## Get it running

1. Download Obsidian from `obsidian.md` — free on desktop and mobile, and free for work
   too: the commercial licence became **optional in February 2025**.
2. **Create one vault**, not one per project. A second brain only works when ideas can
   connect, and a vault per project severs them.
3. Skip the settings tour. Themes and hotkeys are procrastination dressed as setup.

## Three layers — the reason the folders look like this

The layout below isn't taste. It comes from Karpathy's *LLM wiki* — an idea file published
in April 2026 describing a knowledge base built for a human and an agent to share. It's
agent-agnostic (its example schema files are `AGENTS.md` for Codex or CLAUDE.md for Claude
Code, and he reviews the results in Obsidian), and it splits the vault into three layers:

- **Raw sources — you curate, the agent never edits.** Articles, papers, docs pages,
  transcripts, exports. This is the source of truth. It stays immutable so that every claim
  in the layer above it can be re-checked against something that didn't change.
- **The wiki — the agent owns it entirely.** Summaries, concept pages, entity pages, and
  the cross-references between them. This is generated *from* sources and maintained by the
  agent. You read it and correct it; you rarely author it.
- **The schema — a config document that tells the agent the conventions.** Naming, note
  shape, which folders are writable, what a good page looks like. In this vault it's
  `vault-rules.md` at the root, and it co-evolves: every time you correct the AI twice, the
  fix belongs in there.

Two spine files hold it together. **`index.md`** is the catalog of what the vault contains,
updated on every ingest. **`log.md`** is append-only — a dated line for every ingest, query
and clean-up pass, so you can always answer "when did this get in here, and from what?"

Say the division plainly to yourself, because the rest of the pillar depends on it:
**Obsidian is the human interface. An AI is what drafts and maintains `wiki/`, `index.md` and
`log.md`.** Obsidian itself is doing no AI work at any point.

**Don't code?** That's the default route in this pillar. Paste `vault-rules.md` into a ChatGPT
or Claude Project's instructions (or a Gemini Gem), upload the notes a question needs, and save
what it drafts into `wiki/` yourself. You do the file moves; it does the reading and writing.

**Use a coding agent?** It writes the files itself. Each agent looks for its own rules file at
the folder root: `AGENTS.md` (Codex, OpenCode, Cursor, Copilot), or CLAUDE.md / GEMINI.md for
Claude Code and Gemini CLI. Keep that file to one line, "Read vault-rules.md first", so the
rules live in one note whichever agent you run.

## The layout

```diagram
vault/
├── vault-rules.md
├── index.md
├── log.md
├── inbox/
├── sources/
├── wiki/
└── daily/
```

- **`vault-rules.md`**: the schema, meaning the conventions, structure and workflows.
- **`index.md`**: the content catalog, maintained by the AI.
- **`log.md`**: append-only, one line per ingest, query and lint pass.
- **`inbox/`**: raw, unprocessed capture. This is where *you* dump things fast, in whatever
  shape; lesson 4 teaches an AI to drain it.
- **`sources/`**: immutable raw material; the agent reads it and never edits it.
- **`wiki/`**: concept and entity pages, owned by the agent. `sources/` and `wiki/` are the
  two layers above, made physical.
- **`daily/`**: daily notes, one per day, named `YYYY-MM-DD.md` (also lesson 4).

Seven entries — the spine every later lesson refers back to. (With a coding agent, add its
one-line pointer file beside them.) It grows once: lesson 5 adds four PARA folders that are
unambiguously yours. What never changes is who owns what.

The folder a file sits in is how the agent knows what it may do with it. That is the entire
job of this tree, and it's why "start flat and see what happens" is the wrong advice here:
a flat vault gives an agent no way to tell your raw material from its own output.

> 💡 **Try it:** before you create anything, list three things you already own (a lecture
> PDF, a page of your own notes, a policy doc, a bug write-up) and write next to each which
> folder it belongs in: `sources/`, `inbox/` or `wiki/`. If one is hard to place, ask
> yourself: did *I* write this, and may an agent ever edit it?

## Where "don't build a folder tree" still applies

The instinct is still right — just aimed one level down. **Inside `wiki/`, do not build
subfolders.** No `wiki/tools/`, no `wiki/projects/flutter/`. A concept page belongs to many
contexts at once, and the moment you file it under one you've thrown the others away.
Structure in there comes from links (next lesson), not from hierarchy.

The rule to hold: **folders declare ownership; links carry meaning.** The top level is fixed
because ownership must be unambiguous. Everything below it stays flat because meaning isn't.

## Decide sync now (capture depends on it)

Two lessons from here you'll want to capture ideas from your **phone**, and that only works
if the vault syncs. The video doesn't help you here — Sync appears once, at [01:55], purely
as a way to open an existing vault, and is never compared to anything. So decide it from
this list:

- **Obsidian Sync** (paid) — official, end-to-end encrypted, no fiddling, works on mobile
  out of the box. The buy-your-time option.
- **A synced folder** (free) — put the vault in OneDrive, Google Drive or Dropbox and point
  the mobile app at it. Fine for one person; occasional sync conflicts are the tax. On
  Windows, right-click the vault folder and choose **Always keep on this device** —
  on-demand placeholder files and an app that indexes every note are a bad pairing, and the
  agent needs the real bytes on disk too.
- **Git** works and versions everything, but it isn't phone-friendly. Use it *alongside* one
  of the above, not instead.

Either of the first two is fine. Having no answer is what kills the capture habit later.

## You own your data

Open the vault in File Explorer and you'll see seven plain entries — no database, no
account, no export step. That's what lets you point a coding agent at it, or drag any note
into a chat, from the very next lesson, and it's why this whole pillar is possible at all.
