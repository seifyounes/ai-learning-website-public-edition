This is the capstone of the pillar: the architecture behind nearly every current language
model. The earlier lessons
gave you the parts: vectors, softmax, gradients, layers. The transformer is those parts
arranged so that **every design choice you face as an engineer (latency, caching, context,
cost) falls out of the architecture**.

## The pipeline in one paragraph

Your prompt becomes **tokens**, and each token becomes an **embedding vector**. The vectors
flow through N identical **blocks**. Each block has an **attention** step where tokens exchange
information, then an **MLP** where each token is transformed independently (the matmul +
nonlinearity from the neural networks lesson). The final vector is unembedded into **logits**
over the vocabulary, softmaxed into a distribution, and a token is sampled. Append, repeat.

## Attention: a soft, learned lookup

Every token emits a **Query** ("what am I looking for?"), a **Key** ("what do I contain?"),
and a **Value** ("here's my content"). Scores = Q·K matches for all pairs (the n×n matrix and
its quadratic cost); softmax the scores; blend the Values. The **causal mask** hides the future
so training ("predict the next token") matches generation, where the future doesn't exist yet.
Many heads per layer run this lookup for different relationships at once.

```diagram
token vectors x1 … xn
   │
   │  × W_Q → Queries Q
   │  × W_K → Keys K
   │  × W_V → Values V
   ▼
scores = Q·Kᵀ / √d
   n × n: every token
   against every token
   │
   ▼
causal mask
   hides later tokens
   │
   ▼
softmax → weights
   each row sums to 1
   │
   ▼
weights × V
   each token gets a blend
   of the Values it matched
```

## Prefill vs decode — where your latency lives

- **Prefill:** the whole prompt is processed in parallel. Fast; it sets *time to first token*.
- **Decode:** each output token requires a full sequential forward pass. This is the slow,
  per-token crawl your users feel. Streaming hides it; shorter outputs genuinely fix it.

```diagram
PREFILL: one parallel pass
prompt t1 t2 t3 … t4000
   │ all positions at once
   ▼
KV cache filled, t1 … t4000
   │
   ▼
sets time to first token

DECODE: one pass per token
step 1: new token → Q, K, V
        → attend to cache
        → t4001
step 2: t4001 → … → t4002
…
step 300: … → last token
   each step appends its own
   K, V to the cache
   │
   ▼
total wait ≈ output tokens
             × time per step
```

## The KV cache — and why cached input is cheaper

Generated tokens don't recompute the past: the per-layer Key/Value states of all previous
tokens are **cached**. Two consequences you'll pay for:

- Long chats grow the KV cache, which is the memory pressure behind long-context pricing.
- An **identical prompt prefix has identical KV states**, so providers can reuse them across
  calls. That's prompt caching. Design rule: stable text (system prompt, examples) at the top,
  variable text at the bottom.

## Worked example: follow one request through the model

A support assistant sends a 3,000-token system prompt, a 1,000-token customer email, and gets
a 300-token reply.

1. **Tokens to vectors.** 4,000 tokens become 4,000 embedding vectors.
2. **Prefill.** All 4,000 positions go through every block at once. Each attention head in each
   layer builds a 4,000 × 4,000 score matrix: 16 million scores, computed in parallel. The time
   this takes is your *time to first token*.
3. **Decode.** The 300 reply tokens come out one at a time. Each step computes Q, K and V for
   just the newest token and attends over the cached keys and values of everything before it.
   300 sequential steps usually dominate the total time.
4. **The next call.** The same 3,000-token system prompt arrives with a new email. Its KV states
   match the cache, so prefill can start at token 3,001, and those 3,000 tokens are billed at
   the cached rate. If someone had put a timestamp on line one, none of it would match.
5. **Predict the cuts.** Halving the email saves a little prefill time and some money. Halving
   the reply roughly halves decode, which is most of the wait.

## Common failure modes

- **Cache hits near zero** → something volatile (a timestamp, user name or retrieved document)
  sits above the stable prefix → move it to the end, and check your provider's minimum
  cacheable length.
- **A "slow" feature with short prompts** → long outputs, so decode dominates → cap the output
  length, ask for a tighter format, and stream.
- **The model ignores a fact you definitely pasted in** → it was buried mid-way through a huge
  context → retrieve only the relevant chunks, and put key facts near the start or end.
- **Costs climb with every turn of a long chat** → the full history is re-sent and the KV cache
  keeps growing → summarize or trim history, or start a fresh session with a short brief.

"Why is generation slow?", "why does caching need a stable prefix?", "why not stuff the whole
