task: |
  Write one real spec whose every criterion can fail (about 35 minutes). Warm up by making one
  vague acceptance criterion fail-able, in any chat assistant or Claude Code:

  ```prompt
  Rewrite this acceptance criterion in EARS form — a named trigger (WHEN / IF / WHILE) plus a
  single testable response a verifier can pass or fail. Kill any word that can't fail
  ("gracefully", "feels fast", "personal"). Return the before and after.
  Criterion: "the onboarding flow should feel welcoming."
  ```

  Check the result: does it name a trigger and a response something could actually test? If
  not, tighten it again. Then take the **next non-trivial feature** on your own project
  (something that will take more than one session) and have plan mode draft its spec:

  ```prompt
  Plan mode only — write no code. Explore the code this feature touches ([the feature, e.g.
  "recurring tasks in a to-do app: the task model, the scheduler, the list screen"]) and write
  a spec to docs/specs/[feature-name].md with three sections: Goal (what + why), Acceptance
  criteria (EARS-style, each testable), Plan (files + steps in order). Wait for my approval.
  ```

  Critique every criterion the way you did in the warm-up, then commit the spec next to the
  code. **If you don't code yet:** write the three-part spec for a small tool you wish existed,
  and ask a chat assistant to find the criteria that can't fail.

You already drive the loop and know plan mode as a read-only gear you approve before any
edit (→ core-loop). This lesson is about what you *do* with that plan: promote it into a
**spec** — the durable statement of intent your whole stack builds against. Everything else
in the course is a nested stack — prompt ⊂ context ⊂ harness ⊂ loop engineering (the AI
mental models pillar) — that decides *how well* the agent executes. Spec-driven development
runs alongside it as the orthogonal track that decides *what* gets executed at all. Get the
spec right and the stack has a fixed target; skip it and even a flawless harness optimizes
toward a moving guess.

## The spec is the source of truth, not the chat

"Vibe coding" — prompt, hope, repeat — survives toy problems and collapses on anything real:
the agent drifts, intent evaporates, and three sessions later nobody can say what "done"
was. A spec fixes that at the root by writing intent down *before* code and making that
file — not the chat, not your memory — the thing everyone builds to. The payoff is plain:
rework collapses once the target stops moving. In Spec Kit's own framing, the spec stops being
scaffolding you throw away and becomes *executable* — the source that generates the
implementation.

Three parts, always:

- **Goal** — what you're building and why, in a sentence or two. The *why* is load-bearing:
  it's what the agent falls back on when the spec goes silent on an edge case.
- **Acceptance criteria** — the checklist that *proves* it works. Every line must be able to
  fail (more below).
- **Plan** — the files and steps, in order — the same plan-mode output, now written to last.

## From plan mode to a durable spec

Plan mode hands you an *ephemeral* plan; SDD's whole move is to make it *durable*. The
workflow:

1. **Explore in plan mode** so the spec is grounded in the real code, not a guess about it.
2. **Write the spec to a file** — `docs/specs/<feature>.md` (a placeholder path: use whatever
   your repo already uses — some teams keep theirs in `docs/plans/<feature>/`), committed. This
   is the trick. A chat window compacts and resets; a file persists. When context is wiped or
   you open a fresh session tomorrow, you re-feed the spec and the agent is back on contract in
   one step — no re-explaining, no drift into a half-remembered version of the plan.
3. **Implement against it**, ticking acceptance criteria as you go.
4. **Point every subagent and reviewer at the same file** so parallel work shares one truth.

The plan-mode plan is disposable; the spec file is the artifact. That gap — between someone
who *uses* plan mode and someone who does spec-driven development — is the whole lesson.

> 💡 **Try it:** In plan mode, end your exploration prompt with the spec baked in:

```prompt
Don't edit anything. Explore the files this touches, then write a spec to
docs/specs/<feature>.md with three sections: Goal (what + why), Acceptance
criteria (EARS-style, each one testable), Plan (files + steps, in order).
Wait for my approval before writing any code.
```

## Write acceptance criteria that can fail (EARS)

An acceptance criterion that can't fail is decoration. "Handles errors gracefully" proves
nothing; `IF the AI API call times out, the system SHALL serve the last cached answer` either
happens or it doesn't. **EARS** — Easy Approach to Requirements Syntax, built at Rolls-Royce,
now used by NASA and Airbus — is a five-template discipline for writing exactly that kind of
line: ubiquitous (`the system SHALL …`), event-driven (`WHEN <trigger>, the system SHALL …`),
state-driven (`WHILE <state> …`), unwanted (`IF <condition>, THEN …`), and optional
(`WHERE <feature> …`). You don't need the taxonomy memorized; you need the habit it forces —
every requirement names a **trigger** and a **testable response**, so "done" becomes a set of
checks a verifier can run instead of a vibe you eyeball. That's the seam where SDD hands off
to the runnable-check habit from the core loop.

## Keep the spec and the code in sync

A spec is a contract, and contracts go stale. When the build reveals the spec was wrong — and
it will; that's information, not failure — **update the spec on purpose** rather than letting
code and intent silently diverge. A spec the code has quietly outgrown is worse than no spec:
it lies to the next session and to every subagent you point at it. The rule is one line — the
spec and the code are never allowed to disagree; whichever is right, you fix the other
deliberately, in the same commit.

## Tooling: by hand, or a framework

You can run SDD with nothing but a markdown file and a `/spec` skill that drafts one from
plan-mode exploration. Or formalize it: **GitHub Spec Kit** turns it into slash commands
(`/specify → /plan → /tasks → /implement`) that Claude Code drives directly, and IDEs like
**Kiro** bake a three-file structure — `requirements.md`, `design.md`, `tasks.md` — in from
the ground up. Same idea elsewhere: Cursor has its own plan mode, and Spec Kit also runs with
GitHub Copilot, Cursor and Gemini CLI. The tool is interchangeable; the discipline isn't. Actually building a feature
end-to-end from a spec is the capstone's job (→ capstone-build-feature) — here the deliverable is the spec
itself, critiqued until every criterion can fail.
