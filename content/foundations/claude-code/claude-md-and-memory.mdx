You've taught Claude how to *work* (the loop) and how to *talk to it* (prompting).
`CLAUDE.md` is how it **remembers** — the file that turns Claude Code from a sharp
stranger into a teammate who already knows your project, because it's read
**automatically at the start of every session.** Nothing else in the tool pays off as
reliably for so little effort.

## What belongs in it

Think of the brief you'd hand a senior dev on day one. (Same idea elsewhere: Codex, Cursor,
GitHub Copilot and many other agents read an `AGENTS.md`; Copilot also reads
`.github/copilot-instructions.md`, Cursor its `.cursor/rules`. What belongs in them is the same.)

- **Stack & commands** — how to run, build, test, and lint (the exact commands).
- **Architecture** — the folders that matter and where things live.
- **Conventions** — naming, formatting, the patterns you always follow.
- **Gotchas & don'ts** — the traps you keep re-explaining.

Anthropic's own trigger for *when* to add a line is sharp: Claude makes the same mistake
twice, a review catches something it should have known, or you retype a correction you
already gave last session. What does *not* belong: secrets (never), your whole README, or
transient history ("fixed the login bug Tuesday"). And two things that feel like they
belong but don't — a multi-step *procedure* is a skill (→ **skills-and-plugins**), and a
rule that only matters in one corner of the codebase is a **path-scoped rule** (below),
not a line every session pays for.

## Bootstrap with /init, then tune

Don't write the first draft by hand. Run **`/init`** in the repo: Claude scans the
codebase and generates a starter `CLAUDE.md` — detected stack, common commands, a folder
map — in one pass. It's non-destructive: if a `CLAUDE.md` already exists, `/init`
*suggests improvements* instead of overwriting, and it folds in an existing `AGENTS.md` or
`.cursorrules` if you have one. (Set `CLAUDE_CODE_NEW_INIT=1` for the newer interactive
flow — it explores with a subagent, asks follow-up questions, and shows you a reviewable
proposal before writing anything.)

Treat that draft as raw material, not the finished file. `/init` can only encode what it
can *see*, and the highest-value lines are the ones it can't infer: the gotcha that cost
you an afternoon, the convention that isn't in the code yet, the "always do X before Y."
Cut the obvious, add the hard-won, move on. This is the one place the course teaches
`/init`; later lessons assume it's already run.

## The hierarchy: broad to specific

Memory isn't one file; it's a stack, loaded broadest scope first:

- **Managed policy** — an org-wide file IT deploys; it loads first and you can't exclude
  it. Most solo work never touches this layer.
- **User** — `~/.claude/CLAUDE.md`, your personal standards across *every* project.
- **Project** — `./CLAUDE.md` (or `./.claude/CLAUDE.md`), checked into the repo, shared
  with the team.
- **Nested** — a `CLAUDE.md` in a subfolder, loaded *on demand* only when Claude reads
  files in there.
- **Imports** — pull other docs into any of these with `@path/to/file` (relative to the
  file, `@~/…` for home, up to four hops deep; the first external import asks once for
  approval).

Here's the part most guides get wrong: these files are **concatenated, not overriding.**
Claude reads them in order from the filesystem root down to your working directory, so the
most specific file is read *last* — closest to the conversation, which gives it the most
pull. But memory is **context, not enforced config**: if two layers flatly contradict,
Claude may pick either one. So don't rely on a silent override to win — keep the layers
consistent, and when a rule truly is local, *scope* it instead of duplicating it. (Only
managed policy is a hard, non-overridable layer; for guaranteed enforcement you use a
hook, not memory — → **hooks-automation**.)

Two ways to write without opening a file: tell Claude *"remember X"* and it saves to auto
memory, or *"add X to CLAUDE.md"* to put it in your file. **`/memory`** lists every loaded
file — CLAUDE.md, local, rules, auto memory — and opens any of them to edit.

## Keep it lean — under 200 lines

Because it's read on every session, `CLAUDE.md` is *spent* on every session — and loaded
in **full**, however long it is. Anthropic's guidance is now a number: **target under 200
lines** per file; longer files consume more context *and* measurably reduce how reliably
Claude follows them. A tight page beats a sprawl.

When the root starts to bloat, don't just delete — **scope**. A `.claude/rules/` folder
holds topic files, and any rule with `paths:` frontmatter loads *only* when Claude touches
matching files:

```markdown
---
paths:
  - "src/api/**/*.ts"
---
# API route rules
- Every handler validates its input before touching the database.
- Errors return { error: { code, message } }, never a raw stack trace.
```

That keeps API-only rules out of context while you edit the app's UI code. (Same idea
elsewhere: Cursor rules take `globs`, and GitHub Copilot's `.instructions.md` files take an
`applyTo` pattern.) (*Why* a loaded line is a
real cost — token economics, compaction, what to keep hot versus fetch on demand — is
context engineering, and that theory lives in its own lesson (→ context-engineering). Here you just
apply its one rule: every line earns its slot, and you prune the moment one goes stale.)
Bonus: block-level HTML comments in `CLAUDE.md` are stripped before Claude sees them, so a
`<!-- maintainer note -->` costs zero tokens.

## Two kinds of memory: what you write vs. what Claude writes

`CLAUDE.md` is memory *you* author — durable **rules** Claude should always follow. Modern
Claude Code adds a second system: **auto memory**, notes *Claude* writes for itself. As
you correct it and it debugs your project, it saves learnings to
`~/.claude/projects/<project>/memory/MEMORY.md` — an index whose first 200 lines (or 25 KB)
load every session, with deeper topic files it reads on demand. You didn't write a line;
audit or prune it any time with **`/memory`**.

Two things to hold straight. First, auto memory is **machine-local** and Claude-owned —
not the same as a hand-written history doc you commit to the repo (many teams keep a
`MEMORY.md` or `DECISIONS.md` of decisions and gotchas and `@`-import it). Rules shape
every session; history is what you look back on — keep them in different files so neither
bloats. Second, the habit that keeps *your* file alive is unchanged: **catch yourself
correcting Claude on the same thing twice, and encode the rule once.** Auto memory now
catches some of that for you, but the load-bearing contract — the one a fresh session must
never improvise away — you still write into `CLAUDE.md` by hand.

Get these files right and everything downstream — custom commands, subagents, hooks — runs
*your* way. (Turning a prompt you retype into a reusable tool is a → **skills-and-plugins**
topic, not a memory-file one.)
