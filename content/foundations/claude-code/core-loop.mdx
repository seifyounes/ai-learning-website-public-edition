The biggest mistake new users make is treating Claude Code like a vending machine:
type a request, hope for code. The operators who get great results hand it a **loop**
instead. Anthropic's canonical version is **Explore → Plan → Code → Commit**, and it
maps onto the agent loop under every session — *gather context → take action → verify
results*. Learn the loop and you stop guessing and start shipping output you trust.

## 1. Explore (read-only)

Before a single edit, let the agent *understand*. Point it at the relevant files, the
code around them, the tests, and any spec — and tell it not to touch anything yet. You
want it loaded with real context before it forms an opinion, because a plan written from
a half-read codebase solves the wrong problem. **Scope** the exploration
("read `/src/auth` and how sessions work") rather than saying "investigate" — an
unscoped read burns context on hundreds of files. For big reads, hand it to a subagent
so findings come back as a summary instead of flooding your window
(→ `subagents-and-agent-teams`).

## 2. Plan mode (design before doing)

This is the gear that makes the loop work, so learn it properly — later lessons point
back here for it.

**Plan mode is a read-only permission mode.** Press `Shift+Tab` to cycle Claude Code's
permission modes — Manual → Accept edits → **Plan** (from a fresh session, that's
`Shift+Tab` twice) — or launch straight in with
`claude --permission-mode plan`. In plan mode Claude *researches* — reads files,
searches, runs commands to explore — then writes you a plan: the files it will change,
in what order, and how. What it **won't** do is edit your source; anything past
a read still stops for approval, exactly as in Manual mode. It designs; it doesn't build.

Read that plan critically. This is the cheapest place in the loop to catch a wrong
approach: rejecting a paragraph costs nothing; unwinding a bad twelve-file diff costs
your evening.
Approve, and pick *how* it implements — review each edit, accept edits, or hand it to
auto mode; keep planning or reject to send it back with your correction.

> 💡 **Try it:** before your next feature, enter plan mode and paste a prompt like this:

```prompt
Read the files this touches and the tests around them. Don't edit anything.
Then write a plan: exact files, the order you'll change them, and how I'll
verify it. Wait for my approval.
```

**When to skip it:** only when you could describe the entire diff in one sentence — a
typo, a log line, a rename. Plan when you're unsure of the approach, when the change
spans multiple files, or when you don't know the code. Turning a good plan into a
durable, reusable **spec** — the formats, the `SPEC.md`, grading it — is its own skill
(→ `plan-mode-spec-driven`).

## 3. Code (implement against the plan)

Now let it build — running tests and lint **as it goes**, not at the end. The rule:
don't deviate from the plan without an explicit decision. If reality contradicts the
plan, **stop and re-plan** rather than letting it improvise a drift.

## 4. Commit (the handoff)

Finish with a clean commit — a real `type: description` message and, on a shared repo, a
PR. The git history becomes context for the next session, for you *and* the agent, and
on a live product it's your rollback point. A loop that doesn't end in a commit didn't
really close.

## The habit that outranks everything: give it a check it can run

Across every best-practices guide, one habit tops the list: **give Claude a way to
verify its own work.** The mechanism: Claude stops when the work *looks* done.
With no check it can run, "looks done" is its only signal, and *you* become the
verification loop — every mistake waits for you to notice it. Hand it something that
returns a hard pass/fail — a test suite, a build exit code, a linter, a fixture diff, a
screenshot compared to the design — and the loop closes itself. Claude does the work,
runs the check, reads the result, and iterates until it's green.

Don't accept prose ("this should work now") — accept evidence: the command it ran and
what it returned. If you can't verify it, don't ship it. An agent that can check itself
corrects itself; TDD is the strongest version, because the check exists *before* the code.

> 💡 **Try it:** End your implementation prompt with the verifier baked in: "run the
> test suite and fix failures until it passes, then show me the output." Make *green*
> the stop condition, not your eyeballs.

Engineering the loop *around* that verifier and a stop-rule — `/goal`, Stop hooks,
evaluators — is its own lesson (→ `loop-engineering`).

And mind your **context**: it fills fast and quality sags as it does. The next lessons —
CLAUDE.md, skills, MCP — are about feeding the agent the *right* context cheaply,
which is what makes this loop sing.
