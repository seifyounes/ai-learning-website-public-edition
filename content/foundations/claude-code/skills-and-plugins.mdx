  - **A procedure you run by name** → a workflow skill you call as `/name`.

`CLAUDE.md` taught Claude your project's *rules*. A **skill** goes one level up: it packages
a *capability* — a folder of instructions Claude loads itself the moment a task matches. It's
how you stop re-pasting your best prompt forever, and it's the real step from *using* Claude
Code to *engineering* it. One 2026 change reframes the whole lesson: the custom slash command
didn't get a sibling — it got absorbed. **The primitive is now the Skill.**

## The primitive is the skill (commands are legacy)

A skill is a folder with a **`SKILL.md`** — YAML frontmatter (`name`, `description`) plus the
instructions, optionally alongside scripts and reference files. Claude discovers it and loads
it **when the task matches**. That last part is the leap: skills are **model-invoked**. You
describe the capability once and Claude reaches for it — you don't have to remember it exists,
the way you had to remember which slash command to type.

Every skill is *also* invocable by name — `/name` for a personal skill, `/plugin-name:skill`
for one shipped in a plugin. So the thing you used to call a "custom slash command" is just a
skill you happen to invoke by hand.

That's why commands are legacy, not gone. Your old `.claude/commands/review.md` still runs, but
the official docs now treat the `commands/` folder as the flat-file legacy form of skills and
point all new work at `skills/`. The modern home is `.claude/skills/review/SKILL.md`
with a real `description`. If you want a skill to **only** fire when you type it and never
auto-trigger, add `disable-model-invocation: true`; otherwise give it a sharp description and
get both behaviours for free. That's the whole migration.

Same idea elsewhere: Anthropic has published the `SKILL.md` format as an open standard, and
OpenAI's Codex and GitHub Copilot can load skills in the same folder shape, so a skill you
write here usually travels.

## Write the description like it's the trigger — because it is

The **`description`** is the single most important line in the file. Only the frontmatter loads
into the system prompt at startup — that thin slice is what Claude matches every task against to
decide whether to pull the skill in. A vague description is a skill that never fires.

So write it as **what it does + exactly when to use it**, stuffed with the situations and
phrases that should invoke it. Look at any well-authored skill and its description reads like
*"…Use when… Triggers include…"* — that density is deliberate; the description is doing
retrieval.

```md
---
name: commit
description: Write a conventional-commit message for the staged diff. Use when the
  user asks for a commit message, says "commit this", or right after staging changes.
---
Read the staged diff and write a single `type: description` message — imperative mood,
under ~70 chars, no body unless the change is non-obvious.
```

The reason a big skill stays cheap is **progressive disclosure**: metadata is always on, the
`SKILL.md` body loads only when the trigger hits, and bundled files load only when the body
reaches for them. Keep the description tiny and high-signal; push the bulk down a layer. (*Why*
a loaded token is a real cost — the economics, JIT retrieval — is → `context-engineering`; here
you just apply the rule.)

> 💡 **Try it:** open a skill you already have and rewrite its description from *what it is* to
> *when to use it* — add three concrete trigger situations. Then describe one of those
> situations without naming the skill and see if Claude now reaches for it.

## Two shapes: reference vs workflow

Skills come in two flavours, and knowing which you're writing tells you *how* to write it.

- **Reference skill** — packaged *knowledge*: a style guide, an API's quirks, a schema, your
  brand tokens. Mostly declarative content Claude pulls in as a lookup when the topic comes up.
- **Workflow skill** — packaged *procedure*: a sequence of steps Claude executes, imperative
  and often with scripts. A `/wrap-up` skill (harvest decisions → write them to files → commit
  → hand off) or a `/format-prompt` skill (rough idea → structured prompt) is a workflow skill.

Reference = content to load; workflow = steps to run. Most real skills lean one way, and the
lean decides whether the body is a document or a runbook.

## In-context, or forked to a subagent

By default a skill runs **in-context**: its instructions load into your current thread and
Claude acts inline, so everything it reads and produces lands in *your* window. That's exactly
what you want when you need the intermediate work — a formatter that returns a prompt you'll use
next, a writer whose files you want to inspect.

The alternative is a skill that **forks to a subagent**: the work runs in an isolated context
that returns only a summary. Reach for this when the value is the *result*, not the noisy
exploration behind it — a whole-repo audit, a research fan-out. The isolation *is* the point:
the subagent burns its own context and hands you back a clean answer.

The decision rule is one question — *does the caller need the work, or just the result?* Need
the work → in-context. Need only the result, or it's heavy and noisy → fork. (Defining and
configuring the subagents themselves → `subagents-and-agent-teams`.)

## Plugins & marketplaces: package it for everyone

A loose `.claude/skills/` folder is personal and per-project. A **plugin** packages skills —
plus, optionally, agents, hooks (→ `hooks-automation`), and MCP servers (→ `mcp-servers`) —
behind a `.claude-plugin/plugin.json` manifest, so the bundle is **versioned, namespaced, and
installable** across projects and teammates. Plugin skills carry a namespace (`/codex:review`)
so two plugins can't clash.

A **marketplace** is a catalog — a `marketplace.json` in a git repo — listing plugins. Users
`/plugin marketplace add <repo>` and then `/plugin install <name>`. Anthropic runs an
official curated marketplace plus a community one for public submissions.

A concrete example is the **Codex plugin** for Claude Code (→ codex-inside-claude-code): it
ships skills (`/codex:review`, `/codex:rescue`, `/codex:adversarial-review`), a review subagent,
and its own runtime as a single versioned install. That's the shape — a bundle of capability you add in one command and update by bumping
a version, instead of copying files between repos and watching them drift.

## Packaging knowledge is the whole point

Zoom out and every skill is the same move: it turns something *you* know — the prompt you
retype, the convention only you follow, the runbook in your head — into a tool your future
sessions, your subagents, and your teammates inherit. A hard-won prompt becomes a permanent
capability; a new hire installs one plugin and gets the whole playbook; a fresh session starts
already knowing your standards. That is the line between operating Claude Code and engineering
it.
