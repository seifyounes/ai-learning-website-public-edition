toolkit: |
  Place servers by scope, and know when *not* to add one:

  - **Pin project servers in a committed config with env-referenced secrets.** `.mcp.json` with
    `${TOKEN}` references means a fresh clone, a teammate or a subagent gets the same tools and
    no secret ever lands in git. The same idea lives in `.cursor/mcp.json` (Cursor),
    `.vscode/mcp.json` (Copilot in VS Code) and `~/.codex/config.toml` (Codex).
  - **Put personal servers at user scope.** Calendar, email or a notes search follow *you*, not
    a repo: add them with `-s user` so they're live everywhere and never bleed into a shared or
    client `.mcp.json`.
  - **Know where MCP does NOT belong.** A project with no external system to reach (a static
    site, a local-only app) gains nothing from an integration; its wins come from skills and
    `CLAUDE.md` (or `AGENTS.md`). Every server you add is surface area you have to trust.
  - **Write the MCP-vs-skill-vs-hook rule into your instruction file.** One line each — reach →
    MCP, procedure → skill, guarantee → hook — so new automation lands in the right layer
    instead of a reinvented fourth one.
  - **Audit what's connected once a month.** Run `/mcp`, remove servers you no longer use, and
    check each remaining one still comes from a source you trust.

By now you've taught Claude Code your project (`CLAUDE.md`), packaged your repeats
(skills), and delegated big reads (subagents) — but all of that still runs inside one
sandbox: **your files and your shell.** Real work lives outside that box — the issue
tracker, the database, the running app, your calendar. **MCP is the port out.**
Anthropic's analogy is the sharpest: MCP is a *USB-C plug for AI* — one standard socket,
and any compatible tool snaps on.

## What MCP is (the user's-eye view)

**MCP — the Model Context Protocol — is an open standard for connecting an AI to
external tools and data.** A *server* exposes some system (GitHub, Postgres, a browser,
Figma, your calendar) as a set of tools; Claude Code is the *host* that calls them.
That's all you need at this altitude: a server is a tool-pack Claude can plug into.

It's **open and vendor-neutral** — Cursor, Codex, and a growing list of other tools speak
the same protocol — so a server you wire up here is reusable across the whole ecosystem.
The wiring transfers; it's not a Claude-only trick.

Building your *own* server — protocol internals, the host/client/server wiring, transports
— is a different skill, covered in the Applied AI engineering pillar (→ mcp-deep). This
lesson is about *connecting* servers that already exist.

## Adding one

Two ways in. The fast one is the CLI:

```bash
# Remote HTTP server (most hosted services)
claude mcp add --transport http linear https://mcp.linear.app/mcp

# Local stdio server (a process on your machine); --env passes secrets
claude mcp add --env SUPABASE_ACCESS_TOKEN=… supabase -- npx -y @supabase/mcp-server-supabase@latest

# See what's connected, each server's tool count, and log into OAuth servers
/mcp
```

The other path is a **config file** — declare servers as JSON so they load every session
(and, at the right scope, so your team gets them too). Inside a session, `/mcp` lists
every server and runs the OAuth login for the ones that need it.

Once a server is on you don't call tools by name — you just ask. "Open a PR for this
branch," "query the users table," "what's on my calendar Thursday" — Claude picks the
tool. The agent stops *describing* the task and starts *doing* it end to end.

## Scopes: local, project, user

Every server is stored at one of three **scopes**. This is the part most people skip, and
it's the whole game for keeping personal and team wiring separate. It mirrors the
`CLAUDE.md` hierarchy exactly:

- **local** (default) — just you, just this project. Lives in your user config, keyed to
  the project path. Use it for experiments and anything personal to this repo.
- **project** — committed to the repo as **`.mcp.json`**, so everyone who clones gets it.
  Use it for servers the whole team needs (the project's database, its issue tracker).
- **user** — you, across *every* project on this machine. Use it for your personal
  servers — calendar, mail, a docs search you always want on hand.

When names collide the **more specific scope wins** (local > project > user) — the same
rule as memory files. Pick scope by asking two questions: *who else needs this?* and *does
it belong to this repo, or to me?*

> 💡 **Try it:** add one server at project scope, commit the `.mcp.json`, then open a
> clean clone. If a fresh session gets the same tools without re-adding anything, you
> scoped it right.

## Trust before you connect

A server runs with **real access** to whatever it touches — your database, your GitHub,
your inbox. Add one the way you'd install software from a source you vet, not the way
you'd open a link. Claude Code builds two guardrails around exactly this:

- **Project servers don't auto-run.** A `.mcp.json` you pulled from someone else's repo
  sits at **⏸ pending approval** until you explicitly review and accept it — a cloned
  repo can't approve its own servers. So opening a project never silently hands a
  stranger's server the keys.
- **Servers that fetch external content are a prompt-injection surface** — a poisoned web
  page or issue can smuggle instructions the tool relays back into your session. The deep
  threat model (tool poisoning, sanitising) → **`mcp-deep`**; the habit to build *now* is
  the one above — connect only what you trust.

## MCP vs skill vs hook — pick the right tool

Three features blur together in people's heads. The clean split:

- **MCP** adds **reach** — a *new capability* to touch a system Claude otherwise can't (a
  DB, GitHub, a browser, your calendar).
- **Skill** packages a **procedure** you can already do with existing tools — a reusable
  prompt/workflow you kept retyping (→ **`skills-and-plugins`**).
- **Hook** is a **guarantee** — a deterministic shell command the *harness* runs on an
  event (tests before every commit, say), not something the model chooses to do
  (→ **`hooks-automation`**).

Rule of thumb: **reach a new system → MCP · repeat a procedure → skill · force something
to always happen → hook.** They compose — a skill can drive an MCP tool, and a hook can
gate a loop that uses both.

That's the lesson: MCP is Claude Code's port to everything outside your files,
`claude mcp add` wires it, **scope** decides who gets it, and **trust** decides whether
you should. Get the reach right and the agent operates your whole stack — not just your
editor.
