You've learned the parts one at a time. The capstone is where they collapse into a single
**motion** — and this time the thing you build isn't a throwaway demo, it's a **real
improvement to your own system**. That's the whole design of this lesson: you'll re-walk every
stage of the pillar, but as a checklist of *pointers*, not a re-teach. If a beat needs
refreshing, the lesson that covers it is one link away.

The video models it well. Not a scripted tutorial — the person who *built* Claude Code driving
it live, next to Bun's creator. Watch for the operating rhythm: how lean he
keeps context, when he delegates, how he lets the harness verify instead of hovering. That
rhythm is everything below, in motion.

## The motion: six beats, each covered in its own lesson

Run these in order, on one real change. Each is a single beat here; the mechanics live where
they were taught.

1. **Memory** — start from a project that already knows itself. Confirm the `CLAUDE.md` is
   current so the agent begins inside your standards, not guessing them (→ `claude-md-and-memory`).
2. **Spec** — in plan mode, turn the idea into a written contract: goal, acceptance criteria, the
   files it touches. Read it critically — the cheapest place to kill a wrong approach
   (→ `plan-mode-spec-driven`).
3. **Loop** — explore → plan → code → commit, phase by phase; approve the plan before code, and
   re-plan on drift instead of letting it freelance (→ `core-loop`).
4. **Verify** — hand it a check that returns a hard pass/fail and make *green* the stop condition,
   not your eyeballs (→ the runnable-check habit in `core-loop`; the theory in
   `verification-and-grounding`).
5. **Automate** — wire the repeat into the harness so the next build starts ahead: a hook, a
   skill, or a delegated subagent (→ `hooks-automation`, `skills-and-plugins`,
   `subagents-and-agent-teams`).
6. **Ship** — clean `type: description` commit, PR, merged. A loop that doesn't end in a commit
   didn't close (→ `core-loop`).

That's the pillar in one breath. Designing *around* the verifier and the stop-rule — treating the
loop, not the prompt, as the unit of work — is the core idea of the Loop engineering lesson made
concrete (→ loop-engineering).

## Pick your build

The deliverable is a real improvement to your **AI setup** — the instruction files, skills, hooks,
and agents you operate every day — or to **a project you own**. Pick one; each exercises the full
motion.

- **A new skill.** Package a routine you keep retyping into a `/command` — the first entry in
  your own command library. Small surface, whole motion: spec the trigger and output, build, verify it
  fires, ship.
- **A hook.** Turn a rule you *hope* holds into one the harness *runs* — a PreToolUse secret-block,
  a lint-on-edit, a Stop hook that gates on your Definition of Done. Deterministic control, shipped
  in an evening.
- **A subagent.** Stand up a specialized delegate with its own context — a fresh-eyes reviewer, a
  research fan-out, a visual-QA checker — and feel real work come back as a summary instead of
  flooding your window.
- **An app feature.** The heaviest option: one genuinely useful feature for the people who use
  your app (even if that's only you), spec-first, phases verified green against your test suite
  and the design, merged. This is the 2–4 evening path.

> 💡 **Try it:** kick any of them off with the whole motion baked into the first prompt.

```prompt
We're shipping <the build>. Plan mode only first: read the files this touches
and the relevant CLAUDE.md — don't edit anything. Then write a spec — goal,
acceptance criteria, the files you'll change, and the exact command that proves
it works. Wait for my approval before any code.
```

## What "done" looks like

Done isn't "it seems to work." Done is: you can point to the **spec**, the **plan** you approved,
the **check** that went green, and the **commit** that shipped it — intent and proof at every
stage. If any of those four is missing, you vibe-coded it; you didn't engineer it.

Close the session by asking the agent to write the decision and the next step into the right
`CLAUDE.md` and a committed `MEMORY.md` or `DECISIONS.md`. The capstone should improve the system *and* leave a record that it did — otherwise
the next session relearns what this one already figured out.

## Where this goes next

Nothing here was Claude-Code-specific trivia. Context, specs, verification, automation, the loop —
they reappear in *Applied AI engineering* and *Shipping apps*, and because so much of it is open
standard, in every rival tool. You've stopped using Claude Code like an autocomplete and started
operating it like a system. That operator's reflex — feed it context, drive it through a loop,
make it prove its own work, wire the win into the harness — is the foundation the entire rest of
the course stands on. 🎈
