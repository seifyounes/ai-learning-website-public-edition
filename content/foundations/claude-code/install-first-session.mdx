You install Claude Code once and then live in it, so the install itself is the boring part.
What deserves your attention is the **safety model** underneath — the rules that decide how much
you can hand it without watching every move. Get those right on day one and every later lesson
compounds; get them wrong and you either babysit each keystroke or hand a stranger your shell.

## Two install paths

**Native installer (recommended).** One command, zero dependencies — no Node, no npm — and it
auto-updates in the background. macOS/Linux/WSL take `curl -fsSL https://claude.ai/install.sh
| bash`; Windows PowerShell takes `irm https://claude.ai/install.ps1 | iex`. This is the path
Anthropic tests first and the least to go wrong on a fresh machine or client laptop.

**npm.** `npm install -g @anthropic-ai/claude-code`. Still fully supported, but the package now
wants **Node 22+**. On older Node it doesn't fail — it prints an `EBADENGINE` warning and
installs anyway, because what npm pulls down is a native binary that never touches your Node at
runtime. The warning is cosmetic; the friction it flags is that you're a Node upgrade behind.
**Never `sudo npm install -g`** to paper over an `EACCES` error — that just relocates the
permission problem. Fix the npm prefix, use nvm, or switch to the native installer and skip Node
entirely. Homebrew, WinGet, apt/dnf/apk, and a GUI Desktop app exist too — use whatever your
machine already speaks.

## Your first session

Run `claude` *inside the project you want to work on*, never an empty home directory — an empty
folder gives it nothing to reason about. The first run opens your browser, signs you into your
Anthropic account (Pro, Max, Team, Enterprise, or Console; not the free tier), and caches a
token in `~/.claude`, so you authenticate exactly once.

Then watch two things: the **tool calls** it narrates (read this file, run that command) and
the **permission prompts** it raises before anything hits disk. What it *does* with your
goal — the explore → plan → code → commit rhythm — is the next lesson (→ core-loop); teaching
it your stack and standards is its own lesson too (→ claude-md-and-memory). Right here, the only
job is to understand the fence.

## Permissions: the three buckets

Every action lands in one of three buckets, which you pre-set in `settings.json`:

- **allow** — read/verify work that's safe unattended: `Read`, `Grep`, `git status`,
  `git diff`, `npm run test`.
- **ask** — intent-changing work you approve each time: `Edit`, `Write`, `git commit`,
  `npm install`.
- **deny** — dangerous or sensitive, never run: `.env` and `secrets/**`, `rm -rf`,
  `git reset --hard`, `git push --force`, `curl | bash`.

You don't hand-edit JSON for these — run **`/permissions`** inside a session to see the current
rules and move a command between buckets on the spot; the file and the command edit the same
config. Start strict, loosen as trust builds, and keep real work on a branch.

> 💡 **Try it:** In a live session, run `/permissions`, then ask it to read your `.env`. If your
> deny rule is right, it refuses — that refusal is the proof your fence exists.

## The 2026 layer: auto mode + OS sandboxing

Buckets are the classic layer — they gate *whether* a tool runs. Two newer layers change *how
much you have to watch*.

**Auto mode** removes the per-action click. Instead of you approving each step, a safety
**classifier** screens every action and lets the safe ones through, stopping only on the
genuinely risky. You trade your attention for a model's judgement — excellent for flow, so pair
it with strict deny rules the classifier can never override.

**OS sandboxing** (`/sandbox`) is the stronger, structural one. It runs Bash commands inside an
operating-system jail — macOS Seatbelt, Linux/WSL2 bubblewrap — that physically limits what they
can touch: writes only to the working directory, network only to domains you've allowed. Turn on
its **auto-allow** mode and ordinary Bash stops prompting, because the *boundary* is the safety,
not your vigilance — a command that tries to write outside the repo or phone home is blocked by
the OS, whatever the model decided to run.

The two are independent and stack: auto mode screens *intent*, the sandbox contains *blast
radius*. Two caveats that bite: your explicit **deny** rules win even under auto-allow, and the
sandbox's default *read* policy still opens `~/.ssh` or a stray `.env` — so add a
`sandbox.credentials` block for real secrets:

```json
{
  "sandbox": {
    "enabled": true,
    "credentials": {
      "files": [{ "path": "~/.ssh", "mode": "deny" }],
      "envVars": [{ "name": "DATABASE_URL", "mode": "deny" }]
    }
  }
}
```

One note for Windows users: **the sandbox needs WSL2** — native Windows isn't supported,
so there you lean on auto mode plus deny rules, or run Claude Code inside WSL2 to get the jail.

## Choosing a model

Claude Code's default model depends on your plan: some plans default to the lighter **Sonnet**
tier, others to the heavier **Opus** tier, and on some plans Claude Code falls back to Sonnet when
you cross a usage threshold so you keep working — so a mid-session switch isn't a bug. Exact
model versions change every few months; `/model` and the model-config docs (Read-after) always
show the current ones. Swap models any time with **`/model`**,
or use `opusplan` (Opus plans, Sonnet executes) for both at once. When to route which tier — and
how hard to let it think — is its own skill (→ models-and-effort).

You now have a hardened setup, not just a working one — the rest of the pillar is about
*driving* it, starting with the core loop.
