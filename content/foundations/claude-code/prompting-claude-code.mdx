The AI mental models pillar gave you the generic five-part brief — role, task, context,
format, constraints (→ prompting-in-2026). This lesson is the layer bolted on top: how that
brief changes when the reader is an **agent editing your repo**, not a chat window. One shift drives
everything — an agentic prompt is a **work order, not a wish.** Claude Code does
*exactly* what you set it up to do, so most "Claude Code is dumb" moments are really
under-specified orders. You're not asking; you're dispatching.

## From wish to work order

Four moves turn a wish into an order — the CC-native spin on the brief:

1. **Goal** — the outcome in plain terms, one sentence.
2. **Scope** — which files/areas it may touch, and *explicitly what to leave alone.*
3. **Success criteria** — the observable pass/fail you'll both read: a test passes, no
   horizontal scroll at 375px, the bug is gone.
4. **Explore first** — read the real code before proposing changes, so it acts on facts,
   not guesses (this is the loop's Explore step wearing a prompt → core-loop).

Miss any one and the agent fills the gap with a guess. The goal it can usually infer;
scope and success it cannot.

## The skeleton: Input → Workflow → Output

The strongest agentic prompts share one shape — **Input → Workflow → Output.** It's the
work order made mechanical:

- **Input** — everything that goes *in*: the files, the error text, the data, the
  `CLAUDE.md` (or `AGENTS.md`) it should lean on. Name it; don't make it hunt. (*Which*
  tokens to feed and how to keep the window clean is its own discipline
  → context-engineering — here you just name the inputs.)
- **Workflow** — the ordered steps you want run, not just the end state. "Read X → tell
  me the root cause → fix only Y → run the tests → show the diff." Numbering the steps is
  how you stop it skipping the boring middle or declaring victory early.
- **Output** — the exact artifact and shape you want back: a plan, a diff, a JSON block,
  a markdown table you can paste into a PR. Leave it open and you inherit the model's
  default format.

```prompt
Input: src/checkout/*, the failing test in checkout.test.ts, our CLAUDE.md.
Workflow:
1) read them, change nothing
2) tell me the root cause
3) fix ONLY the total calc
4) run the test suite
Output: the root-cause line, then the diff, then the passing test output.
```

The same skeleton scales from a one-line fix to a multi-file feature, and filling the
three slots already covers the four moves above — Input carries "explore first," Output
carries your success criteria.

> 💡 **Try it:** take a request you'd normally type as one line and split it across three
> labels — Input / Workflow / Output. The gaps you're forced to fill are exactly the
> guesses you were about to outsource to the model.

## Fence what it must NOT touch

The highest-leverage line in an agentic prompt is often the **negative** one. An
unbounded agent treats every nearby file as fair game: you ask it to fix the total calc
and it "helpfully" reformats the whole module, renames a shared type, and breaks two
call sites you never mentioned. A one-line fence — "change only `cart.ts`; do not touch
the checkout UI or the shared types" — kills the surprise refactor, keeps the diff
reviewable, and stops it burning context on code that was already fine. This is the
CC-specific reliability lever generic prompting never needs, because a chat model can't
reach into your repo. Yours can.

> 💡 **Try it:** add one clause to your next prompt — "change only these files, leave
> everything else untouched" — and watch how much smaller and more reviewable the diff
> comes back.

## Iterate early, not late

Watch the first move. If the plan or the first edit heads the wrong way, stop and correct
*immediately* — a one-sentence nudge on step one is free; unwinding twenty steps of wrong
work costs your evening. This is why the loop front-loads Plan Mode (→ core-loop): you
approve the approach while a correction is still cheap. Cheap-early beats expensive-late,
every time.

## Weak vs strong, side by side

- Weak: *"make the dashboard better."*
- Strong: *"On the dashboard the charts overflow on mobile. **Input:** `Dashboard.tsx` +
  its CSS. **Workflow:** read them, propose a layout-only fix, implement it. **Output:**
  the diff. **Scope:** don't touch desktop or the data layer. **Success:** no horizontal
  scroll at 375px."*

Same model, different league — and the strong one is just the skeleton filled in. No
clever wording, only structure.

## Build from reusable blocks — the ladder

Notice those sections are **composable**: a role block, an input block, a workflow block,
an output-format block, a verification block. You don't write prompts from scratch; you
*assemble* them from blocks you already trust, swapping only the part that changes.
That's IndyDevDan's core move — and it sets up a **ladder of prompt formats** you climb
as reuse grows:

1. **Ad-hoc ask** — a one-liner. Right when the whole diff fits in a sentence.
2. **Structured order** — goal + scope + success in one message.
3. **Input → Workflow → Output** — the labeled skeleton above.
4. **+ worked example** — an input→output pair to lock a pattern (few-shot mechanics
   → prompting-in-2026).
5. **Parameterized template** — the same skeleton with `{variables}`, saved to a file,
   run across many inputs.
6. **Prompt-as-tool** — that template promoted to a one-key command (packaging
   → skills-and-plugins).
7. **Self-dispatching prompt** — a prompt that writes or fans out prompts to agents
   (→ autonomy-at-scale).

Match the rung to the stakes: don't climb to level 6 for a rename, and don't stay at
level 1 for the thing you run every week. The craft isn't always reaching the top rung —
it's knowing which rung a task deserves, and building the reusable blocks so climbing is
cheap when it's worth it.
