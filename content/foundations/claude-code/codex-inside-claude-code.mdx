You've built the whole machine: the explore→plan→code→commit loop, the context discipline, a
harness of hooks and skills, a team of subagents. Every check in that machine still comes from
one model family, though. This lesson adds a reviewer from outside it: a **rival lab's** model,
OpenAI's Codex, wired straight into the loop you already own. The official `codex-plugin-cc`
turns Codex into an on-call reviewer and delegate you summon with a slash command. The skill
isn't installing it — that's five minutes — it's understanding *why* a second lab's review
catches what a second Claude can't, and *how* to make its judgment actually bite.

## Where Codex sits (the one-paragraph map)

Codex is Claude Code's **sibling in the agentic-CLI family**: same mental model, different lab.
That sibling status *is* the point — a tool that thinks like Claude Code but was trained by a
different company is the ideal second opinion. (The four-family AI-coding-tool landscape is
covered in → what-is-claude-code.) Any "X beats Y" verdict expires in months; re-check the current
landscape before you repeat one.

## Wire it in

The plugin is a thin bridge to your *local* Codex CLI — it wraps the `codex` binary, reuses its
auth and config, and runs on the same checkout. So setup is two installs. First the plugin:

```bash
/plugin marketplace add openai/codex-plugin-cc
/plugin install codex@openai-codex
/reload-plugins
```

Then the engine it drives — the Codex CLI itself (`npm install -g @openai/codex`, or another
install option from its README), signed in with a ChatGPT subscription or an OpenAI API key.
`/codex:setup` checks both: it reports
whether Codex is installed and authenticated, offers to run the npm install for you, and points you
to `codex login` if you're not signed in. Run it until it's green and you'll see the `/codex:*`
commands plus a `codex:codex-rescue` subagent in `/agents`. (Plugin and marketplace *mechanics* are
→ `skills-and-plugins`; here you're just consuming one someone else packaged.)

## The commands that matter

Four carry the weight:

- **`/codex:review`** — a read-only review of your current git state. It reads your uncommitted diff
  (or `--base main` for a branch), a non-Anthropic model critiques it, and the findings come back
  *verbatim* — it never edits your files. Run large ones with `--background`.
- **`/codex:adversarial-review`** — the steerable sibling. Instead of hunting defects it challenges
  the *approach*: the assumptions, tradeoffs, and failure modes. It takes focus text, so aim it:
  `/codex:adversarial-review challenge the retry and caching design`.
- **`/codex:rescue`** — delegation. Hand a bug or a bounded implementation to Codex through the
  rescue subagent; it's write-capable, takes `--model`/`--effort`, runs `--background`, and can
  `--resume` its last thread. Your "let the other lab try" button.
- **`/codex:transfer`** — moves the entire session across. It prints a `codex resume <session-id>`
  so you continue the exact context in Codex's own TUI. A bridge, not a wall.

`/codex:status`, `/codex:result`, and `/codex:cancel` manage the background jobs the first three can
spawn.

## Why a rival lab reviews better than a second Claude

Here's the load-bearing idea. You already run a second reviewer — the diff-only subagent from the
core loop, a fresh Claude with none of your session's blind spots (→ `subagents-and-agent-teams`).
That catches a lot. But it shares Claude's **training data, tokenizer, and failure modes**, so its
errors are *correlated* with the author's. Ask the same model family to check its own work and it
will confidently miss the same class of bug twice — two samples from one distribution aren't
independent evidence, they're the same guess drawn twice.

A different lab's model has **decorrelated** blind spots. Where Claude is structurally weak, Codex
may be strong, and the reverse. That's the entire argument for cross-provider review: you're not
buying a *better* reviewer, you're buying an *independent* one — the only kind that catches what the
author can't see by construction. It's the runnable-check habit (→ `core-loop`) pushed to its
logical end: verify with something that doesn't share your priors.

## Redaction discipline: strip the self-assessment

The single highest-leverage habit in this lesson, and almost nobody does it. When you ask a model
to review a change, the instinct is to hand it context — including the author's own summary:
*"I implemented the guardrail correctly; all tests pass."* That one sentence **anchors** the
reviewer. It now grades the *narrative* instead of the code, nods along, and returns a shallow
rubber stamp.

Redact it. Give the reviewer the **diff and the spec/goal — nothing else.** No "I fixed it," no
self-graded test report, no stated confidence. Practitioners who strip the self-assessment (see
the Todd Orr write-up in Read-after) report **noticeably deeper** reviews, because the model has
nothing to defer to and has to actually read the code. This is *why* the plugin's `/codex:review` reads raw git state and returns output
verbatim — by design it never sees Claude's prose. The trap opens the moment *you* frame a
delegation or paste a summary in "to help." Context, yes; the author's verdict, never.

> 💡 **Try it:** delegate the same diff two ways — once with Claude's "this works, tests green"
> summary attached, once with only the diff and the goal. Watch the second review surface things the
> first waved straight through.

## Division of labor: a working split

There's no controlled benchmark that settles who does what, so treat this as a starting split
drawn from practitioner reports (the Composio write-up in Read-after is one: hundreds of hours
with both, mostly hands-on impressions rather than tests), and re-check it before you quote it.
In many users' reports, **Codex** feels steadier across sessions (it picks a repo back up after
a few days without drifting) and goes further on a plan's usage limits, which suits background
reviews and rescues you don't babysit. The same reports tend to favor **Claude Code** for *long
single sessions* (context management and compaction), *big tool outputs*, and *orchestration* —
subagents, hooks, teams, the harness you spent this pillar learning to run. If that matches what
you see, the split writes itself: **Claude Code as the orchestrator, Codex as the specialist you
delegate to.** Keep the loop, the planning, and the coordination in one place; hand the
second-opinion review and the cheap async pass to the other lab. If your own runs disagree,
swap the roles. Tool-fluent, not tool-loyal.

## Make it non-optional: the Stop-hook review gate

A review you have to *remember* to run is a review you'll skip under pressure. `/codex:setup
--enable-review-gate` wires the plugin's **Stop hook**: every time Claude tries to end a turn *after
making code changes*, a targeted Codex review fires, and on a blocking finding the stop is
**refused** — Claude has to address it before it can finish. That's the hooks lesson's finish-line
gate (the mechanics are covered in → hooks-automation) staffed by a cross-provider brain: the runnable check
made external and mandatory. The cost is real — it's a Claude↔Codex round-trip that can loop and
drain *both* providers' usage limits — so arm it for high-stakes or overnight runs you'll monitor
and disable it for interactive work. Hamel Husain's `claude-review-loop` (backup) is the hand-rolled
version of the same idea when you want to own the wiring.

## Scale it: worktree review fleets

One reviewer is a habit; a fleet is leverage. When several changes are in flight — parallel writers
each in their own **git worktree** (basics in → subagents-and-agent-teams) — fire a
`/codex:review` per worktree and every change gets its own independent, non-Anthropic read at once,
with zero file collisions. The worktree isolates the *write*; the per-worktree Codex pass isolates
the *review*. Orchestrating many self-directing agents into a standing fleet is its own topic
(→ `autonomy-at-scale`); the point here is narrower and immediately usable: **parallelism plus
cross-provider review** is how you keep speed *and* a second lab's eyes on every diff. Not a new
tool to marry, but a rival lab's judgment wired into the loop you already own.
