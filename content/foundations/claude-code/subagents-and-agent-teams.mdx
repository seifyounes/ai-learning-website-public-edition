  clone; about 25 minutes). Add `.claude/agents/diff-reviewer.md` with a `description` like

  ```prompt
  I have two independent questions about this repo. Spawn one Explore subagent per question
  so they run in parallel, each returning a short summary — edit nothing:
  1) [a question about the area you know least, e.g. "how the reporting module reads the

  2) [a question about another, e.g. "where configuration and environment variables are read"]
  ```

A single Claude Code session is one worker with one context window and one train of
attention. Treat it that way and your ceiling is whatever that one worker can hold.
**Subagents and Agent Teams turn the solo worker into a team** — a lead that plans and
delegates, specialists that each think in their own clean context, and parallelism
wherever the work is genuinely independent. The skill isn't spawning agents; it's knowing
*what* to hand off and what to keep in one hand.

## One worker, one window

Two problems push you to delegate. **Context bloat:** reading a large subsystem fills your
main window with logs and file dumps you'll never reference again, and quality sags as it
fills. **Serial bottlenecks:** independent tasks queued one behind another burn time that
parallel workers would reclaim. A subagent solves both — it runs in its **own isolated
context window**, does the heavy reading there, and returns only a summary to yours. Your
main thread stays clean, and the throwaway reading is paid for once, out of sight. (*Why* a
loaded window degrades output is token economics — → **context-engineering**.)

## Custom agents live in `.claude/agents/`

Define a reusable specialist as a markdown file in **`.claude/agents/`** (project, checked
into the repo so the team shares it) or **`~/.claude/agents/`** (user, every project). The
YAML frontmatter sets its **`name`**, a **`description`** — the field Claude reads to decide
when to delegate, so write it like a job posting — an optional **`tools`** allowlist, and a
**`model`** (route cheap, mechanical work to Haiku to control cost). The markdown body
becomes its system prompt. Claude Code also ships built-in **Explore** and **Plan** agents
you already use: Explore is the read-only codebase-mapper the core loop leans on. The
**`/agents`** command lists what you have; in current versions it points you to edit the
files directly or ask Claude to scaffold one. (Same idea elsewhere: GitHub Copilot's custom
agents are also markdown files checked into the repo, and Cursor and OpenAI's Codex can run
several agents in parallel, each in its own worktree or cloud sandbox.)

## Delegate research and review — not implementation

This is the discipline the whole lesson turns on. Subagents are excellent at **read-heavy,
parallel, throwaway-context** work: exploration, research, code review, verification. They
are *bad* at parallel implementation, for one concrete reason — a subagent can't see your
working tree or another agent's edits, so two agents writing the same files silently
overwrite each other. Anthropic's own guidance is blunt: **start with research and review,
and avoid file conflicts by giving each agent different files.** So fan *out* on questions
and converge *in* on a single writer. A second, independent reviewer that sees only the diff
— a fresh context with none of your blind spots — is one of the highest-value delegations
there is: it's the runnable-check habit from the core loop, staffed by a second brain.

> 💡 **Try it:** hand three unrelated questions to three subagents at once:

```prompt
I have three independent questions. Spawn one subagent per question so they
run in parallel, and report each answer back as a short summary — don't edit
anything:
1) where errors are logged and how they're formatted
2) which files read environment variables or config
3) where session state lives in the auth flow
```

## Nested subagents (up to five levels)

A subagent can spawn its *own* subagents. Reach for it when a delegated job splits further —
a reviewer that dispatches a verifier per finding, say — so all the intermediate output
stays buried and only the top-level summary reaches you. Depth is counted from your main
conversation, and the ceiling is **five levels**: a subagent at depth five gets no delegation
tool and can't spawn further. The limit is **fixed and not configurable**, which is the
point — it stops a runaway tree from forking forever while you keep the clean summary at the
top.

## Agent Teams — peers that coordinate (experimental)

Subagents report back to whoever spawned them and never talk to each other. **Agent Teams**
(shipped experimental in early 2026) remove that wall: multiple full Claude Code sessions run
as a team, each with its own context window, sharing a **task list** and messaging each other
directly through a mailbox. One session is the **team lead** — it assigns work and
synthesizes results — while teammates claim tasks and can challenge each other's findings.
It's **off by default**; enable it by setting `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS` to `1`
in your `settings.json` env block, then describe the team in plain language:

```prompt
Spawn three teammates to review PR #142: one on security, one on performance,
one on test coverage. Have them share findings, then synthesize.
```

The same discipline scales up — teams shine on parallel review, competing-hypothesis
debugging, and cross-layer features where each teammate owns *different* files. They cost far
more tokens (each teammate is a whole session), there are no nested teams, and the lead is
fixed for the session — so reach for a team only when the workers genuinely need to
coordinate, not merely return a result. Orchestrating *many* of these into self-directing
fleets is a bigger topic — → **autonomy-at-scale**; driving them with a second model is
→ **codex-inside-claude-code**.

## Worktrees: the safety rail for parallel writes

When agents *must* edit in parallel, isolation stops the collisions. A **git worktree** is a
second checkout of the same repo on its own branch, so each agent works in its own copy and
nobody overwrites anybody. Claude Code gives you two on-ramps: set **`isolation: worktree`**
on a subagent definition (it gets a temporary worktree, auto-cleaned if it makes no changes),
or create worktrees by hand for parallel sessions and teammates. This is the primitive under
every safe parallel-write setup — learn it here as the basics; the fleet-scale version lives
in the two lessons linked above.

## When one session wins

Delegation buys parallelism and clean context at the cost of orchestration and tokens. For a
quick, sequential, one-file change, a single session is simply faster — no hand-off, no
summary round-trip. Reach for the team when the work is **large, parallelizable, or
context-heavy**, and even then hold the rule: **delegate the reading, keep the writing in one
hand** — unless you've given each writer its own worktree.
