`CLAUDE.md` *asks* Claude to follow your rules; a prompt *requests*. **Hooks make them law.** A
hook is a shell script the harness runs automatically at a fixed point in the agent loop — before
a tool call, after an edit, when the turn tries to end — so the behavior happens because the
*harness* fired it, not because the model chose to. That's the shift: from hoping to **wiring**.

## Advisory vs. guaranteed — the whole point

Everything you've built so far steers the model *probabilistically*. CLAUDE.md, skills, a
well-worded prompt: the model usually complies, sometimes doesn't — and "sometimes doesn't" grows
with context pressure and task length. A hook is *deterministic*: the harness executes it every
time, identically, whatever the model decided or forgot. So the rule is blunt. When something
**must** happen — tests run, secrets stay untouched, formatting is clean — you don't write it in a
doc and cross your fingers, you make it a hook. Advisory is for taste; guaranteed is for anything
load-bearing. (Same idea elsewhere: Cursor has its own agent hooks, and for any tool without
them, a git pre-commit hook or a CI check enforces the same rule on every commit.)

## The lifecycle events you'll wire

Hooks attach to points in the agent loop. The load-bearing set:

- **PreToolUse** — fires *before* a tool runs, and can **block it**. This is your gate: inspect
  the exact command or file path and refuse edits to `.env`, an `rm -rf`, a force-push.
- **PostToolUse** — fires *after* a tool succeeds. The workhorse: run your formatter, linter, or
  tests after every edit so quality is automatic instead of remembered.
- **Stop** — fires when Claude tries to *end the turn*. Run the suite here and you can refuse to
  let it stop on red.
- **SubagentStop** — the same finish-line gate for a subagent's turn, so delegated work is
  verified before its result returns (→ subagents-and-agent-teams).
- **Session** (`SessionStart` / `SessionEnd`) — bookend the whole session: load fresh context in,
  log or clean up on the way out.

Two more you'll meet: **UserPromptSubmit** (screen or enrich a prompt before Claude sees it) and
**PreCompact** (snapshot state before the window is summarized). The event surface keeps *growing*
(newer versions add events, including some for Agent Teams), but these core events are unchanged
in name and behavior; the newer ones are additions, not replacements.

Everything is configured in **`settings.json`** with a matcher that picks which tools trigger it:

```json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [{ "type": "command", "command": ".claude/hooks/guard.sh" }]
      }
    ]
  }
}
```

## How a hook blocks and talks back

A hook reads a JSON event on stdin (the tool name, its inputs, the session) and answers two ways.
The fast way is the **exit code**: `0` = allow and continue; **`2` = block, and send stderr
straight back to Claude** as feedback; anything else = a non-blocking error. The precise way is
**JSON on stdout** — a `decision` with a `reason`, or for PreToolUse a
`hookSpecificOutput.permissionDecision` of `deny` with a reason. Either way, the key move is that a
hook doesn't just *log* — it **feeds a verdict back into the loop**, and Claude reacts to it. That
is the difference between a dashboard and a control.

This is also what separates a hook from a **permission deny rule** (those live in
→ install-first-session). A deny rule is coarse, static string-matching; a PreToolUse hook is a
*program* — it reads the real arguments and decides with logic, allowing some cases and blocking
others with an explanation the model can act on.

## Hooks are how you wire a sensor into the loop

Harness engineering gave you the concept: an agent is a model plus the guides and **sensors** you
build around it, and a sensor only matters when it's **load-bearing** — on the path the agent must
travel, not a doc it might read (the theory lives in → harness-engineering). **Hooks are the
wiring.** A test suite on its own is just a sensor; a *Stop hook that runs it and `exit 2`s on
failure* is that sensor made load-bearing — the turn cannot end until it passes, and the agent
can't route around it. A PreToolUse guard is a guide made deterministic — the guardrail fires
*before* the act instead of trusting the model to recall the rule. When the Harness engineering
lesson said "make your scaffolding load-bearing," a hook is the mechanism it meant.

## Two patterns you'll ship tonight

**The safety gate (PreToolUse).** One script that blocks edits and reads of secrets plus the
handful of irreversible commands, with a reason fed back so Claude self-corrects. Write it once
in *user* settings and it guards every repo you touch.

**Test-on-stop (Stop).** Run the suite when Claude tries to finish; `exit 2` with the failure on
red so it keeps working until green — the deterministic version of the runnable-check habit
(the idea is covered in → core-loop; this is how you make it non-optional). One gotcha: the Stop
event passes `stop_hook_active` so you can detect "I'm already looping because of my own hook" and
cap the retries — deterministic shouldn't mean infinite.

> 💡 **Try it:** add a Stop hook that runs your tests and blocks on failure, then deliberately
> break a test and try to end the turn. Watch the harness refuse to let the session close — that
> refusal is your standard, enforced.

Hooks are the smallest lever with the biggest reliability payoff: a few shell scripts on lifecycle
events turn "the agent usually behaves" into "the harness makes it" — the jump from *using* Claude
Code to *operating* it.
