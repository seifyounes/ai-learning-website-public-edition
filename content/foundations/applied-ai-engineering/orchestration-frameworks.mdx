Applied-AI job listings name **LangGraph, LlamaIndex, LangChain and the OpenAI Agents
SDK** often enough that you should know what each one does. But the senior skill is
knowing **when you don't need them**. This lesson gives you both: fluency in what they do,
and a clear rule for when one earns its place in your codebase.

## What frameworks actually give you

You built an agent loop by hand earlier in this pillar (→ build-agent-in-code): LLM call,
tool request, execute, feed the result back, repeat. Frameworks industrialize that loop:

- **State management.** Durable state across steps, resumable after crashes, and
  checkpoints a human can approve before the agent continues.
- **Graphs, not lines.** Branching, parallel paths and cycles ("critique your answer, then
  retry") as explicit nodes and edges you can visualize.
- **Plumbing.** Retries, streaming, memory and a large catalog of pre-built tool and
  retrieval integrations.

## The cast, in one line each

- **LangGraph**: the low-level **runtime**. Agents as state machines with nodes, edges,
  cycles and checkpoints; the durable base the higher layer builds on.
- **LangChain**: the **high-level agent layer that runs on LangGraph's runtime**, not a
  legacy tool it superseded. The fast path to a working agent, with LangGraph underneath
  when you need fine control. Both reached a stable 1.0 on 22 October 2025
  ([LangChain's announcement](https://blog.langchain.com/langchain-langgraph-1dot0)).
- **LlamaIndex**: the **data framework**. Ingestion, parsing, chunking, indexing and
  retrieval; strongest when the RAG pipeline is the hard part.
- **smolagents** (Hugging Face): minimal, code-first agents that write Python instead of
  JSON tool calls. Good for learning and lightweight jobs.
- **Vendor agent SDKs**: the OpenAI Agents SDK, Google's Agent Development Kit and the
  Claude Agent SDK give you a thin agent loop tuned to one provider's models, usually with
  ways to call others. CrewAI is a popular option for multi-agent "crews".

## When vanilla wins

Anthropic's widely cited engineering post *Building effective agents* (in the backups)
makes the point plainly: the most successful production systems tend to use **simple,
composable patterns** (a single call, prompt chaining, routing) rather than heavyweight
agent frameworks. A framework earns its place when you need durable state, complex
branching or human checkpoints. It costs you a debugging layer, version churn and lock-in
from day one.

## Worked example: one support agent, two ways

Take a support agent for an online shop with two tools, `getOrderStatus` and
`getReturnPolicy`.

1. **Vanilla version.** A list of messages and a loop: call the model with the tools; if it
   asks for a tool, run it and append the result; otherwise return the answer. Around 60
   lines in any language, and every line is yours to debug.
2. **Add branching.** Simple questions get answered; return requests get the policy first.
   Still vanilla: that's an `if` on the model's classified intent.
3. **Add a human checkpoint.** Refunds over a set amount need a manager's approval, which
   can take hours. Now you need to save the conversation and pending action somewhere,
   resume after a server restart, and make sure the refund never runs twice. You're
   writing a state store, resume logic and idempotency checks.
4. **That's the trigger.** Step 3 is what a graph runtime gives you: nodes (`classify`,
   `lookupOrder`, `answer`, `proposeRefund`, `humanApproval`, `executeRefund`), edges
   between them, an interrupt before `executeRefund`, and a checkpointer that persists
   state. LangGraph now earns its costs.

The framework didn't become right because the agent got "serious". It became right at the
exact moment you needed durable state and a human pause.

> 💡 **Try it:** Pick one AI feature or automation you have (or want). Answer three yes/no
> questions: does it keep state across more than one request? Does it loop or branch back
> on itself? Does it pause for a human? Zero yeses means vanilla. One or more means a
> framework is worth a look.

## Common failure modes

- **Stack traces run through five layers you didn't write** → a framework was adopted for
  a one-call feature → strip it back to the provider SDK.
- **A routine upgrade breaks the app** → a fast-moving dependency isn't pinned → pin
  versions and upgrade deliberately, rerunning your eval set each time.
- **The token bill is higher than your prompts explain** → hidden framework prompts or
  default memory → trace the calls (→ observability-tracing) and read what's actually sent.
- **A hand-rolled agent loses progress or repeats an action after a restart** → state
  lives in memory and actions aren't idempotent → persist state, or adopt a runtime with
  checkpoints.
