  Build the baseline the gate needs: a real eval set for one AI feature, written before you start
  tuning its prompt. Use a feature from your own project, or a "reply to a support ticket"
  drafter for a small online shop:

  ```prompt
  Help me hand-build a 10-case eval set for [feature]: 10 realistic inputs (include 2-3 hard
  ones, e.g. an angry customer, a missing order number, a request we must refuse), each paired
  with what a GOOD output looks like for one chosen tone (e.g. warm but brief). Then run this
  DRAFT prompt [paste it] against all 10 and score each pass/fail against its reference.
  Report the pass rate and the failure patterns.
  ```

  Then calibrate a judge against yourself: give the 10 outputs and a 0-3 rubric (faithfulness,
  tone, task completion) to a model from a different company than the one that wrote them, and
  count the cases where its verdict disagrees with your pass/fail.

  **No-code path:** keep the 10 cases in a spreadsheet (input, reference, output, pass/fail,
  judge score), run the draft prompt in any chat assistant, paste each output in, grade it
  yourself, then paste the outputs and rubric into a second assistant for the judge column.

  Success: you have 10 scored cases, a baseline pass rate to measure the next prompt tweak against, and a count of where the judge disagrees with you.

This is the lesson that separates hobby AI features from professional ones. LLM output is
**non-deterministic**: it varies between runs, and it shifts every time you tweak a prompt or
switch a model. "I tried it and it looked good" is not a quality strategy. **Evals** are how you
actually measure quality, and they're the missing half of treating prompts as code
(→ prompt-as-code): you version prompts *and* you test them.

## What an eval is

An eval is a **test set for your AI feature**: representative inputs, a definition of a good
output for each, and a way to score. You run a prompt and model against the set and get a
number, so when you change something you can *see* whether quality went up or down.

## Start by reading outputs, not by picking metrics

The most common beginner mistake is reaching for generic scores ("helpfulness 7.2/10") before
knowing how the feature actually fails. Practitioners such as Hamel Husain teach the reverse
order, often called **error analysis**:

1. Run the feature on 30–100 realistic inputs (real logs if you have them).
2. Read every output and write a one-line note on each failure.
3. Group the notes into categories ("promises refunds", "ignores the order number", "too
   long") and count them.
4. Write evals for the categories that matter most.

Your evals then measure *your* product's real failure modes, not someone else's idea of
quality. Good sources of cases: production logs, bug reports, hand-written edge cases (empty
input, angry customer, a request you must refuse) and, carefully, model-generated variations.

## Three ways to score

- **Rule-based or exact checks**: when there's a deterministic answer (a category, a number,
  valid JSON, "never contains a discount code"). Fast, free, objective. Use them wherever
  they fit.
- **LLM-as-judge**: a model scores open-ended qualities (faithful to the source? right tone?
  answered the question?). Scalable for fuzzy outputs.
- **Human review**: the gold standard for nuance; expensive, so used to label a sample and
  calibrate the other two.

Prefer **binary pass/fail with a written criterion** ("passes if every fact in the reply appears
in the ticket") over 1–10 scales. Binary verdicts are easier for humans and judges to agree on,
and a pass rate is easy to compare across versions.

## Use LLM-as-judge carefully

Judges are useful but biased: they tend to prefer **longer** answers, the **first** option in a
side-by-side comparison, and outputs from their **own model family**. Mitigations:

- judge with a model from a *different* family than the one you're testing;
- give it a specific rubric and ask for a short reason before the verdict;
- in side-by-side comparisons, run both orders;
- **validate the judge**: label 30 or so outputs yourself and check how often it agrees with
  you. If it disagrees often, fix the rubric before you trust its numbers.

An unvalidated judge is just confident noise.

## Offline and online

**Offline evals** run on your fixed set before a change ships; wire them into CI so a prompt
or model change can't be promoted if the pass rate drops. **Online evals** watch production:
sampled traces scored by the same judges, user feedback, and spikes in specific failures
(→ observability-tracing). Every production failure you find becomes a new offline case, so the
set grows from reality.

## Worked example: gating a support-reply drafter

1. **Collect.** Pull 40 real tickets and generate replies with the current prompt (v1).
2. **Read and categorise.** You find three failure types: it sometimes promises refunds, it
   drops the order number, and replies to angry customers sound defensive.
3. **Write checks.** A rule: the reply must not contain "refund approved". A rule: if the
   ticket has an order number, the reply mentions it. A judge, from a different model family,
   for tone: "pass if the reply acknowledges the problem before explaining; fail if it argues."
4. **Calibrate.** You label 30 replies for tone yourself and compare with the judge. Where
   it disagrees, you sharpen the rubric's wording until it mostly matches you.
5. **Baseline and gate.** v1 gets a pass rate on all three checks. You write v2; it fixes the
   order number but fails more tone cases. It doesn't ship until it beats v1 on all three.

> 💡 **Try it:** Take one answer a chat assistant gave you this week. Paste it into an
> assistant from a *different* company with: "Grade this pass/fail against this criterion:
> [one sentence]. Give a one-line reason first." Then grade it yourself. Do you agree?

## Common failure modes

- **Every eval passes, but users still complain** → the set is too easy or invented → add
  real failures from logs and support tickets.
- **Scores jump around between identical runs** → non-determinism on small sets → run each
  case a few times, or at low temperature, and compare pass rates, not single runs.
- **The judge rewards waffle** → length bias and a vague rubric → binary criteria, a
  different-family judge, and regular checks against your own labels.
- **Great eval scores, worse product** → you tuned the prompt to the test set → keep a
  held-out slice you never tune against.

Tools such as Promptfoo, Braintrust, LangSmith and Langfuse run and track evals, but a
spreadsheet and a short script are a fine start. Even ten examples beat zero. Next: making
your feature fast and cheap enough to ship (→ cost-latency-caching).
