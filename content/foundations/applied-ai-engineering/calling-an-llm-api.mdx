Everything so far has been *using* AI through someone else's app. This pillar is about
**building AI into your own** software, and it starts with one skill: calling a model from
code through its **API**. Every later lesson in this pillar (structured outputs, RAG, agents,
evals) is this same call with more machinery around it, so it pays to understand it exactly.

**You'll need:** basic Python or JavaScript (variables, functions, a loop), running a script from
a terminal, and an API key kept in a `.env` file, with a spending limit set on the account first.
If you don't code yet, do a free beginner course (freeCodeCamp's Python or JavaScript course is a
good start) before this pillar, or use the no-code path in the task below to see the same call in a
provider's web playground.

## The anatomy of a request

An API call to any major model carries the same three things:

1. **The model**: which model and tier to use (picking one is covered in → models-and-effort).
2. **The messages**: usually a `system` message (the standing rules) plus a `user` message
   (the request). Your prompting skills live here.
3. **The parameters**: `temperature` (how much the sampling varies), `max_tokens` (a hard cap
   on output length) and a few others.

You send that, you get the model's text back. The same pattern powers every AI feature you
have used.

## The model remembers nothing

The single most useful fact for a beginner: by default the API is **stateless**. The model does
not remember your previous call. A "conversation" is your code resending the whole history
(system message, every earlier user turn and every earlier assistant reply) on each request.
Two consequences follow. Long chats get more expensive per turn, because you pay for the
resent history as input tokens. And if your code forgets to append the last assistant reply,
the model answers as if that reply never happened. Some providers offer optional server-side
conversation state, but you should still be able to explain what is in the context on every
call.

## What comes back (read more than the text)

The response carries metadata that production code must read:

- **Token usage**: input and output counts for this call. This is your bill per request, so
  log it from day one.
- **Finish (stop) reason**: *why* generation ended. A natural stop, the `max_tokens` cap (the
  answer is cut off), a content filter, or a tool call. Check for a natural stop (`"STOP"` on
  Gemini, `"stop"` on OpenAI's Chat Completions, `"end_turn"` on Anthropic) before you trust a
  reply. OpenAI's newer Responses API reports the same thing differently (see the footnotes
  below).
- **Errors and timeouts**: real calls fail. Rate limits (HTTP 429), overloaded servers (5xx)
  and network timeouts are routine. The minimum handling is a retry with backoff for transient
  errors and a fallback path for the rest.

## Worked example: one support reply, end to end

Say you are adding an auto-reply to a small online shop's support inbox. Here is the whole
flow, step by step.

**Step 1, build the request.** In provider-neutral form:

```json
{
  "model": "a-small-fast-model",
  "max_tokens": 300,
  "temperature": 0.2,
  "messages": [
    { "role": "system", "content": "You are a concise, friendly support agent for a small online shop. Never promise a refund; offer to escalate to a person." },
    { "role": "user", "content": "My order #1042 is a week late and I want a refund." }
  ]
}
```

Low temperature for consistency; a modest `max_tokens` as a ceiling on length and cost.

**Step 2, read the response.** You get the reply text, a usage block (input and output
tokens) and a finish reason.

**Step 3, decide whether to trust it.** If the finish reason is a natural stop, the reply can
go into the agent's draft queue. If it hit `max_tokens`, the reply is truncated: don't send
it; log it and retry with a higher cap or a "reply in under 80 words" instruction. Log the
token counts either way.

**Step 4, handle failure.** On a 429 or 5xx, wait and retry with exponential backoff (for
example 1s, 2s, 4s, plus a little random jitter so many clients don't retry in lockstep). Stop
after a few attempts and fall back to a fixed message: "Thanks, a person will reply shortly."

**Step 5, the follow-up.** The customer writes back: "Fine, escalate it." Your next request
must contain the system message, the first user message, the assistant's first reply and the
new message, in order. Skip the assistant's reply and the model won't know what "it" refers to.

That is a production-shaped call: bounded, checked, logged and resilient.

> 💡 **Try it:** In any provider playground (Google AI Studio, the OpenAI Playground or the
> Anthropic Console), set the maximum output to about 20 tokens and ask for a three-paragraph
> story. Look at where the text stops and what the finish reason says. That is the truncation
> your code must catch.

**Streaming.** For anything a person watches, stream the reply: the first words appear sooner, and
the usage and finish reason arrive in the final chunk.

## Protect your key

Your API key is a password that spends money. Load it from an **environment variable or
`.env` file**; never hardcode or commit it (deleting it later doesn't scrub git history). In
apps, keep it **server-side** and route calls through your own backend, never the browser or
a mobile client.

## Vendor-neutral by design (with a few footnotes)

OpenAI, Anthropic and Gemini share this request shape, so switching is mostly endpoint, key
and model name. Many providers and local runners (Ollama among them) also offer an
OpenAI-compatible endpoint. Two differences bite on day one: **Anthropic takes `system` as a
top-level parameter** and **requires `max_tokens`** on every request.

**OpenAI has two interfaces.** The shape above is OpenAI's **Chat Completions**, which most
tutorials and most "OpenAI-compatible" endpoints use, and which is still supported. For new
work OpenAI now recommends its **Responses API**. The ideas are the same (a model,
instructions, input, a cap on output), but the fields differ: the system message goes in
`instructions`, the cap is `max_output_tokens`, and there is no `finish_reason`. Instead the
response carries a `status`: trust a reply only when it is `"completed"`. An `"incomplete"`
response says why in `incomplete_details` (the output cap or a content filter, for example).
It can also keep the conversation on OpenAI's side if you ask it to. Field names change
between versions, so check the current docs before you write against either interface.

## Common failure modes

- **401 or "invalid API key"** → the key isn't loaded (wrong `.env` path, variable name typo,
  server not restarted) → print whether the variable is *set*, never its value.
- **Replies cut off mid-sentence** → `max_tokens` too low and nobody checks the finish reason →
  check it on every call and treat truncation as a failure.
- **A burst of 429s when you process a list** → a tight loop with no backoff or concurrency
  limit → add backoff with jitter and cap parallel requests.
- **"It forgot what I just said"** → the history wasn't resent → append every turn, both
  sides, to the messages you send.
- **"Model not found" after months of working** → the model name was retired → keep the model
  name in config, not scattered through code, and watch the provider's deprecation notices.
