You've learned every piece; now ship one. The capstone isn't about a big app. It's about
taking **one small AI feature all the way to production**, deliberately, using the whole
pillar as a checklist. Small is the point: a modest feature that is measured, hardened and
monitored teaches more, and proves more, than an ambitious demo that only works on a
good day.

## The end-to-end run

1. **Define.** Pick one feature and write its **success criteria** before any code. Good
   sizes: "draft a reply to each support ticket", "answer FAQs from our docs", "summarize
   each client call". Each criterion should be something you can check, not a feeling.
2. **Build.** The core is an **API call** with **prompts as code** (a versioned template,
   not a string buried in a handler) and **structured outputs**. Add **RAG and embeddings**
   if it needs your data (→ rag-fundamentals); add **tools or an agent loop** only if it
   needs to *act* (→ build-agent-in-code).
3. **Eval.** Make a small **eval set** and score the feature (→ evals-and-testing).
   Iterate the prompt or model until it clears the bar you set in step 1.
4. **Harden.** Add **cost caps and caching**, **timeouts and a deterministic fallback**,
   and a **human-in-the-loop** gate for anything risky. Keep the **API key server-side**.
5. **Deploy and monitor, with a mechanism, not vibes.** Ship behind a flag, then turn it on.
   "Shipped" includes a minimal **trace table**: one row per call with prompt version,
   input and output tokens, latency, and guardrail or fallback status (a database table, a
   sheet, or a Langfuse project; → observability-tracing sets this up properly). If you
   can't answer "what did yesterday's calls cost, and how many hit the fallback?", it
   isn't monitored.

## Worked example: meeting transcript → action items

Here's one feature run through all five steps, so you can see the level of detail that
counts as "done".

1. **Define.** Success means: every item has an action and an owner; an owner must be a
   name that appears in the transcript (no invented people); output is valid JSON; a
   meeting with no action items returns an empty list; a one-hour transcript finishes in
   under 15 seconds.
2. **Build.** One server-side function loads prompt template `v1` from a file, wraps the
   transcript in a clearly delimited block, and asks for a schema like
   `{ items: [{ owner, action, due }] }`. The response is validated against that schema
   before anything else touches it.
3. **Eval.** Ten transcripts: six ordinary meetings, two with no action items, one where
   someone says "somebody should look into this", and one very long one. Three checks are
   code (schema valid, owner appears in the text, empty list where expected); one is your
   own judgment on whether the items are right. Version 1 scores 7 of 10: it invents an
   owner for "somebody should", and the long transcript times out.
4. **Fix and rerun.** Prompt `v2` says "if nobody is named, set owner to null". You cap
   transcript length and split longer ones into chunks. Rerun the *whole* set: 10 of 10.
   Now you have evidence, not a hunch.
5. **Harden.** Cache results by a hash of the transcript; skip empty input; after one
   retry on a timeout or invalid JSON, fall back to a plain message ("Couldn't extract
   action items for this meeting") instead of an error; key in a server secret; a per-user
   daily cap; a feature flag that's checked on the call path.
6. **Deploy.** Turn the flag on for yourself for a few days, watch the trace table, then
   turn it on for everyone.

None of those steps is clever. Together they're the difference between "it worked when I
tried it" and a feature you can defend.

> 💡 **Try it:** Before you build anything, open a blank note and write three success
> criteria for your feature, each one checkable by code or by a yes/no judgment. If you
> can't write them in five minutes, the feature isn't defined yet, and that's the most
> useful thing you'll learn today.

## Common failure modes

- **It worked in the demo and breaks in week one** → it was only ever tried by hand on
  friendly inputs → build the eval set *before* you show it to anyone, including edge
  cases.
- **A provider hiccup shows users an error page** → no timeout or fallback on the call
  path → add both, and force a failure once to prove the fallback actually fires.
- **A surprise bill** → no cost cap and no caching, so one heavy user or a retry loop
  multiplies calls → add a per-user cap, cache repeat inputs, and check cost per call in
  the trace table.
- **The key leaks** → the model is called from browser or mobile client code → every model
  call goes through your server, with the key in a server-side secret.
- **Nobody knows if it's still good** → no tracing after deploy → log one row per call and
  look at the fallback rate weekly.

## Why this is the whole pillar

Look at that list: it's every lesson, wired together. API calls, prompts, structured
outputs, RAG, embeddings, agents, evals, cost control and a provider choice. A shipped
feature is just these pieces, assembled with judgment.
