Back in the *AI mental models* pillar you chose models as a *user* (which chatbot to
open). This is the *builder's* version: when you put a model inside an app, you make an
**architecture decision** (managed API or self-hosted) that affects cost, privacy and
control for the life of the product. Decide it on purpose now, because migrating later is
far more expensive than choosing well once.

## The fork: API vs self-hosted

- **Managed API** (Anthropic, OpenAI, Google, Mistral and others). Easiest to build on,
  top-tier quality, no infrastructure to run. You **pay per token**, and your data is sent
  to the provider. This is the right default for most features.
- **Open-weight, self-hosted or local** (Qwen, DeepSeek, GLM, Llama, Gemma, Mistral…). You
  run the model on your own server, a rented GPU or even a laptop. You get **privacy,
  control and a fixed cost** (no per-token fee) at the price of operating it. Open-weight
  models have closed much of the quality gap on many tasks, which makes this a genuine
  option rather than a hobby.

There's a middle ground worth knowing. Hosting providers (Together, Fireworks, Groq,
OpenRouter and similar) serve open models through an ordinary API, and the big clouds
(Amazon Bedrock, Google Vertex AI, Azure) run frontier models inside your own cloud
account. You get open-model prices, or your cloud's data boundaries, without running GPUs.

## Decide on four axes

1. **Quality.** Does the task need a frontier model, or is "good enough" fine? The
   tiebreaker is **your eval set** (→ evals-and-testing): run it against two or three
   candidates and let the scores decide, not the marketing pages or a leaderboard.
2. **Privacy and compliance.** Can this data leave your servers at all? If it can't, the
   decision is mostly made for you, before you look at cost.
3. **Cost at scale.** Per-token API versus fixed infrastructure plus engineering time. A
   self-hosted model costs money every hour it runs, busy or idle, and someone has to
   patch, monitor and upgrade it. Most side projects and early products sit far below
   the volume where that pays off.
4. **Latency and control.** Self-hosting can cut network round trips and lets you pin a
   model version that never changes under you. An API provider can update or retire a
   model on its own schedule.

Take them in that order. Privacy is a gate, quality is the first score, cost only matters
between options that already pass, and latency breaks ties.

## Worked example: break-even on the back of an envelope

Say you're adding a "summarize this support ticket" feature. Each call sends about 1,500
input tokens and gets back about 200 output tokens, and you expect 20,000 calls a day. The
prices below are **made-up round numbers** to show the arithmetic, so use real price pages
when you do this for real.

1. **Monthly tokens.** 20,000 × 1,500 × 30 ≈ 900 million input tokens; 20,000 × 200 × 30 ≈
   120 million output tokens.
2. **API cost.** Pretend the API charges $1 per million input tokens and $4 per million
   output. That's $900 + $480, about **$1,380 a month**.
3. **Self-hosted cost.** Pretend a rented GPU server that can carry your *peak* load costs
   $1,500 a month, plus a few hours of engineering time every month. That's already more
   than the API, before you count the hours.
4. **Scale it.** At five times the volume the API bill is about $6,900, while one or two
   servers might still cope. Now self-hosting deserves a serious look, *if* an open model
   passes your evals.
5. **Check the cheap tier.** If a small, cheap API model also passes your evals at a tenth
   of the price, the API stays cheaper for far longer. Quality first, then cost.

The numbers aren't the lesson; the method is. Write the formula down, plug in real prices
and real traffic, and redo it whenever either changes a lot.

> 💡 **Try it:** Pick a feature you have or want. Estimate tokens per call (a token is
> roughly three-quarters of an English word) and calls per day, open one provider's price
> page, and compute the monthly bill on a cheap tier and a frontier tier. Five minutes of
> arithmetic tells you which side of the fork you're on.

## The rule that saves you: don't lock in

Models and prices change every month. So **route every LLM call through one wrapper.**
Then switching provider, upgrading a model, or sending easy tasks to a cheap model is a
one-line change, not a rewrite. The standard implementation is a **routing gateway**,
such as LiteLLM (open source) or OpenRouter (hosted): one API surface in front of many
providers, with per-model routing, fallbacks and spend tracking. A single model-client
module in your own app is the same idea at app scale. Vendor neutrality isn't just a
principle here; it's good architecture.

## Common failure modes

- **Quality drops the week you switch models** → you picked from a leaderboard, and
  leaderboard tasks aren't your task → rerun your own eval set on every candidate before
  any swap.
- **A provider change takes a week** → model names and SDK calls are scattered through the
  codebase → put them behind one wrapper or gateway, with the model name in config.
- **The self-hosted bill beats the API bill** → volume is below break-even and you're
  paying for idle peak capacity → go back to the API until the arithmetic says otherwise.
- **Legal blocks the release late** → nobody asked where the data goes → ask the privacy
  question first, and read the provider's data-retention and training terms.
- **One outage takes the feature down** → a single provider with no fallback → configure a
  second model or provider in the gateway, plus a deterministic fallback response.
