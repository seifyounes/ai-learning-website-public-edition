You may have used MCP as a *consumer* already (→ mcp-servers). Now you build it. MCP (Model
Context Protocol) is the open standard that lets an AI app plug into tools and data the same
way every time, and understanding it from the inside is one of the most reusable skills in
this course.

## The problem it kills: N×M integrations

Without a standard, every AI app needs a custom integration for every tool: one GitHub
connector for your chat app, another for your IDE, another for the next app. N apps times M
tools. **MCP makes it N+M:** build a capability **once** as an MCP server, and **any**
MCP-compatible app can use it. Anthropic, which introduced the protocol, compares it to a
USB-C port for AI. Today many hosts speak it, including Claude's apps, ChatGPT, Gemini CLI,
Cursor and VS Code with Copilot, so the comparison holds well beyond one vendor.

## The architecture

- **Host**: the AI app (a coding agent, an IDE, a chat app, your own app).
- **Client**: lives in the host and holds one connection to one server.
- **Server**: what *you* build. It exposes three kinds of capability:
  - **Tools**: actions the model can call (query a database, create a ticket).
  - **Resources**: data the host can read and attach as context (files, records).
  - **Prompts**: reusable prompt templates a user can pick.

Under the hood the messages are JSON-RPC. A session starts with a handshake in which client and
server declare what they support; the client then asks the server for its tool list, and the
host shows those **names, descriptions and argument schemas** to the model. From there it's the
tool-calling loop you already know (→ build-agent-in-code), with MCP as the wire between the
host and your code. The spec also defines features flowing the other way, such as a server
asking the host for user input, but tools are where most servers start.

**How they actually talk.** A **local** server runs as a child process the host launches and
speaks over **stdio**: simple, private, no network. Most servers you add to a coding agent run
this way. A **remote** server speaks **Streamable HTTP**, which means it needs real **auth**
(OAuth-style tokens scoping who may call which tools). Local inherits your machine's trust;
remote must earn it.

## Worked example: a notes-search server, from launch to answer

You wrap a folder of meeting notes as a server with one tool, `search_notes(query)`.

1. **Register.** You add one entry to your host's MCP config: the command that starts your
   server (for example `python notes_server.py`), with an absolute path.
2. **Launch and handshake.** On startup the host spawns the process, and they exchange
   capabilities over stdio.
3. **Discovery.** The host asks for the tool list and receives `search_notes`, its
   description ("Search the team's meeting notes by keyword; returns titles and dates") and
   its schema.
4. **Use.** You ask "when did we decide to drop the beta?" The model emits a tool call; the
   client forwards it; your server searches the folder and returns three matching snippets.
5. **Answer.** The host appends the result to the conversation and the model answers with the
   date, citing the note.

Notice what *you* wrote: one function, a description and a schema. The protocol did the rest,
and the same server now works in every MCP host you use.

> 💡 **Try it:** If you have Node installed, run
> `npx @modelcontextprotocol/inspector npx -y @modelcontextprotocol/server-everything`. The
> Inspector opens in your browser against the official reference server. List its tools,
> read one description and call it by hand. **No Node?** Open the connected tools list in
> any MCP host you use and read what each tool's description says it can do.

## MCP or plain function calling?

If a tool is used only inside your own app, plain function calling (→ structured-outputs-tools)
is simpler: no extra process, no protocol. Reach for MCP when the **same capability should
work in several hosts**, when you want other people's AI apps to reach your service, or when
you want to use the many servers others have already written.

## Security: descriptions are untrusted input

A third-party server's **tool descriptions and results go straight into the model's context**.
A malicious or compromised server can hide instructions in a description ("tool poisoning") or
in results, steering the model: prompt injection through the side door
(→ llm-security-prompt-injection). Vet servers like dependencies: who publishes it, what it can
write, how it authenticates.

## Common failure modes

- **The server never shows up in the host** → wrong config file, relative path, or the server
  crashes on start → use absolute paths and test it alone in the Inspector first.
- **A stdio server works in testing, then garbles in the host** → the server prints logs to
  stdout, which is the protocol channel → log to stderr only.
- **The model picks the wrong tool or ignores yours** → too many connected tools, or vague
  descriptions → keep the server list short and write descriptions that say when to use each
  tool.
- **A secret leaks into a conversation** → a token placed in a tool description or returned in
  a result → keep credentials in the server's environment and return only the data needed.

The server you write isn't tied to one vendor; it's an asset across every AI tool you touch.
