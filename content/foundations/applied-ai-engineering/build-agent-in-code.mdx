If you built a no-code agent in the workflows pillar (→ build-a-practical-agent), you've seen
an agent from the outside. Now you'll build one **in code**, and discover it's surprisingly
small. An agent is not a mystery; it's a **loop** around the tool calling you already learned
(→ structured-outputs-tools).

## The entire idea, in pseudocode

```python
messages = [system, user_request]
turns = 0
while turns < MAX_TURNS:                 # the cap is not optional
    turns += 1
    response = model(messages, tools=my_tools)
    if response.wants_a_tool:
        result = run_tool(response.tool, response.args)   # YOUR code runs it
        messages.append(response)        # what the model asked
        messages.append(result)          # what the tool returned
    else:
        return response.text             # final answer
return fallback_answer()                 # budget exhausted: fail loudly, not forever
```

That's a real agent: **model + tools + loop, with a cap.** The uncapped `while True` version is
the classic agent bug. A confused model can request tools forever, burning tokens until your
bill notices before you do. Everything else (memory, multiple agents, planning steps) is an
embellishment on this skeleton.

Notice what "memory" is here: the `messages` list. Every tool result is appended and resent on
the next turn, so a long run grows its context, its cost and its chance of losing the thread.
Real agents keep tool results short (return the three fields that matter, not a 5,000-line
JSON dump) and summarise or drop old turns when a run gets long.

## Agent or workflow?

Before you build an agent, ask whether you need one. If the steps are known in advance
(classify the email, look up the order, draft a reply), a **fixed workflow** of model calls is
cheaper, faster and far easier to test. An agent earns its cost when the path **can't be known
in advance**: open-ended questions, investigations, tasks where the next step depends on what
the last one found. Many production "agents" are workflows with one agentic step inside.

## Worked example: "Which arrives first, 1042 or 1077?"

One tool, `get_order_status(order_id) -> {status, eta}`, and `MAX_TURNS = 5`. A trace:

1. **Turn 1.** The model gets the question and the tool schema. It replies with a tool call:
   `get_order_status("1042")`. (Many APIs let it request both lookups at once as parallel
   tool calls; your loop should run every call in the response.)
2. **Your code** validates the id, runs the lookup and appends
   `{status: "shipped", eta: "Thu"}`.
3. **Turn 2.** The model asks for `get_order_status("1077")`. Your code returns
   `{error: "order not found"}`: a short, readable error, not a stack trace.
4. **Turn 3.** The model replies in text: "Order 1042 arrives Thursday. I couldn't find order
   1077; could you check the number?" No tool requested, so the loop returns.

Three turns, one graceful failure, and a cap that was never needed. Log every turn (tool,
arguments, result size, tokens) so that when a run *does* take 40 turns you can see why
(→ observability-tracing).

> 💡 **Try it:** Give any agent you can watch (ChatGPT with search, Claude Code, Cursor's
> agent, Gemini) a question that needs two lookups, such as "compare the latest release notes
> of two tools you use". Open the steps or tool-call view and count the turns: request, result,
> request, result, answer.

## Common failure modes

- **The run never finishes, or ends at a huge bill** → wandering loop with no stop signal →
  a max-turns cap, a per-run token or cost budget, and timeouts on each tool.
- **Tool calls against ids or paths that don't exist** → hallucinated arguments → validate
  arguments before executing and return a clear error.
- **The agent spirals after one tool fails** → a raw stack trace (or nothing) went back to the
  model → return short, structured errors it can act on ("order not found; ask the user for
  the order number").
- **Quality drops late in long runs** → context stuffed with verbose tool output → trim tool
  results and summarise old turns.
- **A mess made at machine speed** → write-access tools with no gate → start read-only, and put
  human approval on anything irreversible (→ reliability).

## Why write it yourself

Frameworks such as LangGraph, CrewAI, the OpenAI Agents SDK and the Claude Agent SDK are
useful, but if you start there, agents feel like magic and you can't debug them. Write the loop
once and you'll *see* that the model simply keeps asking for tools until it's done, and you'll
know exactly where guardrails, logging and cost caps belong (→ orchestration-frameworks).
Testing an agent also differs from testing one call: you check the final answer *and* the path
(did it call the right tools, in a sensible number of turns?) (→ evals-and-testing).
