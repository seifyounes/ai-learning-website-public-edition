LLMs are capable but ignorant of *your* world: your docs, your policies, last week's changes.
**RAG (Retrieval-Augmented Generation)** fetches the relevant information from your data and
hands it to the model, so the answer is grounded in your sources instead of guessed from
memory. It's one of the most widely used patterns in applied AI.

## The core idea and the two phases

Ask "what's our refund policy?" and the system pulls the actual policy text, then the model
answers from *that*. Grounded answers hallucinate far less (→ verification-and-grounding).

1. **Ingest (once, then on every document change):** split documents into **chunks**,
   **embed** each chunk into a vector (→ embeddings-vector-databases) and store it with its
   source and metadata.
2. **Query (every question):** embed the question, **retrieve** the most similar chunks,
   **augment** the prompt with them and **generate** an answer that cites them.

## Long context or RAG?

Context windows now hold hundreds of thousands of tokens, so a fair question is: why not paste
everything in? For a **small, stable corpus** (a 40-page handbook) that's often the right
call. It's simpler, nothing can be "not retrieved", and prompt caching makes the repeated
document cheap (→ cost-latency-caching).

RAG wins when the corpus **outgrows the window or keeps growing**, when sending everything on
every question costs too much or is too slow, when **different users may see different
documents** (you only retrieve what this user is allowed to read), and when you need precise
citations. Long inputs also have their own failure: models often use the start and end of a long
context better than the middle, and accuracy tends to drop as the input grows. A practical rule: start with long context while the
corpus is small, and move to RAG when size, cost or permissions force it. With large windows,
many teams now retrieve whole sections or documents rather than tiny chunks.

## Agentic and iterative retrieval

Classic RAG retrieves once, before the model sees the question. **Agentic retrieval** gives the
model a search tool (→ structured-outputs-tools) and lets it decide what to search, read the
results, and search again until it has enough. That handles multi-step questions ("which
plan includes priority support, and what does it cost annually?") that no single query
answers, and lets the model rewrite a query that missed. It's how coding agents explore a
repo with search commands. The price is more calls, more latency and behaviour that's harder
to test, so cap the number of searches and log every query it makes.

## Evaluate retrieval separately from generation

When a RAG answer is wrong, you need to know which half failed. Build a small labelled set:
20–50 real questions, each tagged with the chunk or document that contains the answer.

- **Retrieval: recall@k.** For what share of questions does a correct chunk appear in the top
  *k* results? If recall@5 is low, no prompt change will save you; fix chunking, search or
  reranking first. (MRR adds *how high* the first correct chunk ranks.)
- **Generation: groundedness (faithfulness).** Is every claim in the answer supported by the
  retrieved text? Usually scored by an LLM judge that you spot-check by hand.
- **Answer correctness and citations.** Does the answer match the reference, and does the
  cited source actually say it?

Open-source libraries such as Ragas implement these metrics, but a spreadsheet and a script
are enough to start (→ evals-and-testing).

## Worked example: the bot quotes last year's policy

An internal HR assistant says parental leave is 10 weeks. The current policy says 16. Diagnose
in order:

1. **Is the right chunk in the store?** Search the index for the 2025 policy. It's there, but
   so is the superseded 2023 version.
2. **Was it retrieved?** Print the top 5 chunks with scores for the question. The 2023 chunk
   ranks first; the 2025 chunk ranks fourth.
3. **Did the model use it?** It answered from the first chunk, as models usually do.

The root cause is at stage 1: stale documents in the corpus. Fix: remove or tag superseded
documents, store an `effective_date` in metadata and filter on it. Then add this question to
the labelled set so recall@k catches any return of the problem.

> 💡 **Try it:** Upload one long document to Gemini Notebook (formerly NotebookLM), a ChatGPT
> or Claude Project, or a Gemini Gem. Ask a question using a word the document never uses (for example "time off"
> when it says "leave"). Check whether the cited passage is the right one.

## Common failure modes

- **Answers miss half the rule** → chunks split mid-thought → chunk along headings and
  sections, with a little overlap.
- **The right passage never comes back** → the user's wording differs from the document's →
  **hybrid search** (vectors plus keyword/BM25) and **query rewriting**.
- **The answer ignores a retrieved chunk** → 20 chunks stuffed in and the middle gets
  overlooked → retrieve more, **rerank**, keep the best few.
- **Confidently cites an outdated document** → stale or duplicate content in the store →
  metadata filters and a re-ingest process for changed documents.
- **Grounded but still wrong** → the model misreads the retrieved text → measure
  groundedness and correctness, not just retrieval.

## Why RAG usually beats "just fine-tune it"

For "make it use my data," RAG lets you **update the data anytime** without retraining,
**cite sources** and **enforce permissions**. Fine-tuning changes *how* a model behaves; RAG
changes *what it knows right now* (→ fine-tuning-fundamentals). Next lesson opens the engine:
embeddings and vector databases.
