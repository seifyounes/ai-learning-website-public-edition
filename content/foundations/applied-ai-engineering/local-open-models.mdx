Frontier APIs are the default, but "we can't send this data to an API" and "this task is
too high-volume for frontier pricing" are sentences you will hear at real organizations,
and **an open model is often the answer both times**. Knowing when it is (and when it
isn't) is a cheap, practical differentiator.

## What Ollama actually does

One installer, then `ollama run <model>` downloads a quantized open model and serves it
locally, with an **OpenAI-compatible API** on localhost. That last part is the engineering
win: your app code doesn't care whether it's talking to a local 3B model or a frontier
API, because the request shape is the same. LM Studio does the same job with a desktop
interface and no terminal; llama.cpp is the engine underneath many of these tools; and
servers like vLLM are what teams use when many users share one GPU.

## What fits on your machine

A rough rule of thumb: at 4-bit quantization, weights take about half a byte per
parameter. So an 8B model needs around 4–5 GB just for weights, plus room for the context;
a 70B model needs 40 GB or more. A model that doesn't fit in GPU memory spills onto the
CPU and slows to a crawl. Laptops with plenty of unified memory (such as recent Apple
silicon Macs) run surprisingly large models; a typical office laptop is happiest at 1–4B.

## The honest quality picture

Small local models (3–8B) are genuinely good at narrow tasks such as classification,
extraction, summarizing short text and redaction. They are noticeably weaker than frontier
models at long multi-step reasoning, subtle tone and reliability on odd inputs. The pro
pattern is **tiering**: route the easy majority of calls to a small, cheap model and
escalate the hard ones to a frontier model, with evals telling you where the line sits
(→ choosing-models-providers covers the cost side).

## Worked example: a local redaction step

Say a small business wants AI-drafted replies to support emails, but the emails contain
names, phone numbers and addresses it would rather not send to a cloud provider. A hybrid
design:

1. **Local first.** A small model on the office machine rewrites each email with personal
   details replaced by placeholders (`[NAME]`, `[PHONE]`).
2. **Belt and braces.** A plain regular expression also catches phone numbers and email
   addresses, because a single miss is a leak, and code is more reliable than a model at
   fixed patterns.
3. **Cloud second.** Only the redacted text goes to a frontier model, which drafts the
   reply in a careful tone (the part small models do worst).
4. **Put it back.** Your code swaps the placeholders back in before a human reviews and
   sends the reply.
5. **Measure it.** Write 20 made-up emails stuffed with personal details and count misses.
   The number that matters is how many details slip through, not how fluent the output is.

Each model does what it's best at: the local one keeps data in-house on a narrow task, and
the frontier one handles judgment and tone.

> 💡 **Try it:** Check your machine's RAM (and GPU memory, if you have a GPU). Apply the
> half-a-byte-per-parameter rule and write down the largest 4-bit model you could run
> comfortably. That number tells you which families and sizes are worth downloading.

## The model landscape in 30 seconds

Open-weight families you'll see everywhere: **Llama** (Meta), **Gemma** (Google),
**Qwen** (Alibaba), **Mistral** and **DeepSeek**. Sizes run from about 1B to 100B+, and
4-bit quantization is the usual way to make them fit. Don't memorize benchmarks: check a
live leaderboard when choosing, then let *your* eval set make the final call, because a
leaderboard rank isn't your task.

## Common failure modes

- **Painfully slow responses** → the model is too big for GPU memory and spills to the
  CPU → pick a smaller size or a more aggressive quantization, and watch tokens per second.
- **Broken JSON** → small models are less reliable at strict formats → use
  schema-constrained output, validate, and retry once.
- **Details from long documents go missing** → local runtimes often default to a modest
  context length → set the context length explicitly, or chunk the document.
- **Dev passes, production fails** → your dev loop used a different model from production
  → run evals against the production model before release.
- **Quality worse than the leaderboard suggested** → leaderboards test other tasks, and
  your quantization level differs → score candidates on your own eval set.

## Where this fits your career

For an applied-AI engineer, local models are less about ideology and more about three
practical wins: **privacy** for clients and enterprises, **cost** at volume, and a **free
dev loop** while you build. Being able to say "I ran the same eval set against a local
model and a cloud one; here's the quality gap and the cost difference" is a strong
portfolio point that takes one evening.
