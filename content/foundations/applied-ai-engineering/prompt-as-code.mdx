When a prompt lives inside a real app, it stops being a throwaway message and becomes
**product code**. If the prompt is wrong, the feature is wrong, and unlike a bug in a function,
a bad prompt rarely throws an error: it just quietly produces worse output. So you manage
prompts with the same discipline as any critical code. That is what "prompts as code" means.

## The problem with inline prompts

Pasting prompt strings into functions works for a demo and rots fast. The prompt gets copied
to three places, the copies drift, and nobody can say which wording produced last Tuesday's
bad output.

## The fixes

- **Centralise**: keep prompts in one module or folder, named and importable, not sprinkled
  through the logic.
- **Templatise**: define the stable structure with **slots** for the dynamic parts (user
  input, retrieved context, tone). Fill slots; don't concatenate strings.
- **Version**: every change creates a new version you can compare and roll back to. When an
  "improvement" drops quality, you'll be glad you can revert.
- **Tool up (optional)**: prompt platforms such as Langfuse, LangSmith, PromptLayer or
  Braintrust add versioning, tracing and side-by-side comparison so you measure prompt
  changes instead of guessing. A folder of prompt files in git is a perfectly good start.

## A prompt version is more than the text

Practitioners learn this the hard way: the same words behave differently on a different model
or at a different temperature. So a "prompt version" should pin the **template, the model
name and the key parameters together**. Swapping the model under an unchanged template is a
new version and goes through the same gate as a wording change. Store them as one record:

```yaml
id: ticket-summary
version: 3
model: a-small-fast-model
temperature: 0.2
max_tokens: 250
template: |
  Summarise the support ticket below for an agent in 3 bullets: problem, what the
  customer wants, urgency (low/medium/high). Use only facts in the ticket.
  <ticket>{{ticketText}}</ticket>
```

Notice the user's text sits inside delimiters, in its own slot. That keeps instructions and
data apart, which also makes the prompt easier to defend against injected instructions
(→ llm-security-prompt-injection).

## Rolling out a prompt change (the production half)

Editing the prompt is the easy part; **shipping the edit safely** is the skill. The pattern:

- **Decouple prompts from code deploys.** Store prompts in a registry or config (a prompt
  manager, or a versioned database table) that the app reads by label, such as
  `production -> v3`. Updating a prompt then doesn't require rebuilding the app, and a bad
  one rolls back in seconds instead of a release cycle.
- **Gate every new version on the eval set** (→ evals-and-testing). Run v4 and v3 on the same
  test cases, compare, and only then move the "production" label. No eval pass, no rollout.
- **Keep the version in your cache key and your logs.** If cached output is keyed by
  `ticket-summary:v3:<input-hash>`, a prompt change can never serve stale output, and logged
  versions let you trace any bad output to the exact prompt that produced it.
- **Roll out gradually when the stakes are high.** Send a small share of traffic to the new
  version, or run it in "shadow" (generate but don't show) and compare, before switching
  everyone.

Version, eval gate, instant rollback: that is the full answer to "how do you ship a prompt
change without breaking production?"

## Worked example: v3 to v4 of a ticket summariser

Support agents complain that summaries miss the order number. Here is the change, step by step.

1. **Reproduce.** Pull five real tickets where the order number was missed from the logs.
   Because each log line carries `ticket-summary:v3`, you know exactly which prompt failed.
2. **Edit as a new version.** Copy v3 to v4 and add one instruction: "Start with the order
   number if the ticket contains one." Never edit v3 in place.
3. **Extend the eval set.** Add the five failing tickets as test cases, alongside the existing
   ones, so the fix is checked and future versions can't regress on it.
4. **Compare.** Run v3 and v4 over the whole set. v4 should fix the five without making the
   others worse (longer summaries, lost urgency labels).
5. **Promote.** Move the `production` label to v4. New cache keys mean no stale summaries.
6. **Watch and keep the exit open.** Check the next day's logs. If something regressed that
   the eval set missed, move the label back to v3 and add that case to the set.

> 💡 **Try it:** Take a prompt you reuse often (in code, a saved chat prompt or a custom
> GPT/Gem/Project instruction). Rewrite it with its variable parts as named slots, add a
> `version: 1` line and a one-line changelog, and save it in a file or doc you'd find again.

**Is a registry overkill?** For a solo project, prompt files in git plus a version constant
are enough. A registry earns its keep when non-engineers edit prompts or you need rollback
without a deploy.

## Common failure modes

- **Quality drops and nobody knows why** → a prompt was edited in place with no version →
  never edit a live version; create a new one and log the version with every output.
- **Users still see old output after a fix** → the cache key ignores the prompt version →
  include the version (and model) in every cache key.
- **A "small wording tweak" breaks a downstream parser** → no eval or snapshot test on the
  output format → gate every version on the eval set, including format checks.
- **Same prompt, worse results after a model upgrade** → the model wasn't part of the
  version → pin model and parameters with the template and re-run evals on any model change.
