Free-text answers are great for humans and terrible for code. The moment you build AI into an
app, you need outputs your program can **trust and parse**, and you need the model to **do
things**, not just talk. Structured outputs and tool calling are the two techniques that make
a model a real software component.

## Structured outputs: JSON you can rely on

Ask a model for "the sentiment and topics" and you get a paragraph, different every time.
Instead, demand a **schema**: `{ "sentiment": "positive", "topics": ["billing"] }`. There are
three levels of strength, and it pays to know which one you're using:

- **Asking in the prompt** ("reply in JSON"): usually works, sometimes doesn't. Fine for a
  prototype, not for production.
- **JSON mode**: the API guarantees syntactically valid JSON, but not *your* fields.
- **Schema-enforced output**: you pass a JSON Schema and the provider constrains generation so
  the reply matches it. OpenAI calls this Structured Outputs, Gemini uses a response schema,
  and on any API with tool calling you can get the same effect by defining one tool whose
  input schema is your output shape.

In code, you usually define the shape once with a validation library (Pydantic in Python, Zod
in TypeScript) and let it produce the schema and parse the reply.

**Schema design is prompt design.** Use enums instead of free strings where the set is known
(`"shipping" | "refund" | "other"`). Give the model a legal way to say "I don't know" (a
nullable field or an `"unknown"` value), or it will invent something to fill the slot. Field
order matters too: models generate fields in order, so a short `reasoning` field placed
*before* the `answer` field gives the model room to work before it commits.

## Tool / function calling: the model acts

You describe functions the model may use, each with a **name, a description and a JSON
Schema for its arguments**, for example `get_order_status(order_id)`. When the model decides
it needs one, it returns the **function name and arguments as JSON**. It does *not* run the
function. **Your code does**, then sends the result back as a tool message so the model can
continue.

That loop (model requests a tool, you run it, feed the result back, repeat until it answers)
is how **agents** work under the hood. The no-code agent from the workflows pillar
(→ build-a-practical-agent) is this pattern with a visual wrapper.

Three practitioner details. The tool **description is a prompt**: say when to use the tool
and when not to, because that's all the model sees. You can control the choice with a
"tool choice" setting (let the model decide, force a tool, or forbid tools). And when a tool
fails, return the error *as the tool result* ("order not found") instead of crashing, so the
model can recover or ask the user.

## Worked example: triage, then look up the order

A customer writes: "Where is order 4471? It was due Monday."

1. **Classify with a schema.** First call, schema-enforced:
   `{category: "shipping" | "refund" | "other", priority: 1-3, order_id: string | null}`.
   The reply parses straight into an object: shipping, priority 2, order `"4471"`.
2. **Validate meaning.** Before trusting `order_id`, check it appears in the email text. It
   does, so continue. (If the model had returned `"4417"`, valid JSON, you'd stop here.)
3. **Offer a tool.** Second call, with the email and a `get_order_status` tool. The model
   replies with a tool call: `{"name": "get_order_status", "arguments": {"order_id": "4471"}}`.
4. **Run it yourself.** Your code checks the id exists in your data, calls your database and
   gets `"in transit, delayed at depot"`.
5. **Return the result.** You append the tool call and its result to the messages and call
   again. The model now writes the reply using a real status, not a guess.

Every arrow in that flow is structured, so every step can be logged, tested and checked.

> 💡 **Try it:** In any chat assistant, paste a short email and ask: "Return only JSON with
> keys sender, intent, deadline (ISO date or null)." Then send an email with *no* deadline and
> see whether it returns null or invents a date. That's why the null option matters.

## What the schema does NOT guarantee

Structured output guarantees the **shape**, not the **sense**. Three problems survive a
perfectly valid schema:

- **Hallucinated arguments**: the model calls `get_order_status("ORD-12345")` with an id it
  invented. Valid JSON, wrong world.
- **Wrong tool choice**: it confidently picks `send_email` when the task needed
  `create_draft`.
- **Schema-valid nonsense**: a support bot returns a flawless `{answer, quote}` where the
  "quote" is something the customer never wrote. Production systems add a
  **must-appear-verbatim check on top of the schema**. The schema checks the envelope; the
  guardrail checks the letter.

Rule: validate **meaning** after you've validated shape, and validate tool arguments **before**
you execute anything that writes, deletes or sends.

## Common failure modes

- **Parsing crashes on some replies** → prompt-only JSON, or a reply truncated at `max_tokens`
  → use schema-enforced output and check the finish reason before parsing.
- **Fields filled with plausible inventions** → no legal "unknown" value in the schema → make
  fields nullable or add an explicit unknown option.
- **The model never calls your tool, or calls it at the wrong time** → a vague tool
  description → state what the tool does, when to use it and when not to.
- **One bad lookup kills the whole conversation** → tool errors raised as exceptions → return
  them as tool results the model can read and react to.

Together, tool calling lets the model *act* and structured outputs make every step
**machine-readable**. That's the backbone of every serious AI feature, and of the agent you'll
build in code later in this pillar (→ build-agent-in-code). Next: giving the model *your*
data with RAG (→ rag-fundamentals).
