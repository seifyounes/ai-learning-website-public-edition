    a: "First open a few traces to confirm the time is in the model call, not your retrieval. Then a timeout so calls fail fast, a fallback to a faster model or second provider, and streaming so users see progress. Anything the user isn't watching moves to an async job."
  - q: "One customer's script calls your AI endpoint in a tight loop, and your daily bill triples overnight. Which boxes should have stopped it?"
    a: "The gateway, with a per-user rate limit and budget enforced server-side; the cache, which serves repeated identical inputs without a model call; and observability, alerting when request rate or cost per user changes sharply."
  - q: "A teammate wants semantic caching on a 'where's my order?' chatbot to cut costs. What's the risk, and where would semantic caching be safe?"
    a: "Near-duplicate questions from different users would get each other's (or stale) order answers, because the right answer depends on who's asking and when. Use it for generic, non-personal questions such as FAQs; personal answers need exact keys that include the user, and a short expiry."

System design questions for LLM apps are a common part of applied-AI interviews, and
they're where "I've called an API" gets separated from "I've shipped a system". More
importantly, this is the lesson that keeps your feature standing when real traffic, real
outages and real bills arrive.

## The core mindset: you don't control the model

Classic system design assumes your components obey you. Here, the smartest component is a
**remote black box** that times out, rate-limits you, drifts between versions and
occasionally emits confident nonsense. Everything in LLM architecture follows from
designing around that one fact.

## The reference architecture

Almost every serious LLM feature converges on the same boxes:

```diagram
client
  │
  ▼
gateway
  auth, rate limits,
  key stays server-side
  │
  ▼
cache check
  exact / semantic
  │
  ▼
model call
  timeout + retry + budget
  │
  ▼
fallback chain
  retry → cheaper model
  → canned response
  │
  ▼
output validation
  schema, guardrails
  │
  ▼
observability
  traces, cost, quality
```

You rarely need all of it on day one. You need to be able to **draw it and say which boxes
you'd add first, and why**. For most first versions the answer is the same three: a
timeout with a fallback, output validation, and basic tracing.

## Failure modes and their standard answers

- **Provider outage or timeout** → timeouts, retries with exponential backoff, a second
  provider or model as fallback, and a circuit breaker so you fail fast instead of piling
  up waiting requests.
- **Latency tails** → streaming (perceived speed), smaller models for easy cases, and
  async processing for anything the user isn't watching.
- **Bad outputs** → schema validation, guardrails and a safe default response. Never let
  raw model output reach users or databases unchecked.
- **Cost blowups** → per-user budgets, caching, model routing (cheap model first, escalate
  the hard cases) and alerts on cost per task.

## Worked example: 10,000 summaries a day

Here's the classic drill done out loud. A helpdesk app adds "summarize this support
thread", and it reaches 10,000 calls a day. The prices are **made-up round numbers**; in
real life you'd read the provider's price page.

1. **Tokens.** A thread plus instructions is about 3,000 input tokens; a summary is about
   300 output tokens. Per month (×30): 300,000 calls, 900 million input tokens and 90
   million output tokens.
2. **Bill.** Pretend $1 per million input and $4 per million output: $900 + $360 = about
   **$1,260 a month**, or roughly $0.004 per summary. That last number is your cost per
   task, and it's the one to watch.
3. **Concurrency.** 10,000 a day averages about 0.12 requests per second, but traffic
   clusters. If the busiest hour carries 15% of the day, that's 1,500 calls in an hour, or
   about 0.4 per second. At an 8-second p95 latency, about **3–4 calls are in flight** at
   peak (requests per second × seconds each). Rate limits aren't your first problem.
4. **What breaks first?** More likely the latency tail and provider hiccups. So: a 15-second
   timeout, one retry with backoff, then a cheaper fast model, then a canned "summary
   unavailable, here's the thread".
5. **Cheap wins.** The instruction block is identical on every call, so provider prompt
   caching on that prefix cuts input cost. Caching each thread's summary until a new
   message arrives skips repeat calls entirely.

That's a whole design answer: numbers shown, a bottleneck named, a fallback chain ordered.

> 💡 **Try it:** Pick an AI feature you use every day (an email assistant, a meeting
> summarizer). Sketch the six boxes on paper and, next to each, write what you'd see as a
> user if that box failed. Five minutes, and you'll start spotting missing boxes in every
> AI product you touch.

## Common failure modes

- **Retries make the outage worse** → every client retries instantly and in sync →
  exponential backoff with random jitter, a retry cap and a circuit breaker.
- **The fallback quietly runs for days** → nothing alerts on fallback rate → chart it and
  alert when it jumps (→ observability-tracing).
- **The cache serves one user another user's answer** → the cache key leaves out the user
  or context → key on everything that changes the answer; keep semantic caching for
  non-personal questions.
- **Outputs change overnight with no deploy** → the code points at a floating model alias
  that the provider upgraded → pin model versions and rerun evals before you move.
- **Cost per task creeps up** → agent loops or retries multiply calls → track cost per task
  and cap steps per request.

## The 10,000-requests-a-day question

Interviewers like it because it forces arithmetic: requests × tokens per request × price
per token = the monthly bill; requests per second × latency = how many calls are in flight
when things clog. Practice the estimate until it's reflexive. Engineers who budget tokens
*before* the bill arrives are the ones teams trust with production.
