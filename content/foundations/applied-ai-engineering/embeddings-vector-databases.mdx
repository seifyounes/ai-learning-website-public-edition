The last lesson treated retrieval as a box. Here it is opened: **embeddings turn meaning into
numbers, and vector databases make those numbers searchable.** Together they're the engine
behind RAG, semantic search, recommendations and duplicate detection.

## Embeddings: meaning as math

An **embedding model** converts a piece of text (or an image) into a **vector**: a fixed-length
list of numbers, typically several hundred to a few thousand of them. The crucial property:
**similar meanings produce nearby vectors.** "Cancel my subscription" and "how do I end my
plan" land close together even though they share almost no words. The model learned that
geometry during training.

Two subtleties practitioners learn early:

- **"Similar" means what the model learned it to mean.** Embeddings mostly capture *topic*.
  "This charger works great" and "this charger stopped working" can sit close together,
  because both are about a charger working. Don't expect embeddings alone to separate
  opposite opinions or negations.
- **Exact identifiers are a weak spot.** Error codes, SKUs, invoice numbers and rare names
  carry little "meaning", so a vector search may miss `ERR-4012` that a keyword search finds
  instantly. That's why production retrieval is usually **hybrid**.

## Vector databases: search by similarity

A normal database finds exact matches. A **vector database** finds the **nearest** vectors to a
query vector, using a similarity measure. Three operations:

1. **Add**: embed your chunks and store each vector with its text and metadata (source, date,
   owner).
2. **Query**: embed the question and find the nearest stored vectors, optionally filtered by
   metadata ("only documents this user can see", "only 2025 policies").
3. **Index**: the structure that keeps search fast at scale.

Comparing a query against every stored vector (exact search) is fine for thousands of items.
Beyond that, databases use **approximate nearest neighbour (ANN)** indexes such as HNSW, which
are much faster and occasionally miss a true nearest neighbour. That small recall loss is a
tunable trade-off, and one more reason to measure recall@k (→ rag-fundamentals).

**Cosine or dot product?** Cosine compares direction only; dot product also rewards vector
length. Many embedding models return normalised vectors, which makes the two equivalent, so
cosine is the safe default.

## Choosing an embedding model

Hosted options (from OpenAI, Google, Cohere, Voyage and others) need only an API call. Open
models (the sentence-transformers family, BGE, E5, Nomic and others) run locally for free.
Public leaderboards such as MTEB are a reasonable shortlist, but test two or three candidates
on *your* data: a model that tops a leaderboard can still lose on your domain's vocabulary.
Check three things on the model card: the **maximum input length** (longer text is often
silently truncated), whether it expects **different prefixes or input types for queries and
documents**, and the **vector size** (bigger costs more storage).

Your choice is a **commitment**: vectors from different models live in different spaces and
can't be compared. Switching models means re-embedding everything, so record which model made
each vector.

## Worked example: an FAQ that understands paraphrases

A small online shop has three FAQ entries: "Tracking your delivery", "Returns and exchanges"
and "Changing your password".

1. **Ingest.** Embed each entry's title and answer with one model and store them in Chroma
   with metadata `{id, model}`.
2. **Query.** A customer types "where's my parcel". Embed it with the *same* model.
3. **Rank.** The store returns all three with similarity scores. "Tracking your delivery"
   comes first, well above the others, despite sharing no words with the question.
4. **Set a floor.** Now try "do you sell gift cards?", which no entry covers. The top match
   still comes back, just with a lower score. Similarity scores aren't probabilities and their
   scale varies by model, so you pick a threshold *for this model* by looking at real matches
   and non-matches, and below it you answer "I couldn't find that; here's how to contact us."
5. **Patch the gap.** Add keyword search alongside so an order number typed into the box also
   matches exactly.

## You don't build it from scratch

- **Chroma** or **LanceDB**: easiest start, runs locally.
- **pgvector**: add vectors to Postgres you already run (most hosted Postgres providers
  support it).
- **Pinecone, Weaviate, Qdrant, Milvus**: dedicated or managed, built for scale.

Start with the database you already have; add a dedicated service only when scale or features
demand it.

## Common failure modes

- **Search results become nonsense after an "upgrade"** → old and new vectors from different
  models mixed in one index → store the model name per vector and re-embed everything on a
  switch.
- **Long documents match poorly** → text beyond the model's input limit was truncated → chunk
  to fit the limit.
- **Exact codes and names aren't found** → pure vector search → add keyword (BM25) search and
  merge the results.
- **Irrelevant answers to out-of-scope questions** → no similarity floor → set a per-model
  threshold and answer "not found" below it.
- **Filtered queries return too few results** → the filter is applied after the approximate
  search → use the database's pre-filtering or raise the candidate count.
