A feature that works in a demo can still be too slow or too expensive to ship. In production,
**cost and latency are features.** The good news: a handful of well-known levers make a large
difference, and you can estimate most of them before you write any code.

## Where the bill and the wait come from

Every call is billed as **input tokens × input price + output tokens × output price**. On the
major providers, output tokens cost several times more than input tokens, so a verbose reply
can cost more than a long prompt.

Latency has two parts you should measure separately:

- **Time to first token (TTFT)**: how long before anything appears. It grows with prompt
  length and is what prompt caching helps most.
- **Generation time**: roughly proportional to how many tokens the model writes. For most
  features, **output length dominates total time**, so bounding the output is a speed lever as
  well as a cost lever.

Agents multiply both: ten turns means ten bills and ten waits.

## Prompt caching: the biggest easy win

If you send the **same context repeatedly** (a long system prompt, a reference document, an
agent's growing history), **prompt caching** lets the provider reuse the already-computed
state for that prefix instead of reprocessing it. OpenAI, Anthropic and Google all support it.
Cached input tokens are billed at a steep discount, and time to first token drops because the
prefix isn't recomputed. Some providers cache eligible prefixes automatically; others need you
to mark the cache point in the request.

Read the fine print before you count the savings:

- **The static content must be a PREFIX.** Caching matches from the start of the prompt; one
  changed early token invalidates everything after it. Stable instructions, examples and tool
  definitions at the top, variable data at the bottom.
- **Cache writes can cost extra.** On some providers, writing a cache entry costs more than
  normal input, so you profit only when the prefix is re-read enough before it expires.
- **Minimums and expiry exist.** Prefixes below a minimum length don't cache, and entries expire
  after a time-to-live, so a low-traffic app may rarely hit the cache. Check your provider's
  current numbers before projecting savings.

## The other levers

- **Right-size the model.** Use a small, cheap model for easy steps and reserve the flagship
  for hard ones (→ models-and-effort). This is usually the largest cost driver. A **cascade**
  goes further: try the cheap model first and escalate only when a check fails.
- **Trim tokens.** Remove dead instructions, shorten retrieved context and set a bounded output
  length.
- **Stream.** Streaming makes the feature *feel* fast; perceived latency often matters more
  than total time.
- **Parallelise.** Independent calls (classify and summarise the same ticket) can run at once
  instead of one after another.
- **Batch.** Work that can wait (nightly reports, re-tagging a backlog) can go through the
  providers' batch APIs, which trade a slower turnaround for a lower price.
- **Cache responses.** An exact-match cache keyed on (input hash, prompt version) avoids paying
  twice for repeat requests. A **semantic cache** also reuses answers for *similar* questions,
  but tune it carefully: "cancel my order" and "cancel my subscription" are similar sentences
  with different answers.
- **Skip the call.** Empty inputs, duplicates and questions a rule can answer need no model.

## Worked example: pricing a support-reply drafter

Use made-up round prices for the arithmetic: input $1 per million tokens, cached input $0.10
per million, output $4 per million. Each call sends a 3,000-token static prefix (instructions
plus a policy document), a 300-token ticket, and gets a 250-token reply.

1. **Baseline.** Input 3,300 tokens ≈ $0.0033; output 250 tokens = $0.001. About **$4.30 per
   1,000 calls**.
2. **Add prompt caching.** The prefix is billed at the cached rate: $0.0003, plus $0.0003 for
   the ticket and $0.001 for the reply. About **$1.60 per 1,000 calls**, ignoring the
   occasional cache write.
3. **Skip 30% of calls** that are duplicates or answerable by a canned reply: about **$1.12**
   per 1,000 incoming tickets.
4. **Look at what's left.** Output is now the biggest line item, so the next lever is a
   shorter reply limit, not more caching.

The exact prices change; the method doesn't. Plug in your provider's current numbers.

> 💡 **Try it:** Open the pricing page of a provider you use and find three numbers for one
> model: input, cached input and output price per million tokens. Which is highest, and by how
> much? That ratio tells you whether to trim the prompt or the reply first.

## Common failure modes

- **Caching is on but the hit rate is near zero** → something dynamic (a timestamp, user name,
  request id) sits near the top of the prompt → move all variable content below the static
  prefix.
- **A sudden bill spike** → an agent looping or outputs with no length cap → per-run budgets,
  `max_tokens` on every call, and cost alerts.
- **A small model and still slow** → long outputs or calls made one after another → bound the
  output, stream, and run independent calls in parallel.
- **The semantic cache gives a confidently wrong answer** → its similarity threshold is too
  loose or it isn't scoped per user → raise the threshold, scope it, or use exact-match only.
- **Nobody knows which feature costs what** → token usage isn't logged per request → log
  tokens, model and feature name on every call (→ observability-tracing).

Measure cost per request and latency the way you measure quality (→ evals-and-testing). A
caching change or a cheaper model on the easy path can cut the bill sharply, and your evals
tell you whether quality held.
