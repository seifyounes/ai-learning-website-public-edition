With a spec in hand, you choose what to build it on. Don't chase the newest framework.
Choose deliberately, and bias toward tech that AI knows well, because AI is now your
co-builder and its strengths become your strengths.

## The layers you're actually choosing

A "stack" sounds like one decision. It's really five or six small ones:

- **Frontend**: what the user sees (a web framework, a mobile framework, or both).
- **Backend and database**: where data lives and server-side logic runs.
- **Auth**: how people sign in. Usually bundled with the backend.
- **Hosting**: where the web app runs, or how mobile builds reach the stores.
- **Third-party services**: payments, email, analytics, AI model APIs.

Decide them in that order, because each one narrows the next. If you don't code yet, your
"stack" is mostly the builder you pick (Lovable, Bolt, Replit and similar). The one question
that matters there is whether you can export the code and take it elsewhere later.

## Web

For most apps: **Next.js + Tailwind.** It's a common default for good reasons: a large
ecosystem, good docs, and AI tools generate it fluently. It's not the only sensible choice.
SvelteKit, Remix / React Router, Django or Rails are all fine if you already know one well,
because the stack you know beats the stack you're learning while also learning to ship.
Pair it with a simple backend (→ backend-database-with-ai).

## Mobile (iOS + Android)

Two strong cross-platform routes:

- **React Native / Expo**: one TypeScript codebase that can target **web, iOS and Android**.
  The most code sharing if you also have a web app.
- **Flutter**: Dart, one rendering engine, a polished and consistent UI on both platforms.

Choose by priorities: maximum code sharing with web → Expo; the most consistent, polished
native feel → Flutter. And ask first whether v1 needs to be a store app at all. A responsive
web app often covers it.

## The AI-era rule: pick boring, popular tech

Here's what's new: **the more popular a framework, the better AI is at it.** Next.js,
React Native and Flutter have huge amounts of public code and documentation, so Claude Code,
Cursor, Codex, Copilot and v0 produce far better results with them than with an obscure new
framework. "Boring and proven" isn't a compromise; it's a multiplier on your AI help. The
same logic says *pin your versions*. A framework that changed last month may be newer than
much of what the model learned from.

## Worked example: the fitness-studio booking app

Take the task's hypothetical: clients book classes, the studio manager checks the day's
schedule. Walk the layers.

1. **Frontend.** Clients book from their phones; the manager glances at a schedule. Both work
   in a responsive web app, so v1 is **web-only**. Native apps are a non-goal until there's a
   reason, such as a store presence or device features the web handles poorly.
2. **Backend.** Accounts, bookings and class capacity mean a real database with per-user
   access rules. A backend-as-a-service such as Supabase or Firebase covers database, auth and
   storage in one place.
3. **Auth.** Bundled with the backend. Email magic links keep sign-up short.
4. **Hosting.** Vercel, Netlify or Cloudflare Pages: push to GitHub and it deploys.
5. **Services.** Payments via a mainstream provider (Stripe is the usual default), if the
   studio wants online payment at all. Ask before you build it.

Write each choice as one line in `docs/decisions.md`: what you picked, what it beat, why.
That file is what stops the next session from quietly swapping your database.

> 💡 **Try it:** Ask any assistant: "For [your app in one line], list the layers of the stack
> and, for each, the most popular option and one serious alternative, with one sentence on
> when the alternative wins." Compare its picks with yours. Any layer where you can't say why
> you chose differently is a decision you haven't made yet.

## Common failure modes

- **AI-generated code uses APIs that no longer exist** → the framework moved faster than the
  model's training data, or the project never states its version → pin versions in the
  instruction file and feed the agent current docs.
- **Building web *and* native apps for v1** → two targets double the work before anyone has
  used the product → ship one target first and make the second a recorded later decision.
- **Picking by benchmark or hype** → speed charts rarely decide whether a small app succeeds →
  weigh your skills, AI support and ecosystem first.
- **A layer swapped mid-build with no record** → the change happened in a chat → write it into
  the decisions file with the reason, so future sessions don't revert it.

## Decide with AI, not by AI

Ask an AI to lay out trade-offs and even argue against your pick; it's good at catching blind
spots. But the decision is yours: weigh your skills, the project's needs and how well AI
supports the tech. With the stack set, you can scaffold the whole thing in minutes.
