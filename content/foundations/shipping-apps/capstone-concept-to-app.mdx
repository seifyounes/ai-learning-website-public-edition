This is the one that proves it all clicked: take an idea **from concept to a deployed app** by
yourself. Not a huge app, but a *small, complete* one, shipped end to end. Expect it to take
several sessions over a week or two. The video runs about three hours, but you only need its
AI-feature and deployment chapters up front (under 40 minutes); your own build will take longer
than watching someone else's.

## The full run

Follow the pillar in order:

1. **Spec**: define a tiny, genuinely useful app. Ruthlessly small (→ idea-to-spec).
2. **Stack**: for example Next.js for web or Expo for mobile, plus Supabase or Firebase for
   the backend (→ choosing-your-stack).
3. **Scaffold**: generate a skeleton with an AI builder (v0, Lovable, Bolt) or your coding
   agent, then move into Claude Code, Cursor, Codex or Copilot for the real work.
4. **Build**: frontend and backend, wired to your spec, with owner-only access rules. Add
   **one AI feature** (smart search, auto-tagging, a summary) using the Applied AI engineering
   pillar (→ calling-an-llm-api).
5. **Test**: have AI write tests for the key flows, and read what they assert.
6. **Deploy**: Vercel or a similar host for web, EAS or a store test track for mobile. Get a
   public link.
7. **Feedback**: show three real people, gather input, make one improvement.

## Worked example: pacing a reading-list app

Here's how the task's suggested idea (paste a link, get a one-line summary) breaks into
sessions. Each session ends with a commit and a deploy, so the public link always works.

1. **Session 1, about an hour:** spec interview, scaffold, one screen that lists saved links,
   deployed to a public URL. Ugly is fine; live is the point.
2. **Session 2:** sign-in and a database table for links, with owner-only access rules. Run the
   two-user test from the backend lesson (→ backend-database-with-ai) before moving on.
3. **Session 3:** the AI feature. A server route receives the link, fetches the page text,
   asks a model for a one-line summary, and saves it. The API key lives only on the server.
   Add a sensible limit (a cap on text length and on requests per user) so a long page or a
   busy user can't run up your bill.
4. **Session 4:** tests for "save a link" and "summary appears", plus the secret scan from the
   deploy lesson. Read every assertion.
5. **Session 5:** three people use it. Cluster what they say, ship one improvement, write down
   what you learned.

Each session has one goal. If a session's goal isn't done, the next session finishes it rather
than starting something new.

> 💡 **Try it:** Before your first session, write your capstone's non-goals list: five things
> this app will *not* do in v1. Keep it at the top of the spec. It's the list you'll lean on
> every time a good idea shows up mid-build.

## Common failure modes

- **Scope creep halfway through** → every new idea feels small → park it in the non-goals list
  and finish the current milestone first.
- **Deploying only at the end** → environment-variable, build and secret problems all surface
  at once → deploy a walking skeleton in session 1 and keep it deployed.
- **The AI feature calls the model from the browser** → the key has to ship to the client →
  move the call to a server route or function.
- **Never showing anyone** → it's never quite "ready" → book the three conversations when you
  start, not when you finish.
