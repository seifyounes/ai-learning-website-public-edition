A finished app on your laptop helps no one. **Shipping**, putting it where real people can use
it, is the whole point, and it's never been easier. The web half takes minutes. The mobile
half takes days of calendar time, mostly waiting on gates you can plan around.

## Web: deploy on Vercel (or a similar host)

For a Next.js app, deployment is almost trivial. Netlify and Cloudflare Pages work the same
way:

1. Push your code to **GitHub**.
2. Import the repo into **Vercel**. It detects the framework, builds and deploys.
3. Set **environment variables** (your secrets) in the dashboard, server-side.
4. Add a **custom domain** when you're ready.

From then on, **every push deploys automatically**, and each branch gets a **preview URL**,
handy for showing work in progress before it goes live. If a release misbehaves, hosts like
these let you put a previous deployment back in a click or two, so a bad deploy is an
inconvenience, not a crisis.

## Worked example: classifying your environment variables

The most common first-deploy problem is environment variables. Before your first deploy, list
every variable your app reads (ask your agent: "list every environment variable this code
reads, and where") and sort them:

| Variable | Public or secret? | Where it goes |
| --- | --- | --- |
| Backend URL | Public | Client is fine (`NEXT_PUBLIC_` on Next.js) |
| Publishable / anon key | Public, by design | Client is fine; access rules protect the data |
| Service-role / admin key | **Secret** | Server only, never prefixed |
| AI model API key | **Secret** | Server only, used inside a server route |
| Payment secret key | **Secret** | Server only |

The prefix is the trap. On Next.js, `NEXT_PUBLIC_` means "copy this value into the browser
bundle"; Expo's `EXPO_PUBLIC_` does the same for the app bundle. Anything with that prefix is
readable by anyone who opens your app. Then add each variable in the host's settings, for the
Production environment as well as Preview, and redeploy.

> 💡 **Try it:** Open your deployed site, open DevTools, and search the loaded JavaScript
> (the Sources panel's search) for the first few characters of one of your secret keys. You
> want zero hits. If you find one, rotate that key today.

## Mobile: the app stores

Mobile is more involved because the stores gatekeep. Two paths, same shape:

- **Flutter:** `flutter build appbundle` for Android (signed with your upload keystore) and
  an iOS archive for the App Store. iOS builds need macOS; on Windows or Linux, a cloud CI
  service such as **Codemagic** can build, sign and push to TestFlight for you. Ship to
  **TestFlight** and **Play internal testing** first, then promote to production.
- **React Native / Expo:** **EAS Build** produces the binaries and **EAS Submit** uploads
  them: the same build → sign → submit pipeline with different tooling.
- Either way you need an **Apple Developer** account ($99/yr), a **Google Play** account
  ($25 one-time), and to pass each store's **review**. Plan for review time; it's not
  instant like the web. One more Google gate: a brand-new **personal** Play Console account
  must run a **closed test with at least 12 testers for 14 continuous days** before it unlocks
  production access (organization accounts are exempt).

Two housekeeping rules save real pain. Every upload needs a **higher build number** than the
last one, so bump it before each build. And **back up your signing key and its passwords**
somewhere safe outside the repo. Losing them turns a routine update into a recovery process.

## Common failure modes

- **Works locally, errors in production** → environment variables were never added on the
  host, or only for Preview → add them for Production and redeploy.
- **A secret is readable in the browser** → it was given a public prefix → rotate it and move
  the code that uses it to a server route or function.
- **"All my data disappeared"** on a preview URL → each preview is a different origin with
  empty browser storage → test on the production URL.
- **The store rejects your upload** → the build number wasn't bumped → increase it and rebuild.
- **Play won't let you publish to production** → the closed-test requirement for new personal
  accounts → start the 14-day test early, in parallel with your final polish.

## "Done" beats "perfect"

The hardest part of shipping is letting go. A live v1 that real people touch teaches you more
in a day than another week of polishing in private. Ship it, then use the next lesson to make
it better with real feedback.
