A frontend looks nice; a **backend** makes it real: saving data, signing users in, storing
files. The good news is that you no longer build these from scratch, and AI handles most of
the wiring. The part it can't own for you is access control, so that's where this lesson
spends its time.

need only about 40 minutes of it now, and the task asks you to stand up a real backend and
attack it. Plan for two or three sittings:

## Use a backend-as-a-service

Don't hand-roll auth and a database. Pick a platform that bundles them:

- **Supabase**: a Postgres database plus auth, storage and instant APIs. Open source,
  developer-friendly, and well known to AI tools. A strong default for web apps.
- **Firebase**: Google's equivalent, with a document database and good realtime and mobile
  support.

Both give you the hard parts (accounts, permissions, a real database) out of the box. If you
don't code, most app builders (Lovable, Bolt, Replit) connect to one of these or provide their
own, and the access rules below still apply to you.

## Where AI does the heavy lifting

From your spec, AI can **design the schema** (tables, relationships, types), **write queries
and migrations**, **generate API routes** and **set up auth**. With an **MCP** server
(→ mcp-servers), such as the one Supabase ships or a generic Postgres server, an agent like
Claude Code, Cursor or Codex can read your real schema instead of guessing at it. Point it at
a development project, and use read-only mode where the server offers it.

## The access model: reads *and* writes

Every row in a shared database is visible to everyone unless something says otherwise. On
Supabase, that something is **Row Level Security**. A table in the exposed schema without RLS
can be read and written by anyone holding the public key that ships inside your app. With RLS
on, nothing is allowed until a policy allows it:

```sql
alter table tasks enable row level security;

create policy "owners read their tasks" on tasks
  for select using ((select auth.uid()) = user_id);

create policy "owners add their own tasks" on tasks
  for insert with check ((select auth.uid()) = user_id);
```

`using` filters which existing rows a user can see or change; `with check` validates the rows
they try to write. On Firebase the same idea is a security rule that compares
`request.auth.uid` with the document's owner field.

Owner-only isn't the whole story. If users can update their own rows directly, they can also
*lie* in them: a score, a streak, a role. Anything that must be trustworthy gets computed
server-side.

## Worked example: a to-do backend in five steps

1. Paste your spec into your agent: "Design tables for users' lists and tasks, with owner-only
   RLS policies for select, insert, update and delete. Output a migration file; don't apply
   it."
2. Read the migration. Every table should have RLS enabled and a policy per operation.
3. Apply it to a **development** project, never production first.
4. Create two test users and a few rows for each.
5. Run the task's attack: as user A, request user B's rows. Empty or denied means it works.

> 💡 **Try it:** If you already have a Supabase project, open its Security Advisor in the
> dashboard (or ask your agent to run it through the MCP server). It lists tables with RLS
> disabled. Any hit is your first fix.

## Server-side functions: where secrets live

Some code must run on a server because it holds a secret: calling an AI model API, taking a
payment, sending email. Supabase calls these Edge Functions; Firebase has Cloud Functions;
on Vercel or Netlify it can be an ordinary API route. The client calls *your* function; only
the function knows the key.

## Common failure modes

- **Every user sees everyone's data** → RLS is off, or a policy says `using (true)` → enable
  RLS with owner-only policies and run the two-user test.
- **The app goes blank right after you enable RLS** → no `select` policy yet, so Postgres
  returns nothing → add the policy; the empty list was RLS doing its job.
- **"Secure" in the SQL editor, leaking in the app** (or the reverse) → you tested as a role
  that bypasses RLS → test as the `authenticated` role or through the app itself.
- **A secret key ends up in the frontend** → it was put in a variable the build exposes
  (`NEXT_PUBLIC_`, `EXPO_PUBLIC_`) → rotate the key, then move the call into a server-side
  function.

## The one rule you can't skip

Backends hold secrets. So: **keys and credentials live server-side, in environment variables,
never in the browser or app bundle.** Use proper auth and row-level security so each user only
touches their own data. AI will help, but *you* own this check.

With data, auth and storage in place, your app can actually *do* things. Next, the platform
many apps need sooner or later: **mobile**.
