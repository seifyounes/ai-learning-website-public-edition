The frontend is where AI feels like magic: describe a UI and watch it appear. But "appear" and
"good" are different things. A good UI is consistent from screen to screen, works on a phone,
and can be used with a keyboard. A repeatable workflow gets you there reliably.

## The workflow

1. **Start from components, not pages.** Build one piece at a time (a card, a form, a nav;
   in Flutter, one widget at a time) so each is easy to get right and reuse.
2. **Use a component library.** On the web that's often **shadcn/ui**; in **Flutter** it's
   shared widgets plus a Material 3 theme. Either way the AI composes from consistent,
   well-structured building blocks, so the whole UI looks coherent and stays maintainable.
   shadcn/ui works especially well with AI because its components are copied into your
   project as ordinary files, so the agent can read and edit them like the rest of your code.
3. **Show, don't tell.** Hand the AI a **screenshot or a site you admire** and say "match
   this". A visual reference beats paragraphs of description; it's few-shot prompting
   (→ prompting-in-2026) applied to design.
4. **Iterate in scoped steps.** "Just this card. Now just the mobile layout." Tight scope
   (→ prompting-claude-code) keeps the agent from refactoring things you liked.

## Tools

- **v0**: prompt-to-UI in Next.js + Tailwind; quick for generating polished components.
- **Claude Code, Cursor, Codex or Copilot**: wire those components into your real app, with
  state and data.

Many coding agents can now also *see* their own output, through built-in browser tools or a
browser MCP server that takes screenshots. When yours can, let it compare its screenshot with
your reference itself. When it can't, take the screenshot yourself and paste it back.

## Worked example: one task card, four passes

Say your to-do app needs a task card: title, due date, a checkbox, and a red "overdue" state.
You have a screenshot of a card you like from another app.

1. **Layout only.** Attach the reference and ask for structure and spacing, using the
   project's existing components. Ignore colors for now. Review: is the hierarchy right?
2. **Tokens.** "Apply the theme tokens; no hex values, no one-off colors." Then ask the agent
   to search the component for hardcoded colors to prove it. If it finds any, they go.
3. **States.** Real data is messy. Ask for the empty state, a 120-character title, a task due
   today, an overdue task and a completed task, and render all five side by side. This is
   where most AI-built cards break.
4. **Constraints.** Check it at 375px wide (your browser's device toolbar does this), tab to
   the checkbox with the keyboard, and confirm the focus ring is visible and the overdue
   state isn't shown by color alone (add an icon or a word).

Four short passes, each one reviewable. One giant "build me a beautiful task card" prompt
would have produced something that looked fine in the default state and broke in the other
four.

> 💡 **Try it:** Open any page you've built (or any site) in your browser, open the device
> toolbar, set the width to 375px, and press Tab a few times. If something scrolls sideways or
> you can't see where the focus is, you've found your first two success criteria.

## Common failure modes

- **Every screen looks slightly different** → screens were generated without shared tokens or
  components → define the theme once and tell the agent to compose only from it.
- **Pretty on desktop, broken on a phone** → nobody checked narrow widths → add "no horizontal
  scroll at 375px" to your definition of done and check it with the device toolbar.
- **"Fix the button" rewrites the whole page** → the prompt didn't say what was off-limits →
  name the component, say what must not change, and ask for a list of touched files.
- **It looks right but a keyboard or screen-reader user can't use it** → the AI optimized
  what's visible → run an accessibility audit (Lighthouse in Chrome DevTools, or the axe
  browser extension) and hand the findings to the agent.

## Don't skip the basics

AI will happily make a pretty desktop UI that breaks on mobile. So always **check responsive
widths** and accessibility, and write them into your definition of done. Give it success
criteria ("no horizontal scroll at 375px", "keyboard-navigable") and it will hit them.

You can now turn a spec into a real, good-looking frontend at speed. Next: the half that makes
it actually *do* something, the backend and database.
