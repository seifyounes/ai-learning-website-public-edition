AI can build an app shockingly fast, which is exactly why you must decide **what** to build
first. The people who ship good AI-built apps don't start with code; they start with a
**spec**. A clear spec is the steering wheel. Without one, the AI drives fast in a random
direction, and every session picks a slightly different direction from the last.

## What a spec captures

Keep it to a page:

- **Problem**: what real pain are you solving, in one or two sentences?
- **Users**: who is this for, specifically? "Everyone" is not an answer.
- **MVP features**: the smallest set that delivers value, **and the non-goals**, the things
  you're deliberately *not* building yet.
- **User flows**: the key paths a user takes through the app, step by step.
- **Success criteria**: how you'll know it works, written so someone else could check.

A page is the right size because it's short enough that you'll actually write it and keep it
current, yet complete enough that a coding agent (or a human developer, or an app builder)
can build from it without guessing. A thirty-page requirements document goes unread; a
one-line idea gets interpreted.

## Worked example: from one sentence to half a page

Start with the kind of sentence most ideas begin as: *"An app that helps students stop
falling behind."* Hand that straight to a coding agent and you'll get *something*: a
calendar, a to-do list, maybe a chatbot, because the sentence allows all of them. Here's how
an interview narrows it.

1. **Problem.** The AI asks what "falling behind" actually looks like. Your answer:
   assignments live on four different course sites, there's no single list, and deadlines
   get discovered the night before. The problem is now *scattered deadlines*, not
   "productivity".
2. **User.** It asks who, exactly. "University students taking four or more courses, checking
   on their phone between classes." That one answer already implies a phone-friendly layout,
   fast entry and no long setup.
3. **MVP features.** Add an assignment (title, course, due date); see everything due in the
   next seven days, sorted by date; mark one done. Three features.
4. **Non-goals.** This is where the interview earns its keep. No syncing with course
   platforms, no grades, no study timer, no group sharing, no AI study plans, *in v1*. Each
   is a reasonable idea, and each is days or weeks of work.
5. **Flows.** First open → add the first assignment in under thirty seconds → see it on the
   seven-day list. Daily use → open, glance, tick something off.
6. **Success criteria.** "A new user adds an assignment without instructions." "The seven-day
   list is correct across a month boundary." "Usable on a 375px-wide phone screen."

That fits on half a page, and a fresh session in a different tool could build from it
without asking you a single question. That is the test of a good spec.

## Let AI help you write it

Writing a spec from a blank page is hard; answering questions about your idea is easy. So
have the AI **interview you**: "Ask me one question at a time until you can write a clear
spec for this idea." *One at a time* matters. Ask for a full draft instead and the model
fills every gap with a confident guess, and you end up editing its assumptions rather than
stating yours. Questions surface the gaps you'd otherwise hit in code, when they cost more.

Then refine the draft together and save it as a file **in the repo** (`docs/plans/` or
`spec.md`), or as a doc in your notes if you don't code yet. Your coding agent (Claude Code,
Cursor, Codex, Copilot) or app builder then builds against that file, session after session.
For bigger projects, tools such as GitHub Spec Kit add structure (spec, plan, tasks), but the
one-page habit comes first.

> 💡 **Try it:** Paste your idea in one line into any assistant, followed by: "Ask me one
> question at a time until you can list five non-goals for v1. Then list them." In five
> minutes you'll see scope you didn't realise you were carrying.

## Common failure modes

- **The agent keeps adding features you didn't ask for** → the spec has no non-goals, so every
  gap gets filled with plausible extras → add an explicit non-goals list and tell each
  session to build only against the file.
- **Success criteria nobody can check** ("fast", "intuitive") → they describe feelings, not
  behavior → rewrite each one as something you could observe or test ("the list loads in
  under a second on a phone").
- **A "minimal" spec with ten MVP features** → nothing was ranked, so nothing was cut →
  force-rank them, keep the top three, and move the rest to non-goals marked "v2".
- **The spec lived in a chat that's now gone** → it was never saved → commit it to the repo or
  a notes doc and point every session at that file.
- **The AI invents answers you never gave** → you asked for a draft before it had enough
  information → tell it to interview first and to list unknowns as open questions.
