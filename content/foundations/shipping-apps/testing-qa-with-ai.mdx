Testing is the step everyone skips and everyone regrets. AI removes the excuse: it writes the
tests *for* you, so quality stops being optional. It also ties directly to habits you already
have: "let the agent verify its work" (→ core-loop) and "measure with evals"
(→ evals-and-testing).

## What AI tests for you

- **Unit tests**: individual functions and logic. Fast, and the bulk of a healthy suite.
- **End-to-end tests**: full user flows (sign up, log in, check out) with tools like
  **Playwright** or **Cypress** driving a real browser. On mobile, Flutter's
  `integration_test` package or a tool such as Maestro plays the same role.
- **Test plans and cases**: structured coverage generated from your spec.
- **Edge cases**: ask "what could break this?" and it surfaces inputs you didn't think of.

Keep the proportions sensible: many fast unit tests, a few end-to-end tests for the flows that
must never break. A suite that's all end-to-end gets slow, and a slow suite stops being run.

The most useful move: after AI builds a feature, ask it to **write the tests for what it just
wrote**. Then every later change gets checked automatically. Recent Playwright versions go a
step further and include agent definitions that plan, generate and repair tests, which is what
the video demonstrates.

## Worked example: testing a streak counter

Take a small, realistic function: given the dates a user completed a task, return their
current streak of consecutive days. Here's how to test it with AI without fooling yourself.

1. **Ask for the tests with the behavior spelled out.** "Write tests for `currentStreak(dates,
   today)`. Assert exact numbers, not just that it returns something."
2. **Read the assertions.** A test like `expect(result).toBeDefined()` passes for a function
   that returns the wrong number. You want `expect(currentStreak([...three days...],
   today)).toBe(3)`.
3. **Ask for edge cases, then pick.** The AI suggests: empty list, duplicate dates, unsorted
   input, a gap yesterday, a completion just before midnight in another time zone. The last
   two are the scary ones. Add tests for those.
4. **Break the code on purpose.** Change one comparison in the function (say `>=` to `>`) and
   run the suite. If nothing goes red, your tests aren't guarding that line. This trick is a
   manual version of mutation testing, and it's the fastest way to find out whether a green
   suite means anything.
5. **Restore the code and commit.** Code plus tests, together.

> 💡 **Try it:** Pick any function that already has a test in a project you have. Break one
> line on purpose, run the tests, and see whether anything fails. Five minutes, and you'll know
> how much that green tick is worth.

## Common failure modes

- **All green, and the bug still ships** → assertions check that something exists, not that
  it's correct → read the assertions, use exact expected values, and break the code to prove
  each test can fail.
- **The agent "fixes" a failing test by changing the expected value** → nothing told it tests
  are the spec → add "never edit a test to make it pass without asking me" to the instruction
  file.
- **End-to-end tests fail at random** → fixed sleeps and shared test data → use Playwright's
  auto-waiting locators, wait for real conditions, and give each test its own data.
- **Passes on your machine, fails in CI** → environment differences (time zone, missing env
  vars, seed data) → pin them in the CI config and make the test set its own data.

## This is "verify your work", made real

You met the principle in the Claude Code pillar (give the agent a way to check itself) and as
**evals** for AI features. Here it becomes a real **test suite** for your whole app: a safety
net that catches regressions the moment they appear, so you can ship fast *and* safely. Wiring
the suite into a hook or CI makes it non-optional (→ hooks-automation).

## Trust, but read the tests

AI drafts the suite in minutes; your job is to make sure it tests the things that matter. A
quick rule of thumb: for each critical flow, you should be able to say in one sentence what
would have to break for its test to go red. If you can't, the test isn't guarding it yet. With
a tested app, you're ready to put it in front of real users. Let's ship it.
