The blank project is the slowest part of any build, and now the easiest to skip. AI app
builders turn your **spec into a running skeleton in minutes**, so you start from "it works"
instead of "untitled folder".

## The tools

You met these in the Claude Code pillar (→ what-is-claude-code); here's where each one shines:

- **v0** (Vercel): generates polished React / Next.js + Tailwind UI from a prompt. A strong
  fit if your stack is Next.js.
- **Lovable / Bolt**: full-stack scaffolds (frontend, backend, auth, database) from a
  description, runnable in the browser.
- **Replit**: a full AI development environment if you want everything in one place.

Paste your spec, describe the app, and you get pages, components and a basic backend to build
on. There's also a quieter option: your **coding agent can scaffold too**. Ask Claude Code,
Cursor, Codex or Copilot to run the framework's own starter (`npx create-next-app`,
`npm create vite@latest`, `flutter create`, `npx create-expo-app`) and build the first screen
from your spec. You lose the instant visual preview, but the code is in your repo from minute
one. For native mobile, that's usually the better start.

## The pro workflow: scaffold, then engineer

Here's the move that separates working builds from prompt-and-pray:

1. **Scaffold** with a builder → get to "it runs".
2. **Export the code** into a coding agent → do the real engineering: refactor, add features,
   wire up your spec properly, add tests.

The builder beats the blank canvas; your skills (the whole Claude Code pillar) make it
production-worthy.

## Worked example: a landing page, end to end

Say your spec is a to-do app for students. Here's the whole handoff, step by step.

1. **Prompt the builder with the spec, not a vibe.** Paste the problem, user and three MVP
   features, then ask for "a one-page landing page: headline, three feature blocks, a
   waitlist form". The spec gives it real content to lay out.
2. **Iterate visually, briefly.** Two or three requests in the builder's chat ("tighter
   headline", "stack the cards on mobile") while changes are cheap and visual. Stop once it's
   roughly right. Builders shine here.
3. **Export or sync to GitHub.** Most builders can push to a repo or download the project. Do
   it now, before you invest more.
4. **Run it locally.** Clone, install, start (`npm install`, then `npm run dev` for a typical
   JavaScript project). If it fails, the usual cause is missing environment variables; ask the
   agent to list every one the code reads and create a `.env.example`.
5. **Add the project's memory.** A `README.md` and an instruction file (CLAUDE.md, AGENTS.md,
   `.cursor/rules`) describing the stack and your rules.
6. **Do one engineering pass and commit.** Real copy, `[PLACEHOLDER]` wherever you'd have to
   invent something, a working form. Commit with a clear message. That commit is your
   baseline.

If you don't code, steps 1–3 and the copy pass still work entirely inside the builder. The
export simply keeps your options open.

> 💡 **Try it:** Before you put an hour into any builder, open its export or GitHub-sync
> option on a throwaway project and check what comes out. Does it run outside the builder?
> Two minutes now saves you from discovering lock-in later.

## Common failure modes

- **Every fix in the builder's chat breaks something else** → the app has outgrown
  prompt-only editing → export, then make scoped changes with a coding agent and review
  each diff.
- **The exported code won't start locally** → it depends on environment variables or hosted
  services the builder set up for you → have the agent list them, fill a local `.env` file
  from a `.env.example`, and note them in the README.
- **Invented content ships** (fake testimonials, made-up user counts) → builders fill empty
  slots with plausible filler → mark gaps as `[PLACEHOLDER]` and search for that marker before
  you deploy.
- **Credits or quota run out mid-project** → many small regenerations of the whole app → batch
  your requests, and move to your editor once the skeleton is done.

## Mind the trade-off

Building *entirely* inside an app builder is fast but gets harder to control and maintain as
it grows. So treat builders as a brilliant **starting point**, not the final home for serious
code. Now that you have a skeleton, let's flesh out the frontend.
