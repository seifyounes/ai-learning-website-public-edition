Plain automations are powerful but dumb — they only follow exact rules. The moment
you drop an **AI step** into the middle, the workflow gains *judgment*: it can read
messy human input, decide, summarise, and write. This is where automation stops
being plumbing and starts being smart.

## An LLM is just another action

In your trigger → action flow, an AI node sits in the middle like any other step:

1. Data comes in (an email, a message, a transcript).
2. The **LLM step** transforms or decides — summarise it, classify it, extract
   fields, draft a reply.
3. Its output feeds the next action — route, reply, log, notify.

Everything from the prompting lessons lives inside that node (→ prompting-in-2026): you write a
**system prompt**, give it **few-shot examples**, and demand a strict **output format** so the
next step can rely on it.

## What it unlocks

- **Classify** — "is this email urgent? what's it about?" → route accordingly.
- **Summarise** — turn a long thread or transcript into the key points.
- **Extract** — pull structured fields (name, date, intent) from free text.
- **Generate** — draft a tailored reply, a social caption, a first response.

Rule-based automation could never read "this customer sounds upset and wants a
refund." An AI step can — and acts on it.

## Rules first, AI for the rest

An AI step costs money on every run, takes a second or more, and can be wrong in ways a rule
never is. So put cheap rules in front of it. If the subject line says "unsubscribe", a filter
handles it. If the sender is your own team, skip triage. Let the AI handle only the messages
rules can't sort. Your flow gets cheaper, faster and easier to debug.

## Worked example: one message through the node

Say this arrives through a contact form:

> "Hi, I was charged twice for my March invoice and need it sorted before Friday. Also, any plans
> for a dark mode?"

The node's system prompt says: classify as exactly one of `bug | question | feature-request |
praise`, rate urgency 1–5, write a one-line summary, and return JSON only. Two few-shot examples
show a short complaint and a compliment with their correct JSON. The model returns:

```json
{"category": "bug", "urgency": 4, "summary": "Double charge on March invoice, needs fix by Friday; also asks about dark mode."}
```

Now the flow takes over:

1. **Validate.** An IF step checks that `category` is one of the four allowed words and
   `urgency` is a number from 1 to 5. Anything else goes to a "Needs review" tab.
2. **Route.** `category = bug` goes to the Bugs tab; urgency 4 or above also pings you.
3. **Keep what the label lost.** The message held two requests, and the summary kept both. If
   mixed messages are common, add a `secondary` field so the feature request isn't buried.

Two settings help. Use a **low temperature** (or the provider's default for classification) so
the same message gets the same label. And where your tool offers it, switch on **structured
output** (a JSON schema the model must follow), which most major model APIs now support
(→ structured-outputs-tools).

> 💡 **Try it:** Paste the same tricky message into your classifier three times. If the category
> changes between runs, your categories overlap or your examples are too thin. Fix that before you
> trust the routing.

## Common failure modes

- **The next step crashes on the reply** → the model added a sentence or code fences around the
  JSON → no enforced format → use structured output or a parser, then validate.
- **Labels drift ("Bug report", "bug", "BUG")** → free-text categories → the allowed values were
  only implied → list the exact values and reject anything else.
- **Confident wrong labels on ambiguous messages** → the model had to pick one of four → no
  "unsure" option → add `other` and route it to a human.
- **The bill creeps up** → AI runs on every item, including obvious ones → no pre-filter →
  put rules first and use the cheapest model that labels well.
- **A message talks the model into a label** → instructions hidden in the input → the input
  wasn't treated as data → delimit it and validate the output.

## One caution

Because the AI can be wrong (→ verification-and-grounding), keep a **human in the loop** for
anything high-stakes: have it *draft* the refund email, not *send* it. The reliability lesson
makes this a full system (→ reliability). First, the glue that connects anything to anything:
webhooks and APIs (→ webhooks-and-apis).
