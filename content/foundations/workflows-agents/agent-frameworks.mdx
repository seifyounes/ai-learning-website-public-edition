So far you've built agents with **no-code** (n8n). When you outgrow that, there's a
world of **code frameworks** for building agents with full control. You don't need
them yet — but you should know the map, and one important freshness note.

## The current players (2026)

- **LangChain / LangGraph** — one of the most widely used ecosystems. LangGraph is the
  go-to for **stateful, controllable** agents (explicit steps, memory, loops), modelled as a
  graph of nodes you define.
- **CrewAI** — orchestrates **multiple agents** as a "crew" with roles; beginner-
  friendly for multi-agent setups.
- **OpenAI Agents SDK** — OpenAI's official, lightweight framework for building
  agents with tools and handoffs.
- **Claude Agent SDK** — Anthropic's agent stack: the same harness that powers Claude
  Code, exposed as an SDK. If you already use Claude Code, this is the framework whose
  mental model you know.
- **Microsoft Agent Framework** — Microsoft's unified successor to AutoGen and Semantic Kernel.
- **⚠️ AutoGen** — Microsoft has put AutoGen in **maintenance mode**: bug fixes and security
  patches only, no new features, community-managed, with new projects pointed to the Microsoft
  Agent Framework (the README linked below the video says so). Lots of older tutorials still
  feature AutoGen; treat those as legacy and don't start new work on it.

You'll also meet Google's Agent Development Kit, LlamaIndex (strong on retrieval-heavy agents)
and lighter libraries such as PydanticAI. The list will look different in a year; the questions
below won't.

## What a framework actually gives you

Strip the branding and most frameworks offer the same five things:

1. **The loop** — call the model, run the tool it asked for, feed the result back, repeat.
2. **Tool plumbing** — turn your functions into tool definitions the model can call.
3. **State and memory** — keep track of what happened across steps and sessions.
4. **Orchestration** — handoffs between agents, branches, a human approval pause.
5. **Tracing** — a record of every step, so you can debug why the agent did what it did.

If your feature needs none of these, you don't need a framework. Anthropic's guide to building
effective agents makes the same point: start with direct model API calls and add abstraction
only when it earns its place (→ intro-to-agents links it).

## Worked example: one feature, two designs

Say you want a support assistant inside an online shop.

- **Version 1: "Summarise this customer's last five orders for the support agent."** The data
  is fetched by your normal code, then one model call writes the summary. No loop, no tool
  choice. **Single call.** Twenty lines in your backend, easy to test.
- **Version 2: "Let customers ask anything about their orders and act on it."** Now the model
  must decide whether to look up an order, check a delivery status or start a return; it may
  need several lookups in a row, must remember the conversation, and must pause for a human
  before refunding. That's a loop, tool choice, memory and an approval step. **Framework
  territory.** LangGraph if you want explicit control over every state, an official SDK if
  you're committed to one model vendor.

The wall between the two isn't size or ambition. It's the moment **the model, not your code,
decides what happens next.**

> 💡 **Try it:** Open the quick-start page of one framework and find three things: the last
> release date, how it defines a tool, and how it caps the number of loop steps. Five minutes,
> and the "magic" turns into ordinary code.

## The honest truth: you probably don't need one yet

For agency and business automation, **n8n and Make cover most of what you'll do** —
visually, fast, and reliably. Reach for a code framework only when you hit a real
wall:

- You need **custom logic** or control no-code can't express.
- You're operating at **serious scale**.
- You want to **embed an agent inside your own app** (an AI assistant inside a product
  you're building) — which is exactly the *Applied AI engineering* pillar (→ build-agent-in-code).

## Common failure modes

- **A framework for a single call** → hundreds of lines and new dependencies for one prompt →
  reaching for tools before need → ship the direct API call first.
- **Following a stale tutorial** → imports and class names don't exist → the framework moved on
  → check the version and date; use the official quick-start.
- **A multi-agent crew for a one-agent job** → slow, costly, hard to debug → roles were added for
  their own sake → start with one agent and split only when it clearly struggles.
- **Can't explain what the agent did** → a wrong answer and no record → tracing was skipped →
  turn on the framework's tracing or an observability tool from day one (→ observability-tracing).
- **Locked into one vendor** → switching models means rewriting → model calls are scattered
  everywhere → put model access behind one function of your own.

## What actually transfers

Frameworks come and go. The **concepts** don't: model + tools + loop + memory + human oversight.
Master those — which you now have — and you can pick up any framework quickly when a project
finally needs one. Last lesson: a recipe book of automations worth building for your business
(→ business-recipes).
