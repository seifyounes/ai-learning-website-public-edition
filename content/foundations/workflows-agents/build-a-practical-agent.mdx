Time to build a real one. A practical agent isn't a sci-fi robot — it's a model,
a few tools, and a loop, pointed at a useful goal. Start small and supervised, and
it'll save you hours.

## The anatomy you'll wire up

1. **The brain** — an LLM with a clear **system prompt** stating its goal, its
   limits, and the output you want. (All your prompting skills apply here.)
2. **The tools** — only what it needs: web search, send-email, read/write a sheet,
   query a database. Fewer tools = more reliable.
3. **The loop** — the agent node lets it act, see the result, and choose the next
   step until the goal is reached.

Optionally, a fourth part: **memory**, so a chat-style agent remembers earlier turns. A
one-shot research job usually doesn't need it.

## A great first agent: research & draft

Build a **research agent**: input a company name → it searches the web → summarises
what it found → drafts a tailored outreach email → drops it in a sheet for you to
approve and send. It's genuinely useful, and it's **low-risk** because the agent
*prepares*, you *approve*.

## Worked example: wiring it in n8n

Exact labels move between n8n versions, but the shape is stable.

1. **Trigger.** Start with a manual trigger (or a chat trigger) that passes in one field:
   `company`.
2. **AI Agent node.** Add it and attach a **chat model** underneath: OpenAI, Gemini, Anthropic,
   or a local model through Ollama. The agent node is the loop; the model is the brain.
3. **System message.** State the job in five lines: who it works for, the goal, the output
   shape, what to do when it can't find something ("write *not found*, never guess"), and what it
   must never do ("never send anything").
4. **Tools.** Attach two: a web-search tool and a sheet tool. Give each a plain description of
   *when* to use it ("use search to find the company's site and pricing page"). The model chooses
   tools from those descriptions, so vague descriptions mean wrong choices.
5. **Limits.** Set an iteration cap (n8n's agent node has a max-iterations setting) so a confused
   run stops instead of searching forever.
6. **Run three real inputs.** Then open the execution log and read it like a transcript: which
   tool it called, with what input, what came back, what it decided next.

That log is where you learn the most. You'll spot the run where it searched the same query
twice, or summarised a review site instead of the company's own page, and each one points to a
specific line to fix in the system message or a tool description.

**If you code:** the same agent is about a page of code in the OpenAI Agents SDK, the Claude
Agent SDK or LangGraph (→ build-agent-in-code). **If you don't code:** n8n *is* your path; the
skills of scoping, describing tools and reading the log are identical.

> 💡 **Try it:** Open one finished run's execution log and write one line per step: tool,
> input, what it decided. Mark the single step where you'd have decided differently. That one
> mark is your next prompt fix.

## Keep it on a leash

Two rules that separate "saves me hours" from "emailed a client nonsense":

- **Narrow scope** — one job, minimal tools, a tight prompt.
- **Human in the loop** — for anything external or high-stakes, the agent drafts and
  *you* hit send. (Whole next lesson on this: → reliability.)

## Common failure modes

- **It ignores a tool** → answers from memory instead of searching → the tool's description
  doesn't say when to use it → describe the trigger for each tool in one plain sentence.
- **It invents facts** → a price or feature that isn't real → no rule for missing data →
  require a source URL per fact and "not found" when there's none.
- **Runs get long and expensive** → repeated searches, dozens of steps → no cap, no finish line
  → set max iterations and say exactly what "done" looks like.
- **The output shape changes every run** → the next step can't parse it → no enforced format →
  add a structured output parser or validate the JSON after the agent.
- **Great on one test, bad on the next** → you tuned it on a single input → no test set → keep
  five to ten varied inputs and rerun all of them after each prompt change (→ evals-and-testing).

## Tune until it's boring

Build the research-and-draft agent, test it on a few real inputs, and tune the
prompt until the output is reliably good. You now have a teammate that does the
boring 80% while you keep the judgment. Next: making agents reliable enough to
trust.
