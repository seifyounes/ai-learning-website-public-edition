Pre-built integrations are great until the app you need isn't on the list. **APIs**
and **webhooks** are the two primitives that let you connect *anything* to
*anything* — and they're simpler than they sound.

## API: you ask, it answers

An **API** is how one app lets others talk to it. You send a **request** ("create a
contact with this email"), it sends a **response** ("done, here's the ID"). You
initiate. In automations, an **HTTP Request** step lets you call any app's API
directly — even one with no native connector.

Every request has the same four parts, and once you can read them, any API's docs make sense:

- **Method** — what you want to do: `GET` (read), `POST` (create), `PUT`/`PATCH` (update),
  `DELETE`.
- **URL** — which thing: `https://api.example.com/contacts/42`.
- **Headers** — who you are and what you're sending, usually including an API key or token.
- **Body** — the data, usually JSON, for creates and updates.

The response comes back with a **status code** and usually a JSON body. Learn five codes and
you can debug most failures: `200` OK, `401`/`403` your key is missing or lacks permission,
`404` wrong URL or ID, `429` too many requests (slow down), `500` the other side broke.

## Webhook: it tells you

A **webhook** is the mirror image: instead of you asking, the other app **notifies
you** the instant something happens. It POSTs the event to a URL you provide. The
classic line: *"don't call us, we'll call you."*

## Why this matters for triggers

- **Webhook trigger** — real-time. The payment provider pings your URL the moment a
  payment lands. Instant, efficient.
- **Polling** — the old way: your automation repeatedly asks "anything new?" Slower
  and wasteful. Prefer webhooks when the source supports them.

## Worked example: a payment webhook, end to end

Say a payment provider should tell your n8n flow every time someone pays. Here's what actually
happens, in order.

1. **You create the receiver.** Add a Webhook node. n8n gives you two URLs: a **test URL** that
   only listens while you click "listen for test event", and a **production URL** that works once
   the workflow is active.
2. **You register the URL.** In the provider's dashboard, add the URL and pick the events you
   want (say, "payment succeeded"). Most providers show a **signing secret** here; save it in
   your tool's credential store.
3. **An event fires.** Someone pays. The provider sends a `POST` to your URL with a JSON body:
   an event type, a unique event ID, the amount, the customer reference.
4. **You reply fast.** Your endpoint should answer `200` within seconds. If it doesn't, many
   providers assume delivery failed and **retry**, which is why the same event can arrive twice.
5. **You verify, then act.** Check the signature against your secret, look up the event ID to
   skip duplicates, then write the row, notify the team, or hand it to an AI step.

**If you don't code:** steps 1–5 are all clicks in n8n, Make or Zapier ("Catch Hook" in Zapier,
"Custom webhook" in Make). **If you code:** the same five steps are an API route in your backend.

> 💡 **Try it:** Open a free request inspector such as webhook.site, copy the unique URL it gives
> you, and send it a request (from a form tool's webhook setting, or with curl). You'll see the
> raw method, headers and JSON body: exactly what your automation receives.

## Common failure modes

- **Worked in testing, silent in production** → the provider still points at the test URL, or
  the workflow isn't active → test and production URLs differ → register the production URL
  and activate.
- **Duplicate records** → the provider retried because your reply was slow or failed →
  webhooks are delivered "at least once" → reply 200 first, de-duplicate on the event ID.
- **Fake events accepted** → anyone with the URL can POST to it → no verification → check the
  provider's signature or a secret header.
- **`401` or `403` from an API** → missing, expired or wrongly placed key → credentials pasted
  by hand → store them in the credential manager and match the header format in the docs.
- **`429` errors in a loop** → you're calling faster than the rate limit → no pacing → batch
  requests, add a wait, and retry with a growing delay.

## The "connect anything" superpower

Once you're comfortable with these, no app is off-limits. A niche tool with an API
but no Zapier integration? Call it over HTTP. Need instant reactions? Hand out a
webhook URL. This is what turns "I can automate the easy stuff" into "I can wire up
my *entire* stack." Next, we level up from fixed workflows to **agents** that decide
the steps themselves (→ intro-to-agents).
