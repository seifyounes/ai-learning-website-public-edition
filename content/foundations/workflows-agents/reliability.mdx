The gap between a cool demo and something you'd run for a paying client is
**reliability.** Automations run unattended and on repeat, so when (not if)
something goes wrong, it goes wrong at scale. Three habits close that gap.

## 1. Error handling — fail loud, not silent

APIs go down; data arrives malformed. Without handling, your flow either crashes
quietly or does the wrong thing 200 times. So:

- Add an **error branch / error workflow** that catches failures and **notifies
  you** (Slack, email).
- Use **retries** for flaky steps (a momentary network blip shouldn't kill the run).

The principle is the coding-agent one again: give it a way to surface problems.

## 2. Human-in-the-loop — approve the risky stuff

The single best safety mechanism: for anything **external or irreversible**, insert
an **approval step.** The agent *prepares* (drafts the email, stages the charge),
and a human *approves the send*. You keep the speed and remove the "AI emailed a
client something wrong" nightmare. Reserve full autonomy for low-stakes tasks.

## 3. Cost control — don't get a surprise bill

AI steps and API calls cost money, and a loop bug can spend it fast:

- Use the **cheapest model that's good enough** per step (→ models-and-effort).
- Add **run caps and max-iteration limits** so nothing loops forever.
- **Monitor** token usage so a runaway flow can't quietly rack up charges.

A quick estimate keeps you honest: **runs per month × model calls per run × cost per call.** A
plain AI step makes one call per run. An agent makes one call per loop iteration, so a run that
takes ten steps costs roughly ten times as much, and a bug that loops 200 times costs 200 times
as much. That's why the iteration cap matters more for agents than for anything else.

## Worked example: hardening the triage flow

Take the AI triage flow (→ ai-in-automations): form message → AI classifies → row in a sheet →
alert for urgent bugs. Here's how it becomes safe to leave running, in n8n terms (Make and Zapier
have equivalents for each move).

1. **Retries on the flaky steps.** In the AI node's and the sheet node's settings, turn on retry
   on fail with a few tries and a short wait. A timeout at 3 a.m. now heals itself.
2. **An error output instead of a dead end.** Set the AI node to continue through its error
   output, and route that output to the deterministic fallback: write the row with category
   `unclassified` and the raw message, so nothing is lost.
3. **A validation gate.** An IF step checks the JSON fields against the allowed values. Fails go
   to a "Needs review" tab, never to the alert.
4. **An error workflow.** Create a small separate workflow that starts with an Error Trigger and
   sends you a message with the failed workflow's name and the error. Set it as the error
   workflow in the main flow's settings.
5. **A heartbeat.** Errors only fire when the flow runs. Add a daily check that alerts you if no
   successful run happened in the last 24 hours. This catches the expired login that stops the
   trigger without a single error.
6. **Approval before anything leaves.** If the flow drafts replies, they wait for your click
   (n8n can send a message and wait for a response; a "Ready to send" column works too).
7. **Break it on purpose.** Point the AI step at a wrong model name, submit a message, and check
   that you get pinged, the row lands as `unclassified`, and nothing else breaks.

> 💡 **Try it:** Break one of your live flows on purpose (a wrong URL in one step), trigger it, and
> time how long it takes you to find out. If the answer is "I wouldn't have," that flow needs
> step 4 today.

## Common failure modes

- **Weeks of silent failure** → nobody noticed the flow had stopped → no error workflow and no
  heartbeat → add both; errors catch crashes, heartbeats catch silence.
- **Retries cause duplicates** → two emails, two charges → a non-repeatable step was retried →
  retry only safe steps, or de-duplicate on a unique key.
- **Approvals pile up unread** → the queue becomes the bottleneck and people approve blindly →
  everything needs approval → gate only external or irreversible actions; batch the rest.
- **A surprise bill** → a loop or a traffic spike ran the model thousands of times → no caps
  → max iterations, a provider budget alert, and the cheapest adequate model.
- **Bad output slips through** → the "rules" lived only in the prompt → prompts are requests,
  not checks → validate in a separate step after the model.

## The mindset shift

Demos optimise for "it worked once." Production optimises for "it keeps working,
and tells me when it doesn't." Bake in error alerts, approval gates, and cost
guards, and you can actually trust your automations with real client work. Next, a
