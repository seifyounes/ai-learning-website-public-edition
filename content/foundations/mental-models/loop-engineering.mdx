task: |
  **If you code:** take one repetitive, well-specified job you currently *babysit* — "get lint +
  typecheck + tests green on this branch", or a behaviour-preserving refactor of one function
  covered by tests you trust — and write its four parts, one line each: **TRIGGER** (what re-runs
  it), **TOPOLOGY** (doer fixes / checker = the test command — two passes), **VERIFIER** (the
  exact command whose exit code is pass/fail), **STOP-RULE** (green, OR 5 iterations, OR
  no-progress → hand back). Work on a branch or a git worktree so every doer pass is reversible,
  and never let the doer edit the tests to make a pass. Then run one turn by hand:

  ```prompt
  DOER: fix the current failures on this branch. Do NOT declare success.
  Then STOP — I will run the verifier myself.
  ```

  Run the verifier yourself (`npm run lint && npm run typecheck && npm test`, or your stack's
  equivalent such as `pytest` or `flutter analyze && flutter test`), then feed the failures back
  for one more doer pass.

  **If you don't code:** run the same loop with two chat windows on a repeatable document job (a
  cover letter, a product description, a weekly report). Write the four parts first: TRIGGER (you
  paste the checker's verdict back), TOPOLOGY (window A drafts, window B checks), VERIFIER (a
  checklist of four to six yes/no items, such as "under 250 words", "names the reader's main
  objection", "no claim without a source"), STOP-RULE (all PASS, or three rounds, or the same
  FAIL twice → you take over). Then run it:

  ```prompt
  [Window B — the checker. Paste once, then paste each draft below it.]
  You are a strict checker. You did not write this draft. Check it against this list and answer
  each item PASS or FAIL, quoting the line that proves it: [your checklist]. Final line: PASS or
  FAIL only. Do not rewrite the draft.
  ```

  Paste window B's FAIL lines into window A with "Fix only these, change nothing else," and repeat
  until the stop-rule fires.
  Success: four crisp parts written and at least one full doer → checker → feedback turn executed by hand. If you can't write a one-line verifier, that job isn't loop-ready — that's the finding.

**Who this is for:** people who build with AI, with a coding agent or with automations that run
on a schedule. If you don't code and haven't automated anything yet, you can skip this lesson for
now. Come back when a repetitive AI job (drafting replies, tagging feedback, cleaning a
spreadsheet every week) is eating your time and you want it to run, check itself and stop without
you in the chair. The two-chat-window version in this lesson needs no code when you do.

Every lesson so far left one job in your hands. Prompt engineering phrased the request; context
engineering curated the window; harness engineering wrapped the model in guides and sensors — but
*you* were still the one who read the output, decided it wasn't done, and typed the next prompt.
**Loop engineering is the discipline of removing yourself from that seat.** The unit of work stops
being the prompt and becomes the *loop*: a self-continuing cycle where the **system** decides to run
the AI again, not you. Addy Osmani set out the idea in a June 2026 essay,
[Loop Engineering](https://addyosmani.com/blog/loop-engineering/), and practitioners such as Peter
Steinberger and Boris Cherny, both quoted there, describe the same shift. The video compresses it to
one line: **the system prompts the agent.**

## You are the loop — until you're not

Start without any code. You ask a chat assistant for a cover letter. You read it, notice it never
mentions the job's main requirement, and type "add a paragraph on X." You read it again, spot that
it's too long, and type "cut it to 250 words." You stop when it looks right. That cycle — run,
judge, re-prompt, stop — *is* a loop, and **you are the running part of it.** Your eyes are the
verifier. Your finger on Enter is the trigger. Your gut sense of "okay, that's done" is the
stop-rule.

A coding session is the same cycle with different nouns: the agent produces a change, you catch the
test it forgot, you type "now make the tests pass," repeat. Loop engineering is the deliberate act
of **replacing yourself as the prompter**: encoding those three human functions so the loop keeps
turning without you. You're not automating the *work* — the model already does that. You're
automating **your judgment about when to run it again and when to stop.**

## The anatomy: trigger → topology → verifier → stop-rule

Every loop, from two chat windows to a fleet of agents, factors into four parts. Name all four or
you don't have a loop — you have a runaway or a one-shot.

- **Trigger** — what starts each iteration: a schedule, a new file or email arriving, a webhook,
  or simply the previous pass finishing. The video's shorthand — **timer + goal = loop** — is the
  smallest complete recipe: a goal the AI chips at, plus something that keeps firing.
- **Topology** — how the roles are wired for one iteration. The simplest is one assistant
  re-running itself; the load-bearing one is **doer/checker** (next section); scale to
  manager/worker or fan-out when the work splits. Topology is the *shape*, independent of what
  triggers it.
- **Verifier** — the check each iteration must pass: a checklist, a word count, a schema
  validation, a test suite, an LLM-judge. This is exactly the **sensor** from harness engineering,
  now dropped into a loop so its verdict becomes feedback. *(How to design a sensor you can trust →
  harness-engineering; here it's just the slot that rules pass/fail.)*
- **Stop-rule** — when the loop ends: success (the verifier passes), a max-iteration cap, a
  token/time budget, a no-progress detector, or a human gate. **A loop with no stop-rule isn't
  autonomous — it's a fire.**

The four compose into one cycle: trigger fires → topology does a pass → verifier judges →
stop-rule says *continue or halt* → continue loops back. That cycle is the machine you engineer —
prompt, context, and harness engineering all live *inside* it now.

## Keep the maker away from the checker

One topology choice decides whether a loop is trustworthy: **the doer and the checker must be two
different passes.** An assistant that writes something and then grades its own work is committed to
its own story — it rubber-stamps. You met this by hand in verification (chain-of-verification) and
as a principle in harness engineering (separate the generator from the judge); in a loop it becomes
structural. The checker runs in an **independent context — ideally a different model or
provider** — and its verdict is the feedback that triggers the next doer pass. Osmani's essay makes
the same point: you split the verifier from the maker so that "done" means something, and even then
"done" is a claim to check. Anthropic describes the same shape as the **evaluator-optimizer**
workflow — one call generates, another evaluates, in a loop. *(Configuring separate agents for
these roles → subagents-and-agent-teams; here the only point is that they must be separate
passes.)*

> 💡 **Try it:** feel the split in five minutes. **Without code:** open two chat windows. In window
> A ask for a 100-word product description of something on your desk. In window B paste: "You did
> not write this. Check it: under 100 words? names one concrete benefit? no made-up numbers? Answer
> PASS or FAIL per item, quoting the line." Paste B's verdict into A, ask for a fix, and stop at PASS
> or three rounds. **In a coding agent**, run the same split as two rounds:
>
> ```prompt
> Round 1 — DOER: implement the change. Do not evaluate it.
> Round 2 — CHECKER (act as if you've never seen round 1): run the tests and the
> type-checker. List every failure as file:line. Verdict must be PASS or FAIL only.
> If FAIL, hand the list back to the doer and repeat. Stop at PASS or 5 rounds.
> ```
>
> A single session playing both roles is weaker than two separate contexts; it's here so you feel
> the shape.

## When a loop beats a session

Not everything should be a loop. A **session** — you in the chair — wins when the work is
exploratory, ambiguous, taste-driven, or when a wrong autonomous step is expensive to undo. A
**loop** wins when three things line up: the goal is **specifiable**, an iteration's cost is
**bounded and reversible**, and — the deciding factor — **there's a verifier you'd trust more than
your own glance.** That last one is everything. **A loop is only as good as its verifier.** Point
one at "make the tests green" or "every field in this form is filled and valid" and it's gold.
Point it at "make this essay more elegant" with an LLM-judge that can't really tell, and you've
built a machine that mass-produces plausible-wrong output *faster than you ever could by hand.* So
before you loop, ask one question: what is the check, and do I trust it unwatched? No good answer
means keep it a session.

## Cost and safety: mind the blast radius

Autonomy has two bills. **Cost:** every iteration burns tokens and compute, so a permissive
stop-rule on a weak verifier is a budget fire — cap iterations, set a token budget, add no-progress
detection (three passes that don't move the verifier → stop). **Safety:** a loop acts while you're
not looking, so what matters is **blast radius** — what a bad iteration can touch. Drafting text or
editing files on a separate branch is reversible; sending emails, posting publicly, deploying,
spending money or deleting records is not. Match the leash to the damage: shrink what the loop can
reach (drafts folder, sandbox, scoped permissions, a separate git branch or worktree), and **gate
anything irreversible or high-stakes behind a human.** The whole judgment reduces to one line:
**autonomy scales with verifier-trust × reversibility.** Strong verifier and reversible actions →
let it run all night. Weak verifier *or* irreversible actions → tighten the stop-rule, shrink what
it can reach, or keep your hand on it.

## Common failure modes

- **The loop never stops, or stops at a random point** → no explicit stop-rule → add success, a
  round cap and a no-progress rule before the first run.
- **Every pass is approved on the first try** → the checker shares the doer's context → move the
  checker to a fresh window or a different model.
- **The output gets longer and blander each round** → the verifier rewards vague qualities ("more
  engaging") → replace them with yes/no checks you could verify yourself.
- **One bad pass did real damage** → the loop could take an irreversible action → restrict it to
  drafts or a branch, and gate sending, publishing or deleting behind a human.

## The habit

Most loops you already run lack two things: a separate checker and a hard cap. Name the four
parts, harden the weakest, and you've engineered a loop instead of babysitting one. *(The
commands that run loops unattended inside coding agents → autonomy-at-scale; loop engineering is
the thinking those commands execute.)*
