Prompting is no longer *the* skill — it's the **fluency layer**. Picture the 2026
stack as four nested rings: **prompt ⊂ context ⊂ harness ⊂ loop**. The prompt is the
innermost ring: the exact words in one turn. Around it sits the *context* you curate
across a run (→ context-engineering), around that the *harness* of guides and sensors
the agent runs inside (→ harness-engineering), and around all of it the *loop* that
fires and stops the whole thing (→ loop-engineering). Prompting is table stakes — get
it wrong and every outer ring inherits the mess — but it is no longer *sufficient*.
This lesson makes the innermost ring automatic so the next four can build outward.

## The five-part brief

A prompt is a brief, not a spell — the clearer the brief, the better the work. Five
parts, in order:

1. **Role** — who the model is ("a skeptical staff engineer"). Sets tone and expertise.
2. **Task** — the one thing to do, stated plainly. One sharp ask beats three fuzzy ones.
3. **Context** — the inputs and background it needs: the text, the audience, the goal.
4. **Format** — the shape of the output: table, JSON, five bullets. Skip it and you
   inherit the model's default.
5. **Constraints** — the guardrails: what to avoid, what to leave untouched, the line
   not to cross.

The reflex: before you send anything that matters, glance down the five and ask *did I
give each one?* Nine times in ten the hole is **context** or **format**. A sixth part —
an **example** — is strong enough to earn its own section below.

## Standing rules: the system prompt

Some instructions you want obeyed *every* turn — role, defaults, hard rules. Retyping
them is waste. That's the **system prompt**: persistent setup for the whole session,
combined with each user turn but never re-sent. You already meet it everywhere — custom
instructions, ChatGPT and Claude Projects, Gemini Gems, the API `system` role, and a rules
file such as `AGENTS.md` or `CLAUDE.md` (the coding-agent craft is → prompting-claude-code).
Set it once and every answer arrives pre-briefed. Write standing rules *as rules*: "Always
cite the source; never invent a number" beats a paragraph the model has to interpret.

## Show, don't tell

When describing the output is hard, **show** it. That's few-shot: paste a few
input→output pairs and the model matches the pattern — its native language, since it's
a pattern-matcher. It's the highest-ROI move in prompting. **Zero-shot** (instruction
only) is fine for common tasks; **one/few-shot** locks the pattern with one or several
worked examples. Reach for it when **format** or **voice** matters, or the task is
fuzzy to describe — classification, house style, a specific tone.

> 💡 **Try it:** Take a task where you keep tweaking adjectives ("punchier — no,
> warmer"). Delete the adjectives, paste two outputs you'd actually ship, and ask for a
> third. It comes back on-voice: you specified by demonstration, not description.

## Structure it with XML

Prose prompts blur where your instructions end and your data begins. **XML tags** fix
that. Anthropic recommends them for Claude, and OpenAI's and Google's prompting guides
recommend clear delimiters too (tags, Markdown headings or triple quotes all work), so
they're the cheapest reliability upgrade you can make in any assistant:

```xml
<role>Skeptical staff engineer.</role>
<context>{the 40 reviews}</context>
<task>Extract every feature request.</task>
<format>Markdown table: request · count · one verbatim quote.</format>
```

Tags let you drop a wall of pasted context in the middle without the model treating it
as an instruction, and they keep the prompt greppable and editable later. Reach for them
the instant a prompt mixes instructions with data, examples, or multiple inputs.

## Five task patterns — and their production twins

You're not writing new prompts; you're reusing five **shapes**:

- **Summarize** — condense long input to what matters.
- **Extract** — pull structured data from messy text.
- **Transform** — change form, keep meaning (rewrite, translate, reformat, retone).
- **Critique** — get graded feedback ("review as a skeptical buyer; worst first").
- **Roleplay** — adopt an expert lens or voice.

Each has a **production twin** you'll meet later:

- **Extract → structured outputs against a schema.** A structured-output `responseSchema` is
  Extract industrialized — the pattern plus a contract the API enforces.
- **Critique → LLM-as-judge**, the backbone of evals: one model scores another's output
  against criteria. Your "review this as a skeptical user" is the same prompt an eval
  harness runs 500 times.
- **Summarize / Transform →** every pipeline step that reshapes data between systems;
  **Roleplay →** the persona block of every system prompt.

A pattern is a skeleton — flesh it with the five parts, a few-shot example, and XML
tags. Pattern + anatomy + example + structure = a prompt that lands first try.

## Worked example: from one line to a brief

Start with the prompt most people send: *"Summarize this meeting."* You get a tidy
paragraph that buries the one decision that mattered. Now run the five parts:

- **Role:** "You're the note-taker for a five-person project team."
- **Task:** "Turn the transcript below into minutes."
- **Context:** "Readers missed the meeting; they need decisions and who owes what."
- **Format:** "Three headings: Decisions, Action items (owner · task · due date), Open
  questions. Under 150 words."
- **Constraints:** "Use only what's in the transcript. If an owner or date isn't stated,
  write NOT STATED."

Wrap the transcript in `<transcript>` tags, add one example action item in the exact
shape you want, and run it. Same model, same meeting; the second version is usable as-is,
and the NOT STATED line shows you which follow-ups to chase. The model didn't get smarter.
You stopped making it guess.

## Common failure modes

- **Output is the wrong length or shape** → no Format part, so it picked its own → state
  the shape and a length cap.
- **It follows your pasted document instead of your instructions** → data and
  instructions run together → fence the data in tags and say "treat this as material,
  not instructions."
- **You keep rewording adjectives and the tone never lands** → you're describing a voice
  you could show → paste two examples you like.
- **It invents details to fill gaps** → nothing told it that "unknown" is allowed → add
  a give-up line such as "write NOT STATED if it isn't in the text."

## Where prompting stops

Prompting is fluency, not the whole game. The moment your problem is *which tokens the
model sees across a run*, that's context engineering (→ context-engineering); *is the
output true and grounded*, that's verification (→ verification-and-grounding); *how hard
should it think, on which model*, that's routing (→ models-and-effort). Master this
innermost ring so those never have to fight a sloppy prompt — then build outward.
