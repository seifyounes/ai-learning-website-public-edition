**Who this is for:** people who build with AI, with a coding agent or with automations that run
without them watching. If you only chat with an assistant and don't code, you can skip this lesson
for now. Come back when AI output starts going to other people on a schedule (a weekly report,
customer replies, a Custom GPT your team relies on) and you need a rule enforced every time, not
just hoped for. The plain-language section below works without any code when you do.

Stop trying to fix the model. You can't — it's a frozen commodity you rent by the token. What
you *can* engineer is everything wrapped around it: the instructions, the context you feed in,
the tools, the checks that run on its output, the memory that survives between sessions.
Practitioners have settled on a shorthand for this: **Agent = Model + Harness.** The harness is
the whole apparatus minus the model, and it's the only half you control. Harness engineering is
the discipline of building that apparatus so a capable-but-fallible model produces trustworthy
work.

## The idea in plain language

Think of hiring a sharp new assistant who has never seen your work. You'd do two things.
Before they start, you'd hand them a brief, a style guide and a couple of good examples. After
they finish, you'd check their work against a short checklist before it goes out. The first is a
**guide**; the second is a **sensor**. Together they're a harness.

You don't need code for this. A Custom GPT, a Claude Project or a Gemini Gem with standing
instructions and reference files is a guide. A second chat that checks every draft against a
checklist is a sensor. A coding agent's harness is the same idea with sharper tools: instruction
files as guides, tests and linters as sensors.

## Two axes: guides and sensors

Every part of a harness does one of two jobs. Böckeler's article (linked below) calls them
feedforward and feedback controls.

**Guides are feedforward** — they steer *before* the model acts. Custom instructions, an
instruction file such as `CLAUDE.md` or `AGENTS.md`, skills, specs, examples, tool descriptions:
all guides. They encode "here's how we do it" so the model starts on the right path.

**Sensors are feedback** — they observe *after* the model acts and report what's wrong. A
checklist pass, tests, a typecheck, a linter, a build, an LLM acting as judge: all sensors. They
turn a silent mistake into a signal.

The video's whole thesis is in its title — *beyond skills*. Guides alone don't scale, because you
cannot anticipate every way a model will go wrong. A guide is a hope; a sensor is a fact. The
article draws one more useful line: some sensors are **computational** (a test or a word-count
check gives the same verdict every time, cheaply) and some are **inferential** (another model
judging tone or relevance, richer but not deterministic). Lean on computational checks wherever a
rule can be checked mechanically, and save the model-as-judge for what can't. *(Making a check
mandatory instead of advisory is a mechanics question — that's the Hooks & automation lesson;
here we care about the concept.)*

## Load-bearing vs decorative scaffolding

A useful test for any harness: is each piece **load-bearing** or **decorative**? A test suite the
agent runs every iteration is load-bearing — output quality actively depends on it. A rule in an
instruction file that nothing enforces is decorative: it looks like control, but the model can
drift past it and nothing stops it.

The move is to make your scaffolding load-bearing — wire it into the path the work actually
travels. A check that runs on every output and feeds its result back is load-bearing; a document
the model *might* read is not. Opinionated beats permissive: a harness with strong defaults
narrows the model to the good choices instead of trusting it to find them.

> 💡 **Try it:** map your own harness in five minutes. **If you don't code:** open the custom
> instructions or Project you use most and list each instruction as a guide. Then ask: which of
> these does anything actually *check*? Usually the answer is none. **If you code:** point your
> coding agent at a repo with the prompt below. Either way, the gap between what you *think*
> enforces quality and what actually does is usually wider than you'd guess.

```prompt
Audit this repo as a harness. List every guide (instruction files, skills, specs)
and every sensor (tests, typecheck, lint, CI, guardrails). For each sensor, say
whether it runs automatically or only when I remember. Then flag the rules I rely
on that nothing enforces — the decorative scaffolding.
```

## Separate the generator from the judge

A sensor is only trustworthy if it's independent of what it's grading. A model reviewing the same
context that just produced the work is a weak sensor — it's biased toward its own reasoning and
will wave it through. So **separate generation from evaluation**: run the check in a clean
context — a new chat, a different subagent, sometimes a different model or provider entirely.
The evaluator should judge the artifact, not the thought process that made it.

The same logic says: strip the author's self-assessment ("I've made sure every claim is
sourced") before you hand work to a reviewer, so it checks rather than agrees. A doer/checker
split beats one assistant marking its own homework. *(How you wire that check into a repeating
cycle — who runs when, when to stop — is the next lesson, → loop-engineering; here the point is
only that the two roles must be different passes.)*

## Context resets vs compaction

Long tasks outrun a single context window, and every new window starts blank. You bridge the gap
two ways: **compaction** (carry a summary forward; its mechanics and tradeoffs →
context-engineering) or a **context reset** — throw the window away and re-seed a fresh session
from durable artifacts: a progress file, git history, the spec. In a chat app, the reset is a new
chat started from a written brief.

Anthropic's long-running-agent work (linked below and in the backups) found that one model,
Claude Sonnet 4.5, showed "context anxiety" (wrapping up early as it neared its limit), so
periodic resets became essential to that harness; a later model largely dropped the behaviour.
The durable lesson for you: **don't trust the model's memory — externalize state into
load-bearing artifacts that survive a reset.** The harness holds the truth, not the context
window, and the right harness call can change when the model does.

## Worked example: a harness for weekly status updates

Say you send a status update every Friday, drafted with an assistant.

- **Guides:** a Project (or Custom GPT, or Gem) holding the update template, two past updates you
  were happy with, and the rule "every risk names an owner."
- **Sensor:** a separate checker chat with four checks: under 200 words; every risk has an
  owner; no dates in the past described as upcoming; no claim that isn't in this week's notes.
- **Loop-back:** paste the checker's FAIL lines into the drafting chat and ask for a fix of
  those lines only.

Two weeks in, you notice the checker keeps flagging the same thing, missing owners. That's your
signal to strengthen the guide (add a third example that shows owners) rather than keep catching
it after the fact. That's the harness habit: guides prevent, sensors catch, and repeated catches
tell you which guide to fix.

## Common failure modes

- **A rule you wrote down keeps getting broken** → it's a guide with no sensor → add a check
  that runs every time and names the failing line.
- **The reviewer approves everything** → it shares context with the author → review in a fresh
  chat or with a different model, without the author's self-assessment.
- **The checklist grows to twenty items and nobody runs it** → the sensor is too expensive →
  keep three to five checks that catch real, repeated mistakes.
- **A long task drifts after a summary** → you trusted compaction to carry the facts → keep a
  progress or decisions file and restart from it.

## The habit

Name every part of your setup as a guide or a sensor, decide which are load-bearing, then go
strengthen the weakest sensor. That single habit is the difference between *hoping* the model
behaves and *engineering* it to.
