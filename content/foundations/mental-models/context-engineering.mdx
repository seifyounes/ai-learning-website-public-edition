Prompt engineering was table stakes — the craft of phrasing one request well (that's the
previous lesson, → prompting-in-2026). The skill that actually decides whether an *agent*
succeeds over a long run sits one level up: **context engineering** — deciding what occupies the
model's window at every single turn. Anthropic published its guidance for agents in September 2025
(linked below), and it's the current foundation everything else stacks on.

## From prompt to context

A prompt is one message. **Context is everything the model sees when it generates the next
token**: the app's hidden instructions, your custom instructions or instruction file
(`CLAUDE.md`, `AGENTS.md`), the whole conversation so far, any files you attached, and the
results of any searches or tools it ran. On a one-shot question the two are nearly identical.

In plain terms: imagine briefing a brilliant temp who forgets everything the moment they leave
the room. What's on their desk *right now* is all they have. A long chat to plan a trip, a
research session with five uploaded PDFs, a 90-minute coding-agent session: in each, you write a
handful of prompts, but the desk gets re-stacked dozens or hundreds of times as files, search
results and old replies pile up. Engineer *that* and you're steering; polish the wording alone and
you're rearranging one message inside a moving river.

## Curate the tokens, every turn

The core discipline is unglamorous: **treat the window as a finite budget you actively spend, turn
by turn.** You already know *why* it's finite and why a stuffed window degrades — tokens, the
window, and "lost in the middle" were the earlier lesson (→ tokens-and-context). Context
engineering is what you *do* about it. Every token you add is a bet that it earns its attention;
irrelevant tokens don't just cost money, they dilute the signal and drag the model toward the wrong
thing ("context rot"). More context is routinely *less* intelligence. So each turn is subtraction as
much as addition: keep the window dense with exactly what this step needs and nothing it doesn't.

## Write, Select, Compress, Isolate

Lance Martin's framework gives you four moves — the whole discipline factors into these, and each
maps onto something you can do in a chat app or a coding agent:

- **Write** — push state *out* of the window so it survives. Scratchpad notes, a plan file, the
  TODO list, a rules file (`AGENTS.md`, `CLAUDE.md`) as durable memory. The window is working
  memory; files are long-term memory. (Structuring that rules file → claude-md-and-memory.)
- **Select** — pull the *right* context *in* at the moment you need it: read a file, search the
  codebase, call a tool, load a skill. Retrieval on demand, not everything up front.
- **Compress** — shrink what's already in the window while keeping the signal: summarize the
  history, cut a 500-line tool dump down to the ten lines that mattered.
- **Isolate** — split context across boundaries so no single window has to hold it all: hand a
  subtask to a subagent with its own clean window.

Martin demos this in LangGraph; ignore the framework and keep the moves. **In a chat app** they
are: a notes doc or Project knowledge (Write), pasting only the section you need (Select), "give
me a brief of this chat so far" before starting fresh (Compress), and a separate chat for a side
research question (Isolate). **In a coding agent** (Claude Code, Cursor, Codex, Copilot) they are:
instruction and plan files, on-demand file reads, `/compact` or its equivalent, and subagents.

## Compaction: buy back the window

**Compress** is the one you'll feel first. As a session runs, history fills the window; left alone,
the oldest turns fall off the edge and the agent starts forgetting decisions and re-reading files it
already saw. **Compaction** is the fix: summarize the run-so-far into a lean brief and continue from
*that* instead of the raw transcript. Coding agents such as Codex and Claude Code do this
automatically as you near the limit, and both let you force it with `/compact` — steer the summary
so it keeps what matters:

```prompt
/compact keep the data-model and deploy decisions and the current task list; drop the raw file dumps and the dead-end we already abandoned
```

The trap: compaction can quietly summarize away a load-bearing fact. So **Write before you
Compress** — promote the decisions you can't lose into a rules file (`AGENTS.md`, `CLAUDE.md`) or a
plan file *first*, where the summary can't touch them.

> 💡 **Try it:** next time a session feels like it's "getting dumber," don't re-explain everything
> (that makes the window worse). **In a chat app:** ask "Write a 10-line brief of the goal, the
> decisions so far and the open questions," open a new chat, paste the brief, and carry on.
> **In a coding agent:** run `/compact` (or your tool's equivalent) with a focus line. Either way,
> watch it get sharp again.

## Just-in-time, not just-in-case

The instinct to paste *everything* up front — "so the model has full context" — is the classic
mistake. **Just-in-time retrieval** is the opposite, and it wins: keep lightweight references (file
paths, function names, a table of contents) and let the agent pull the actual content only when a
step needs it. Pre-loading thirty files spends your window and the model's attention on the
twenty-nine irrelevant ones; loading by reference keeps every token live. This is why coding agents
search and read on demand instead of ingesting your whole repo, and why a lean rules file
(`AGENTS.md`, `CLAUDE.md`) that *points* to detail beats one that inlines all of it. Write + Select working together: persist state
outside the window, then re-hydrate exactly the slice you need.

## Isolation: a fresh window per subtask

Some work is a context hazard — a research sweep that pulls 200 KB of docs, or a scan of fifty
files. Run it in your main window and it poisons everything downstream. **Isolate** it: dispatch it
to a subagent that gets its own clean context, burns *that* window on the mess, and returns only the
distilled result. Your main thread stays dense; the subagent's 200 KB never touches
it. That's the *context* reason subagents exist — separate from *how* you define and run them
(→ subagents-and-agent-teams) and from the verifier role they can also play (→ harness-engineering).
Here the point is one thing: **isolation is a context-management tool.**

## Bake the context once

The last move is about time, not one session. Some context you supply *over and over* — your stack
defaults, an app's brand voice, the rules a task always needs. Re-typing it each session is the same
waste as pre-loading files: pure overhead. **Bake it once** into a durable asset — a rules file such
as `AGENTS.md` or `CLAUDE.md`, a skill, a Project — so it loads automatically and you never
re-explain it. This is the capture →
template → reuse loop from the prompting pillar, grown up: a prompt you use twice is worth *saving*;
one you run weekly with the same loaded context is worth *graduating* into baked context. The signal
to promote is **frequency × shared-context × reuse**. Your prompt library becomes your context
library — the highest-leverage tokens you own, written down once and spent for free forever.

## Common failure modes

- **The assistant forgets a decision you made an hour ago** → it was only in the chat, and
  the chat got summarized or scrolled away → write load-bearing decisions to a file or
  Project before compressing.
- **Answers get worse after you upload "everything"** → irrelevant material is competing for
  attention → select: give it a table of contents and the one section that matters.
- **A side question derails the main task** → the side research filled the window with noise
  → isolate it in a separate chat or subagent and bring back a three-line answer.
- **Every new session starts with ten minutes of re-explaining** → context you need every time
  isn't stored anywhere durable → bake it into custom instructions, a Project, a Gem or an
  instruction file.
