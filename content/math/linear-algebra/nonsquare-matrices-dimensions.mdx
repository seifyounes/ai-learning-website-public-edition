  ```python
  import numpy as np

  tokens, d, d_head, vocab = 10, 768, 64, 32000
  X = np.random.randn(tokens, d)        # one row per token
  W_q = np.random.randn(d, d_head)      # a query projection
  W_out = np.random.randn(d, vocab)     # an output head

  Q = X @ W_q
  print("Q:", Q.shape)
  scores = Q @ Q.T
  print("scores:", scores.shape)
  logits = X @ W_out
  print("logits:", logits.shape)
  print("output head parameters:", W_out.size)
  try:
      X @ W_q.T

      print("error:", e)
  ```

So far every matrix was square: 2D to 2D, 3D to 3D. The matrices inside real models almost
never are. An embedding table, a query projection, an output head: each one maps vectors of one
size to vectors of another. This short lesson gives you one rule that makes all of them
readable from their shape alone.

## Columns are inputs, rows are outputs

Nothing new is needed. A linear map from 2D into 3D still keeps grid lines parallel and evenly
spaced and the origin fixed, and it's still recorded by where each input basis vector lands.
Two input basis vectors, each landing on a point with three coordinates, give **two columns of
three numbers: a 3 × 2 matrix**.

So an **m × n matrix maps n dimensions to m dimensions**. The number of columns is the input
size; the number of rows is the output size. A 2 × 3 matrix takes 3D down to 2D. A 1 × 2 matrix
takes 2D vectors to single numbers, which is where the dot product comes from
(→ dot-product-duality).

## Rank when the shapes differ

A 3 × 2 matrix with independent columns has a column space that is a plane inside 3D. That's
rank 2, as high as two inputs allow, so it's **full rank**, yet it can't reach most of 3D.
Going the other way, a 2 × 3 matrix flattens 3D onto at most a plane, so at least one direction
lands on zero.

## Worked example: shapes in a tiny model

**A 3 × 2 map.** M has columns (1, 0, 2) and (0, 1, −1). Applied to (3, 2):
3·(1, 0, 2) + 2·(0, 1, −1) = **(3, 2, 4)**, a 3D point on the plane spanned by the columns.

**Shapes chain by the inner size.** (a × b) times (b × c) gives (a × c), and the two b's must
match. In code, data usually sits in rows, so a batch of 10 token vectors of width 768 is a
10 × 768 matrix X.

1. A query projection W_q of shape 768 × 64 gives X·W_q: **10 × 64**.
2. Scores between those queries, (10 × 64)(64 × 10): **10 × 10**, one per pair of tokens.
3. An output head of shape 768 × 32,000 gives X·W_out: **10 × 32,000**, one score per token in
   the vocabulary, and it holds 768 × 32,000 = **24,576,000** parameters.

The math writes y = W·x with W as (out × in); code that writes x @ W stores the transpose.
Same map, different bookkeeping.

## Common mistakes

- **Reading the shape backwards.** In y = W·x, columns are inputs. Check each library's
  convention: PyTorch's `nn.Linear` stores (out, in).
- **Assuming full rank means "reaches everything".** A tall matrix is full rank when its columns
  are independent, yet its outputs fill only a slice of the space.
- **Expecting to undo a projection down.** Going from 768 to 64 loses directions; mapping back up
  can't restore them.
- **Fixing shape errors by reshaping.** A transpose is often right; a reshape usually scrambles
  the data.

## Where you'll see it in AI

- **Attention projections:** each head maps d-wide token vectors down to a smaller head width
  (→ transformers-attention).
- **Embedding tables and output heads:** a vocabulary of V tokens and width d is a V × d table,
  and the head maps d back to V scores (→ what-is-an-llm).
- **Low-rank adapters:** a tall-times-wide product, as in → rank-column-null-space.
- **Embedding search:** shrinking vectors to fewer dimensions saves storage at some loss of
  detail (→ embeddings-vector-databases).
