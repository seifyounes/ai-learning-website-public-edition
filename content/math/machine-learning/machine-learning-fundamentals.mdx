Before transformers, before RAG, there is one recipe, and every AI system you'll ever ship,
including the LLM APIs you call, came out of it: **fit a model on one part of the data, judge
it on a part it never saw, and keep the one that predicts best.** Learn that once and a hundred
buzzwords collapse into three questions: *what's the data, what's the loss, does it generalize?*

## The recipe

**Supervised learning** has three parts: examples with known answers (inputs → labels), a
**loss** that measures how wrong a prediction is, and a way to adjust the model to make the
loss small. A spam filter, a churn model and LLM pretraining are all this recipe. Pretraining
just uses huge amounts of text as data and "the next token" as the label.

## Generalization is the only thing that matters

A model that aces its training data has proven nothing; maybe it **memorized**. So we split:
**train** (learn), **validation** (tune choices), **test** (touch once, at the end). The
moment information from test leaks into training (duplicated rows, tuning on test, eval
examples pasted into prompts) your score becomes fiction.

> 💡 **Try it:** in Google's MLCC overfitting widget, crank model capacity up on noisy data and
> watch the curve contort itself through every point, then watch test error climb.

## Worked example: a churn model, start to finish

A hypothetical subscription business has 1,000 customers; 150 cancelled last quarter. You want
to predict who cancels next.

1. **Baseline first.** Always predicting "stays" is right for 850 of 1,000: **85% accuracy**.
   Any model has to beat that to be worth anything.
2. **Split.** 800 customers to train, 200 to test, keeping the same 15% cancel rate in both
   halves.
3. **First model:** a deep decision tree. Training accuracy 99%, test accuracy 84%. It
   memorized the training customers and is *worse* than the baseline on new ones
   (→ bias-variance-overfitting explains why).
4. **A too-good second try.** Someone adds a `refund_issued` column and test accuracy jumps to
   98%. Suspicious: refunds are issued *because* people cancel. The column leaks the answer.
   Drop it.
5. **Honest model:** a simple classifier without the leaky column (→ logistic-regression).
   Training 89%, test 88%. The two numbers are close and it beats the baseline by 3 points.
6. **Is 3 points real?** At n = 200 the rough noise band is ±1/√200 ≈ ±7 points
   (→ standard-error-vs-deviation). So the gain is promising, not proven. Rotating the test
   slice gives a steadier answer (→ cross-validation-folds).

Nothing in that walk-through needed a large model. It needed a baseline, a clean split and a
nose for leakage.

## Common mistakes

- **Scoring on training data.** Training accuracy measures memory as much as skill; report the
  held-out score.
- **High accuracy, useless model.** It just predicts the majority class. Compare against the
  baseline every time.
- **Leakage.** A column known only after the outcome, duplicates across splits, or a random
  split on time-ordered data. Drop post-outcome columns, dedupe, and split by time when rows
  have dates.
- **Wearing out the test set.** If you keep tuning against it, it becomes training signal.
  Make choices on validation data and touch test once.

## Where you'll see it in AI

- **Evals for LLM apps** are this recipe's test set: a fixed set of cases the prompt never saw
  (→ evaluation-metrics, → evals-and-testing).
- **Fine-tuning** keeps a held-out set to catch a model that memorized your examples
  (→ fine-tuning-fundamentals).
- **Training** is the same loop at any scale: the rest of this track walks through the loss
  (→ least-squares-regression), how a model fits (→ fitting-by-gradient-descent), and the
  tabular models that still win on spreadsheets (→ gradient-boosting-trees).
