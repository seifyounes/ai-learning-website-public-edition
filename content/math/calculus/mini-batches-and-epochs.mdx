task: |
  **See batch size trade steps for noise (25 minutes, Python).**

  This fits one weight to 10,000 examples generated with a true weight of 3, for exactly one
  epoch at four batch sizes, then shows how much single-batch gradients vary:

  ```python
  import random

  rng = random.Random(0)
  data = []
  for _ in range(10_000):
      x = rng.uniform(-1, 1)
      data.append((x, 3 * x + rng.gauss(0, 0.5)))    # true weight is 3

  def grad(w, batch):    # gradient of mean squared error for prediction w * x
      return sum(2 * (w * x - y) * x for x, y in batch) / len(batch)

  def train(batch_size, lr=0.5):
      w, steps = 0.0, 0
      rng.shuffle(data)
      for i in range(0, len(data), batch_size):
          w -= lr * grad(w, data[i:i + batch_size])
          steps += 1
      return w, steps

  for bs in (10_000, 1_000, 100, 10):
      w, steps = train(bs)
      print(f"batch {bs:>6}: {steps:>5} steps in one epoch, w = {w:.3f}")

  print("full gradient at w=0:", round(grad(0.0, data), 2))
  print("five batches of 32:", [round(grad(0.0, rng.sample(data, 32)), 2) for _ in range(5)])
  ```

  Then answer: which batch size got closest to 3 in one epoch, and why didn't the smallest one
  win?

  Success: full-batch takes 1 step and ends far from 3 (about 1.0); batch 100 lands about 3.00;
  batch 10 takes 1,000 steps but ends slightly off (about 3.1) because its steps are noisier; and
  the five 32-example gradients scatter around the full gradient of about −2.0.

The one idea of this lecture: **instead of reading the entire training set before each step,
cut it into small mini-batches and take a gradient step after every one.** The cost of one step
drops dramatically, so training starts making progress almost immediately. Every modern
training and fine-tuning run works this way.

## The problem with the full batch

In theory the cost is an average over all `m` training examples, so its exact gradient needs all
of them. Vectorised code handles thousands at once, but with five million examples you still
process all five million before the first step, and again before the second. That's **batch
gradient descent**: accurate, and slow.

## Mini-batches

Split the set into mini-batches of, say, 1,000 examples: `X{1}, Y{1}` is the first 1,000,
`X{2}, Y{2}` the next, up to `X{5000}`. For each mini-batch `t`:

1. Forward pass on `X{t}` only (vectorised over its 1,000 examples).
2. Cost `J{t}`, the average loss over those 1,000.
3. Backprop to get the gradient of `J{t}`.
4. Update every weight: `W ← W − α·dW`.

One pass through all the mini-batches is an **epoch**. Batch gradient descent gets one step per
epoch; mini-batch gets 5,000. You usually run several epochs.

## Worked example with real numbers

**Counting steps.** 2,000 fine-tuning examples, batch size 8, 3 epochs: `2,000 ÷ 8 = 250` steps
per epoch, 750 in total. With 50,000 examples and batch 64, an epoch is `⌈781.25⌉ = 782` steps.

**Progress in one epoch.** Fitting one weight (true value 3) to 10,000 examples, one epoch,
learning rate 0.5, starting from 0 (the task's script):

| batch size | steps | final w |
|---|---|---|
| 10,000 (full) | 1 | 1.01 |
| 1,000 | 10 | 2.97 |
| 100 | 100 | 3.00 |
| 10 | 1,000 | 3.10 |

The full batch barely moved. Mini-batches got there within the same single pass over the data.
The smallest batch took the most steps but ended a little off, because a gradient from 10
examples is noisy: at `w = 0` the full gradient is −2.02, while five random batches of 32 gave
values from −1.36 to −2.24. Each one points roughly the right way, not exactly. (Andrew Ng's
next video in the course explores this noise; → learning-rate-decay-schedules shows how
shrinking the step size late in training calms it.)

## Common mistakes

- **Comparing runs by epoch when batch sizes differ.** The step counts differ too.
- **Changing batch size without retuning the learning rate.** The effective step changes.
- **Panicking at a jagged per-step loss curve.** Each point is a different mini-batch; judge the
  trend and the validation curve.
- **Forgetting to shuffle.** Mini-batches should be random slices, not sorted runs of similar
  examples.

## Where you'll see it in AI

- **Fine-tuning settings** (batch size, epochs, steps) are exactly these numbers
  (→ fine-tuning-fundamentals).
- **Optimizers** like momentum and Adam smooth the noisy mini-batch gradients
  (→ momentum-optimizer, → adam-optimizer).
- **Overfitting checks:** more epochs means more passes over the same data, so watch the
  held-out curve (→ calculus-for-optimization, → evaluation-metrics).
