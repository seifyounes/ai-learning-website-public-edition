applyIt: |
  **Before you say "the new version is better", state the null hypothesis and say what result
  would reject it.** Take one change you're about to judge: a reworked prompt, a different model,
  a new step in an automation, a template for a weekly report.

  1. Write the null: "There is no difference in [metric] between the old and new version."
  2. Decide the test set before looking at results, and run **both** versions on the **same**
     inputs.
  3. Count only the inputs where the versions disagree, and see whether one side wins clearly
     more of them than a coin flip would.
  4. Report "rejected" or "failed to reject", never "proven equal".

  **If you build software:** keep a fixed regression set and a script that runs two versions side
  by side and prints the disagreement counts. **If you don't code:** a two-column spreadsheet of
  pass/fail marks for the same inputs is enough.

Every "is the new version better?" question in AI work is a **hypothesis test**. Two prompts,
two models, two retrieval settings: you have noisy scores for each, and you need a rule for when
a gap is real. Hypothesis testing gives that rule, and its most useful habit is a modest one: you
either reject a claim or fail to reject it. You never prove it.

## Reject or fail to reject

Results vary from run to run for reasons you don't control: which examples were in the set, how
the sampler happened to draw. So one result suggests a hypothesis, and repeats test it.

- If the data points clearly against the hypothesis, you **reject** it.
- If the data is roughly consistent with it, you **fail to reject**. That's weaker than "it's
  true": other hypotheses would fit the data just as well.

## The null hypothesis

When comparing two versions, there are endless specific claims you could test: B is 3 points
better, 4 points, 4.5. Instead, test one: **there is no difference**. That's the **null
hypothesis**. It needs no first experiment to set up, because "no difference" is always zero, and
it turns the question into a clean yes or no: does the data rule out "no difference"?

With few examples, small random changes can flip which version looks better, so you'll fail to
reject. With many examples, random flips stop mattering and a real gap can reject the null.

## Worked example: paired versus unpaired

Prompt A passes 168 of 200 questions (84%), prompt B passes 176 of 200 (88%).

**Unpaired view.** Treat them as two independent rates. Each has a standard error of about 2.5
points, the difference about 3.5. A 4-point gap is barely more than one standard error. **Fail to
reject.**

**Paired view.** Both ran on the same 200 questions. They agree on 188 (both pass or both fail),
which tells you nothing about which is better. On the 12 where they disagree, B wins 10 and A wins
2. Under the null, each disagreement is a coin flip. Ten or more heads out of 12, in either
direction, happens about **4%** of the time (2 × 79 ÷ 4,096). That's surprising enough to
**reject** the null at the usual 5% level.

Same data, different verdict. Pairing removes the noise of which questions happen to be easy or
hard, which is why it's the cheapest upgrade to any eval. How to read that 4% is the subject of
→ p-values-explained.

## Common mistakes

- **Treating "fail to reject" as "equal".** It means "not shown different", often because n is
  too small.
- **Setting the hypothesis from a tiny pilot.** Test the null instead of the pilot's number.
- **Running prompts on different examples.** You throw away the pairing and need far more data.
- **Changing the test set after seeing results.** Fix the set first, or the test means nothing.

## Where you'll see it in AI

Prompt and model comparisons on a regression set (→ evaluation-metrics), A/B tests of AI
features, research papers claiming one method beats another, and judge-based win rates. The
interval view from → confidence-intervals-for-evals asks the same question: does the interval of
the difference include zero?
