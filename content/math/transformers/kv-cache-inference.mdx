Generating text is a loop: run the model, pick a token, append it, run again. The KV cache is
the trick that stops that loop from redoing all its past work, and it explains three things
you pay for every day: **slow output, memory-hungry long contexts, and cheap cached input**.

## Why the naive loop wastes work

In the attention step (→ query-key-value-attention), every token produces a query, a key and a
value. With the causal mask, a token's key and value depend only on the tokens before it. So
when token 501 arrives, the keys and values of tokens 1 to 500 are exactly what they were a
step ago. Recomputing them is pure waste.

The fix: **store each token's key and value, per layer, the first time you compute them.** At
each new step, compute Q, K and V for the newest token only, compare its query with every
cached key, blend the cached values, and append its own K and V to the cache.

## Prefill vs decode: where your latency lives

- **Prefill:** the whole prompt goes through the model in one parallel pass and fills the
  cache. It is fast, and it sets *time to first token*.
- **Decode:** each output token needs its own sequential pass, because token t+1 needs token t
  as input. This per-token crawl is what users feel. Streaming hides it; shorter outputs fix it.

```diagram
PREFILL: one parallel pass
prompt t1 t2 … t4000
   │ all positions at once
   ▼
KV cache filled
   │
   ▼
sets time to first token

DECODE: one pass per token
new token → Q, K, V
   → attend to cache
   → next token
   → append its K, V
repeat per output token
   │
   ▼
wait ≈ output tokens
       × time per step
```

## Worked example: how big is the cache?

Per token, the cache holds one key and one value vector at every layer:

`bytes per token = 2 (K and V) × layers × model width × bytes per number`

Take a model with 32 layers and a model width of 4,096, stored in 16-bit numbers (2 bytes),
which is the shape of several 7-billion-parameter open models with standard attention:

- Per token: 2 × 32 × 4,096 × 2 = **524,288 bytes**, half a megabyte.
- A 4,096-token conversation: 524,288 × 4,096 ≈ **2.1 GB**.
- Serve 8 such conversations at once: about **17 GB**, more than the roughly 14 GB the weights
  take at 16 bits (7 billion × 2 bytes).

That is why long contexts and big batches run out of memory before the weights do, and why
newer models share keys and values across heads (grouped-query attention): 8 key/value heads
instead of 32 would cut every number above by 4×.

## Why cached input is cheaper

An **identical prompt prefix has identical KV states**, so a provider can keep them and skip
prefill for that part on your next call. That is prompt caching. A support assistant that sends
the same 3,000-token system prompt with every new email gets those 3,000 tokens billed at the
cached rate, unless something that changes (a timestamp, a user name) sits on line one, in
which case nothing after it matches.

## Common mistakes

- **Halving the prompt to fix latency.** Most of the wait is decode; cap the output length,
  ask for a tighter format, and stream.
- **Volatile text at the top of a reused prompt.** One changed early token invalidates the
  cache below it; put dates and retrieved documents at the end.
- **Sizing a GPU by the weights alone.** Add the cache: per-token bytes × context × batch.
- **Re-sending ever-growing chat history.** The cache and the bill grow every turn; summarize
  or start fresh with a short brief.

## Where you'll see it in AI

Every serving stack (vLLM, llama.cpp, Ollama, hosted APIs) manages a KV cache, and their
"tokens per second", "context length" and "cached input" numbers are all cache numbers. The
cost and latency trade-offs are applied in → cost-latency-caching, and the model these caches
belong to is the one you built in → build-gpt-from-scratch.
